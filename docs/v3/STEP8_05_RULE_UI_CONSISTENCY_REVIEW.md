# STEP8-⑤｜ルール説明と画面の整合チェック・実装前レビュー記録

日付：2026-11-16。対象：**現行の単発・小規模地域イベント準備支援Webアプリ**。旧空き家の物件・所有者・マッチング機能は取り込まない。**設計のみ。コード実装・テスト実行・公開なし**。

## 今回の推奨方針（既決の範囲で具体化）

1. **判定の正本**：[ADR-003](ADR_003_PRIORITY_RULES_ADOPTED.md)のP05、物理会場なしP08、ID昇順と[ADR-027](ADR_027_P08_P2_NO_FACILITY_AUTO_ESCALATION.md)の施設条件でもP08=P2基本を優先。古い判定表に残る「施設固有条件でP08をP1候補」といった行は**歴史的案で現行不採用**。
2. **文字列の正本**：[STEP8-④](STEP8_04_REASON_CODE_AND_SCREEN_COPY_DRAFT.md)の「理由→次の一歩→根拠」を基準に、画面では利用者が理解できる自然文を優先。reasonCode識別子や内部の`needs_information`をそのまま人に表示しない。
3. **表示例の整合**：「子どもが参加する体験会」でP05が未解決ならP05=P1。例示画面でP07等のP2を最優先として表示することは、別途P05完了・再確認不要のような条件を示さない限り**誤り**。
4. **情報が足りないとき**：質問への明示回答「未定」と未回答を混同せず、決まっていないことをそのまま説明。入力不足だけを理由に施設の法定義務、予約・許可・安全基準を確定しない。
5. **完了と要再確認**：本人の`completed`または`not_applicable`は本人の保存済み判断。`needsRecheck=true`なら再確認が未解決として残り、成功した明示操作のみ解除。出典の`needs_review`は利用者進捗とは別。
6. **旧イベントの進捗**：[ADR-026](ADR_026_U03_PROGRESS_CAS_INDEPENDENT_OF_INVALID_INPUT.md)どおり、保存済み入力が新しいバイト上限を超えていてもU03進捗のみCAS付き保存。U04入力全体は修正後の保存に限定。
7. **正式決定と推奨候補の区別**：P01〜P04、P06、P07、P09〜P12の新たなP2昇格条件を一括して正式決定とはしない。P01〜P12の文言、説明、否定例、テストの整合は推奨案として進める。

## 仕様間の不整合として注意すべき箇所

- **U03の古いモバイル例**は「子ども参加」なのにP2会場条件カードを代表として例示していた。P05が未解決ならP1となるため、例を修正して誤解を避ける必要がある。
- **初期要件草案の「JSONファイル入出力は対象外」**は[ADR-015](ADR_015_JSON_BACKUP_EXPORT_IMPORT.md)で**MVP対象に変更済み**。文書の初期章にも後続決定への注記が必要。
- **STEP4判定表v1.1のP08行**には過去の「公式条件でP1候補」が残るが、後続のADR-027で**不採用**。実装で古い表だけを拾わないよう表の近くへ注記する。
- 出典の**月次点検方針**はADR-009〜012で確定しているが、個々の高岡市施設の原ページが今現在有効であることの検証結果ではない。公式条件・申込期限の具体的断定は原ページ照合が終わるまで禁止。
- Unicodeの**文字数100/500**と**UTF-8実バイト4/16 KiB**は独立制限。JSONの**1ファイル100件かつ2 MiB**とも別。
- 理由コードの英語識別子は実装用の候補であり、現時点では安定IDが確定・実装されたとは扱わない。

## 次の設計タスクと品質ゲート

- **細部は推奨で進行**：U03代表カード、一覧、状態別文言、理由コードの表現統一、判定のテストベクトル整理。
- **外部事実の確認が必要**：高岡市の施設公式情報の原ページ確認、対象施設・利用者構成のスコープ、点検担当とレビュー結果。未確認の自治体条件を実装済み・検証済みと表現しない。
- **利用者の承認が必要になる場合**：基本6問・P01〜P12の変更、未採用の広範なP1/P2ルールの確定、本人の保存データの自動変更、利用対象・中心価値の変更、実装・公開開始。
- **実装の着手条件**：設計レビューの完了だけでは開始しない。ユーザーによる明示的な実装開始指示が必要。
