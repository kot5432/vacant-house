# A〜D共通｜チーム開発・統合・UIルール v1（2026-11-21）

> **対象**：富山県の地域活動に「参加する／企画する」単一のReact+TypeScript+Viteアプリ、A〜D開発者・E品質責任者。
> **位置づけ**：既存の[CONTRIBUTING](../../CONTRIBUTING.md)、[Git操作詳細](GIT_WORKFLOW_AND_BRANCH_RULES.md)、[ADR-029〜032](README.md)を優先して運用する**チーム共通の実施ルール**。本資料は設計・作業ルールであり、UI部品の実装や動作検証を済ませたことを意味しない。
> **重要**：A〜Dは4つの別アプリを作らない。リポジトリは1つ。短命ブランチからPR→レビュー→main統合して、全員が最新mainを取り込む。チーム承認前の配色数値は「仮基準」であり正式UIの最終決定ではない。

## 1. 守る原則（全員必須）
1. **同一リポジトリ・同一アプリ**。各担当者は自分のIssueと担当機能に集中する。別のViteプロジェクト、新しいpackage-lock.json、別の保存方式を独自に作らない。
2. **mainへ直接pushしない**。Issueごとに短命ブランチ→小PR→本人以外のレビュー→mainマージ。PR作成者の自己承認・自己マージは禁止（既存CONTRIBUTINGに準拠）。
3. **着手前に最新mainを取り込む**。他担当のPRがmainへ入ったら自分の作業ブランチを更新し、動作確認を繰り返す。**他人のファイルを手でコピーしない**。
4. **他担当の共有ファイルを勝手に改変しない**。共通API・UI・アプリのルート変更はIssue/PRで影響する担当者のレビューを求める。
5. **小さく統合する**。12/20に初めて結合するのではなく、11/29の初回小PRからmainへ順次統合。未完成の機能は明確にmockとし、実データや本保存と混同しない。
6. **既決ADRを守る**。D00〜D02＋U01〜U04、P01〜P12の親タスクのみ。旧空き家の物件機能や子チェックを足さない。
7. **無断公開しない**。CI・Vercel・外部公開・アンケート配布・イベント掲載承認は別の作業であり、このルールの追加では許可しない。

## 3. 型・API・データの共有
- **Dが正本**：EventInput / EventRecord / 親TaskProgress / validation / Repository契約。B/Cは同じ型をimportして使う。既存の[STEP25](STEP25_TYPESCRIPT_DOMAIN_TYPES_AND_REPOSITORY_SIGNATURES_20261119.md)とADR-032に従う。必要な10メソッドを勝手に減らさない。
- **Bが正本**：P01〜P12優先順位・該当性・理由と次の一歩の判定。画面側で独自に優先度を再計算しない。
- **C**：進捗更新・要再確認解除・編集はDのRepository APIを経由し、Dexieへ直接書き込まない。保存状態とUI仮状態を区別。
- **A/E**：ActivityCatalog（公開活動）と個人のEventRecord（主催）は別データ。参加閲覧で利用者の主催レコードを書き換えない。
- **B/C/Dの接続の最初の期限：11/25**。Dは型/APIの名称、引数、返り値、エラーと「まだmockの箇所」をIssue #40へ記載しB/Cへ知らせる。未完成の間は型に沿ったmockでUIを開発してよいが、本物の保存成功表示はしない。
- 共通API変更時：まずIssueに変更理由→使用者全員（特にB/C/D）に連絡→型と呼び出し側を調整→テスト結果をPRへ記載。

## 4. GitHub Desktopでの共同開発手順（全員）

### 初回
1. [セットアップ](../ALL_MEMBERS_PC_SETUP.md)に従い、一度だけClone。すでにclone済みなら複製しない。
2. GitHub Desktopで **main → Fetch origin → Pull origin**。
3. 各自に配布済みの最初のブランチに切替。A `feature/34-participation-entry`／B `feature/36-organizer-input`／C `feature/38-parent-progress`／D `feature/40-domain-types`。
4. メニュー **Branch → Update from main** などで最新mainを作業ブランチへ取り込む。未コミット変更がある場合は先に確認。競合したら勝手に上書きせずE・関係者へ相談。
5. `npm ci`（共通lockfile）、`npm run doctor`、`npm run typecheck`、`npm run build`、`npm run dev` を必要に応じて確認。PCセットアップの結果はIssue #55へ。

### 日々の作業
1. 作業開始時と**他メンバーのPRがmainへマージされた後**：最新mainを取得して自分のブランチへ取り込む。少なくとも開発日ごとに一度は更新を確認。
2. Issueに紐づく小さな編集だけ実行。AIコーディングには「担当Issue・既決ADR・本共通ルールを読み、変更予定のファイル一覧を先に示し、担当外/共有ファイルには無断で触れない」と明記。
3. 変更点を確認→手元で動かす→コミット→Push→PR→レビュー。**更新を取り込んだらtypecheck/buildと影響画面を再確認**する。
4. PRがmainへ入ったら、その担当者はIssueと関係者へ報告。「どこが完成」「何はmock/未実装」「残る課題」を分ける。
5. 競合時に `force push`、他人の作業破棄、「ours/theirs」で全選択しない。作業中の未コミット変更は消さず、状態を共有する。

### PRとレビュー
- PRにはIssue、変更ファイル、画面画像（機密や個人情報なし）、動作確認、失敗時/スマホ確認、設計との差分、影響先を記入。
- 未実行は`not_run`。AI生成コードの意味が分からないままレビュー依頼をしない。
- UIを変更したPRは共通UIルール準拠をチェック。保存/判定/公式情報を変えたPRはそれぞれD/B/Eの確認を追加。
- PR提出はDoneではない。別人レビュー・指摘対応・必要テスト・mainマージを確認して完了。

## 5. UI/UXを統一するルール（必須の原則）
1. **全画面で同じヘッダー・戻る導線・本文最大幅・主ボタン・カード・フォーム部品を使う**。共通部品が完成するまでは同じ暫定スタイルを使い、後で画面ごとに違う独自CSS体系を残さない。
2. **スマホ優先**。最低320px幅、200%文字拡大、Tab/Enter/Space/Escapeの主要操作を確認。色のみで重要状態を伝えない。
3. **同一操作は同じ見た目と文言**。主操作は各画面で原則1つ。ボタンの危険操作（削除）は二次操作＋確認。
4. **保存・失敗の語句を共通化**。「保存中…」「このブラウザに保存しました」「保存できませんでした」「別のタブで変更されました」など。ローカル保存をクラウド同期と表現しない。
5. **カード・入力・ラベルの構造を揃える**。ラベル→入力→補足/エラーの順。フォームに無意味な必須項目を増やさない。画面遷移は[全7画面契約](STEP14_SCREEN_BEHAVIOR_AND_ERROR_MATRIX_20261119.md)に従う。
6. **共通UIのCSS/React部品の単独オーナーはまだ確定していない**。最初のレビューでEがA〜Dと調整し、共有UI担当と変更レビュー体制を指定する。担当者が無断でグローバルCSSやApp.tsxを編集しない。
7. 開発画面に架空のイベントやmockを使う場合、**開発用サンプルと分かる表示**をする。承認済み公開イベントが0件なら0件と表示する。

### デザイントークンの**仮基準**（チーム確認前の推奨値）
仕様文書にある「明るい背景・落ち着いた青緑・読みやすい日本語」を起点とした**暫定の数値**。以下はまだ正式採用色ではなく、チーム承認後に単一のtoken/CSS変数へ集約する。各担当が独立した色・間隔を決めない。

| トークン | 推奨初期値 | 用途 |
|---|---|---|
| `--color-bg` | `#F7FAF9` | ページ背景 |
| `--color-surface` | `#FFFFFF` | カード、入力欄 |
| `--color-text` | `#18322E` | 主要文字 |
| `--color-muted` | `#60736F` | 補足説明（コントラスト検証前） |
| `--color-primary` | `#167B72` | 主操作 |
| `--color-border` | `#D9E5E1` | 区切り・入力枠 |
| `--radius-card` | `12px` | カード |
| `--radius-control` | `8px` | 入力欄・ボタン |
| `--space-unit` | `4px` | 8/12/16/24/32px単位の余白 |
| `--content-max` | `960px` | 本文の最大幅（スマホ時は左右16px目安） |
| 本文 | `16px`, `line-height: 1.6` | 日本語可読性 |
| フォント | システム日本語サンセリフ（例：`system-ui, sans-serif`） | 個別の外部フォント読み込みなし |

文字色・ボタン色・エラー色のコントラストを実機で検証し、必要なら数値を修正する。危険/注意/保存失敗は色に加えてアイコンまたは文章を表示。**仮基準を勝手に既決ADRと同等に扱わない**。
