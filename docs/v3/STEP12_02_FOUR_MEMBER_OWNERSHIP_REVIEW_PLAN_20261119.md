## 3. レビュー相互組み合わせ
- A ↔ C：入力型・判定・保存・JSON。片方の変更が他方へ波及する場合、**両方レビュー**。
- B ↔ D：参加画面と原文の出典・表現。個別イベントの確認者と公開承認者を同一人にしない。
- B ↔ C：保存中/成功/失敗/競合・未保存ドラフトのUI。
- A ↔ D：公開活動のカタログ型・地域/分野のタグ・参加のNextAction判定。
- チーム全員：コンテストの発表で、地域課題/需要仮説と「まだ検証できていないこと」を分けて説明。

## 5. 分担人数を実際の4人へ割り当てる判断基準
- 最も仕様の矛盾に気付ける人：A。言語経験の多さより設計の説明力。
- 操作を人に試してもらい、説明・デザインを得意とする人：B。
- データが消える/競合する問題を粘り強く追える人：C。
- 富山の一次情報を調べ、出典を読み込み、参加側のデータも作りたい人：D。
- 4人が初心者ならAIコーディングで**各人が自分の担当領域を説明・レビュー**できることを優先。「AIが作ったのでわからない」は完了にしない。
- 4人の経験差が大きい場合、Cには技術レビュー相手Aを必ず付け、B/Dにもコードを扱う機会を持たせる。
- 役割決定はメンバー自身の希望と、担当できる時間を聞いた上で実名/ユーザー名を記入。**現段階で勝手に人名を入れない**。

## 6. 共同運用：GitHubルールの提案
- Issueで着手範囲、担当、レビュアー、期待ケース、未決値、Doneの証拠を明記。
- 実装開始許可後の各PRは**できれば本人以外がレビュー**。本人レビューのみで「確認済み」としない。
- ユーザーデータ/個人名/連絡先/実行環境の秘密情報をPR・サンプルに含めない。
- 新たな重要な仕様変更は勝手に既決ADRを上書きせず「提案→レビュー→ユーザー判断→新ADR」を原則にする。
- CI・ブラウザ確認・利用者テストは、実施するまでは`not_run`。コードレビューだけでPASSとしない。
