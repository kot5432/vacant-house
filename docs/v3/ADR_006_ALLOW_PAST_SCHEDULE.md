# ADR-006｜過去の希望開催日・開催月を警告付きで許容（A案正式採用）

決定日：2026-11-15。**利用者が明示採用済み。実装・テスト・Vercel公開は未実施**。対象は単発・小規模の地域イベント準備支援アプリ。旧空き家案・物件マッチング・所有者向け用途診断は一切対象外。

## 正式決定

- Q3の`schedule`は実在する暦日`YYYY-MM-DD`、暦月`YYYY-MM`、`undecided`を受け付ける。**過去の実在日／月は保存・閲覧・編集可能**。
- 過去と判定したときは**注意メッセージ**を示すが、エラーにしない。注意は明確なテキストで伝え、確認不要の自動改変・未来日への強制修正をしない。
- `date`は`localCalendarDate`（評価基準となるユーザー側の暦日）より**前の日**なら過去と判定。当日は過去扱いしない。
- `month`は`YYYY-MM`同士を比較し、**当月は過去扱いしない**。過去月のみ警告。月初1日を開催日だと補完しない。
- 暦日のバリデーションで無効とするのは、形式不正、実在しない日付（例：2026-02-30、平年の2月29日）など。うるう年を正しく扱う。
- `schedule=undecided`は回答済みの未定として受け付け、年月日を推測しない。
- 過去の日付を設定しても、**イベントが開催済み・募集終了・申請期限切れ・完了済みだと自動判定しない**。期限「開催14日前」等の未採用閾値も導入しない。
- U02の初回入力中は永続下書き保存をせず、初回プラン生成に伴うIndexedDB保存成功後だけU03へ。U04で日時を変える場合はドラフト→明示反映の保存成功で確定。

## 表示と日付基準

警告例：「選択された開催時期は過去です。この日付のまま準備プランを作成できます。」（開催月のときは「この月」）。**注意の後に選択を変更しないで続行する導線**を残す。開催予定と過去の記録は意味が異なるため、利用者に確認を促す文言にする。

ルールエンジンはブラウザの現在時刻を直接参照せず、アプリケーション層から`localCalendarDate: YYYY-MM-DD`を明示的に受け取る。境界日時に依存する場合も同じ`localCalendarDate`なら同じ結果とする。テストではこの日付を固定する。日時のタイムゾーン自動変換で入力`YYYY-MM-DD`が前日にずれないよう日付単位で扱う。
