# STEP7-㉑｜新しい文字列バイト上限を超える既存保存イベントの扱い（未決・比較）

作成：2026-11-15。**利用者確認待ち**。正式採用済み：[ADR-008](ADR_008_OPTIONAL_TEXT_LIMITS.md)（施設名100書記素・説明500書記素）と[ADR-024](ADR_024_UTF8_TEXT_BYTE_LIMITS.md)（それぞれ4 KiB／16 KiB UTF-8上限）。現行地域イベント準備支援アプリのみ。旧空き家・物件・マッチングは一切扱わない。**実装・試験未実施**。

## 問題

実装前の設計では、将来JSONバックアップ・旧形式・IndexedDBのイベントを読み込んだとき、現行のバイト上限を超える文字列がある可能性を想定する。**本人のメモ・進捗を黙って切断・削除してはいけない**。同時に、上限違反の新しい内容を保存成功として扱うことも避けたい。

## 比較する3案

| 案 | 既存レコードが上限を超えていた場合 | 利点 | 注意点 |
|---|---|---|---|
| **A（推奨）** | **読み取りは許可し、注意表示。該当テキストを修正してからU04保存可**。データは自動変更しない。JSONインポートは現行仕様の上限に適合しなければ全件拒否。エクスポートは不適合レコードを無断で除外せず、対応できない場合は説明 | 本人の既存情報の閲覧を維持し、段階的に修正可能。保存と復元の整合が明瞭 | 内容を修正しない限りバックアップを作成できないイベントがあり得る |
| B | **既存レコードは閲覧・編集でき、旧上限のまま保存し直せる特例**を設ける。インポートにも旧版例外を追加 | 過去データの維持を優先 | 最新の安全上限を例外で緩め、検証とUXが複雑になる |
| C | **制限超過を検出したら該当メモを自動で短くして保存** | 制限へすぐ収められる | 本人の情報を無断で失わせるため非推奨 |

**推奨A**：ユーザーの記録を壊さない一方、新しい保存・インポートには一貫したバリデーションを適用する。バックアップをエクスポートできない場合も、何が原因でどう修正すればよいか説明する。

## A案の技術・UI細則候補（承認前）

- U01一覧・U03閲覧は、既存イベントの読み取りに成功する限り使用可能。ただし「このイベントには現在の文字列サイズ上限を超えるメモがあります」と案内。**DBを黙って書き換えない**。
- U04を開くと該当欄を強調し、現在の書記素数・UTF-8実バイト長・上限を示す。修正・キャンセルの選択を本人に残す。U04保存前に全入力の検証が必要。
- 旧版などからのインポート時は**現在の上限に合致しないファイルは全件拒否**。データを一部だけ取り込まない。
- エクスポート時は本人が選んだイベントに不適合な文字列があれば、**選択された全件のバックアップが成功したと誤表示しない**。原因となるイベントを示し、選択を見直す・元の内容を修正する導線を出す。他のイベントを黙って含めたり外したりしない。
- 上限を超えるメモがあっても、**タスクの進捗・再確認状態を勝手に解除・巻き戻さない**。本人が保存を選ぶまで記録は変えない。
- 以前のバックアップから復元できない事情を明示し、互換性が検証済みの旧形式の変換でも、意味を保てない場合は無断の切断をせず拒否。
- 警告の表示条件とエラーのUIはPC・スマホで検証。イベント名、内容をエラーに過剰引用しない。
