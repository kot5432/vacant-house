> 現行「初めて単発・小規模の非営利地域イベントを主催する人向け準備支援Webアプリ」のみ。旧空き家・物件マッチング・所有者診断は対象外。
> 依存：[ADR-002](ADR_002_NO_PHYSICAL_VENUE_SCOPE.md)、[ADR-003](ADR_003_PRIORITY_RULES_ADOPTED.md)、[U03](STEP5_03_PREPARATION_PLAN_UI.md)、[U04](STEP5_04_EDIT_SAVE_ERROR_UI.md)、[データ](DATA_DESIGN_V1.md)。

## 1. 状態を3軸に分ける

1. **算定された該当性** `applicability: yes | no | needs_information`（ルールエンジンの出力。本人の進捗とは独立）。
2. **本人が更新した進捗** `status: not_started | in_progress | completed | not_applicable`。初期は未着手。
3. **条件変更で必要になった再確認** `needsRecheck: boolean`, `recheckReasonCodes[]`。完了や対象外と同時に成立する。

子チェック項目の`applicability=no`（建物予約が不要など）は親の`status=not_applicable`に自動伝播しない。子項目をすべてチェックしても親を自動完了しない。

## 2. U03の提案操作

- 各タスク行：`タイトル / P1|P2|P3 / 未着手|進行中|完了|本人が対象外 / 要再確認`をテキストで表示。展開ボタンと進捗メニューは別操作。
- 進捗メニューから本人が`完了`を選ぶと、確認した事実を本人が表明したものとして保存を試みる。法令上の完了や安全性の保証ではない。
- `対象外`を選んだときは**軽量な確認**（例：「この準備は今回行わないという判断でよいですか？」）。安全／公式条件に関するタスクでは「必要な確認がなくなるわけではありません」を明示。自由記述で理由を入力させない（入力負担と個人情報増を防止）。
- 本人が対象外にしても、公式根拠・施設条件の適用注意や不明点は、根拠のある範囲で見られる状態にする。代表優先候補からは通常除外されるが、`needsRecheck=true`なら再確認候補に戻す。
- `完了`または`対象外`のタスクに`needsRecheck=true`が立つと、行の状態は**「以前は完了／対象外・現在の条件で再確認が必要」**とし、優先候補に含める。本人の以前の判断値は保存し続ける。
- 通常の`進行中`や`未着手`に`needsRecheck`が立った場合も、別のフラグとして表示する。ただしルールで過剰に付与しない。

## 3. 再確認を解除する流れ（ADR-004正式採用）

```text
U04で会場を変更 → P08の依存条件に変化 → 完了のままneedsRecheck=true
 U03: 「以前は完了・新しい会場の条件を再確認してください」
 タスクを開く: 変わった前提と確認事項、該当する出典・確認日を表示
 [再確認を終えた]       [進捗を変更]
       ↓
「今回の条件で確認を終えましたか？」（**確認ダイアログの有無・文言は未承認**）
       ↓
progress.statusを保持したままneedsRecheck=false、recheckReasonCodesを消去
       ↓
同一イベント内でrevision照合→IndexedDBトランザクション保存
       ↓
成功後に「このブラウザに保存しました」。失敗なら解除完了と表示しない
```

**大事な例外**：以前の`status=not_applicable`は「本人が不要と判断した」ことの再確認であり、再確認解除だけで公的な条件が不要と承認されたわけではない。出典や入力が`needs_information`のままでも、本人の確認操作とルール上の未確定は別軸として表示する。

## 4. 再確認を発生させるタイミング

- U04で**保存が成功した条件変更**に対して、旧条件と新条件の差分・タスクの依存を比較。
- **単純な文字の修正**や、タスクに無関係な条件変更で一律に再確認を付けない。
- 会場・参加対象・時期・設備・主催体制・施設カテゴリの変更が以前の確認対象を変えたときに必要なタスクだけ付ける。
- 親タスクが現在`applicability=no`ならランキングから除外。履歴は維持し、再び該当となった際は保存されている進捗と条件の変化から再確認を判定する（自動で完全確認済みに戻さない）。
- 出典台帳の版変更時の再確認は別の「ルール版の差分比較」が必要。**情報更新のたびに全件強制再確認しない**。

## 5. 保存と競合

- U03の操作は自動保存。**操作した瞬間と保存成功を区別**（`dirty` → `saving` → `saved | failed | conflict`）。
- 保存失敗時、まだ画面上にある編集差分と最後の保存済み版を混同しない。再試行または編集内容を破棄する導線。
- 別タブ変更でrevisionが異なると、本人の選択を自動上書き／自動マージしない。最新版を読み込む前に未保存差分が失われ得ることを説明。
- 保存済みイベントの変更は同一eventIdに限定。削除されたイベントIDを古いタブから新規作成し直さない。
- 解除ボタンを押したことだけでrecheck=falseに**保存成功したとは表示しない**。

## 7. 実装前の残る判断

- **正式採用**：`再確認を終えた`の明示操作でだけ解除し、本人のprogress.statusを変えない。[ADR-004](ADR_004_EXPLICIT_RECHECK_CLEAR.md)。**未承認**：対象外確認ダイアログと解除時の二重確認の文言・形式。
- 再確認理由の記録粒度（reasonCodeのみか変更元フィールド情報も持つか）。
- 複数条件変更・複数回の再確認がある場合の理由の付与・重複排除・履歴保持期間。
- 施設固有の公式情報が変わった場合のルール版更新と再確認境界。
- UXの有効性はユーザー検証前であり、法的な可否・安全性の判断機能ではない。

## 8. ADR-004の状態遷移補足（正式採用）

| 旧状態 | 解除保存成功後 | 代表優先への影響 |
|---|---|---|
| completed + needsRecheck=true | completed + false | 原則、未解決候補から外れる |
| not_applicable + needsRecheck=true | not_applicable + false | 本人の対象外判断を維持、根拠ある注意は消さない |
| in_progress + needsRecheck=true | in_progress + false | 進行中は未解決のまま |
| not_started + needsRecheck=true | not_started + false | 未着手は未解決のまま |

再確認解除は保存トランザクション成功後のみ確定。保存失敗・revision競合時に`needsRecheck=false`と永続保存されたと扱わない。現在の理由は空にするが、MVPが全変更履歴を監査保存することは意味しない。
