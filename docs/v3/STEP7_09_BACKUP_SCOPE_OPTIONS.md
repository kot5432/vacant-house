# STEP7-⑨｜ブラウザ保存データのバックアップ範囲の選択

作成：2026-11-15。**利用者判断前の比較資料。** 現行の地域イベント準備支援Webアプリのみ、旧空き家・物件・所有者データは対象外。アプリの認証、クラウド同期、サーバーDBはMVPで不採用。技術：[ADR-001](ADR_001_TECH_STACK_ADOPTED.md)、対応ブラウザ：[ADR-014](ADR_014_MAJOR_DESKTOP_MOBILE_BROWSER_SUPPORT.md)。コード・実行テスト・デプロイはなし。

## 1. なぜ決定が必要か

イベント条件・P01〜P12の進捗を保存する先はIndexedDBであり、**ブラウザのサイトデータ削除、プライベートモード、ストレージ容量・環境の影響で失われる可能性がある**。同じPCでも別ブラウザ・別端末への自動同期はない。利用者にこれを説明するだけか、バックアップ可能にするかでMVPの範囲・データ設計・試験工数が変わる。

## 2. 選択肢

| 案 | MVPに含む機能 | 利点 | 懸念 |
|---|---|---|---|
| **A（推奨）** | **エクスポートとインポートの両方を追加**。本人がローカルJSONでバックアップし、同じ形式のデータを復元可能 | ブラウザ消去や端末交換に対する自己管理の選択肢ができる | インポートのスキーマ移行・重複ID・不正なデータ・ファイル内容・競合・復元時の本人確認に十分な追加設計と試験が必要 |
| B | **エクスポートのみ**。ローカルJSONを書き出せるがMVP内では復元できない | 進捗内容を手元に保存可能。復元の複雑さを先送りできる | 書き出したファイルをアプリに戻せず、利用者が「バックアップ可能」と誤解しやすい |
| C | **バックアップ機能をMVPに入れない**。ローカル保存の限界をU01/ヘルプに明示 | MVPの設計・試験を最小化できる | 利用者がデータを失った場合にアプリ内から復元できない |

**製品価値の観点ではA案を推奨**（進捗の継続利用を中心価値に含むため）。ただしMVPの開発期間とコンテスト提出時期が厳しい場合、C案の方が現実的。技術負担はA＞B＞C。いずれもユーザーの明示承認前に機能として確定しない。

## 3. A案採用時に必要な安全契約（提案）

- JSONは**イベント入力・本人進捗のみ**。利用者の機微情報を追加収集しない。公式出典カタログ自体は静的ビルド同梱のため、バックアップへ複製しない。
- `exportSchemaVersion`と`eventSchemaVersion`を区別。書き出した日時と件数、アプリの版を明記。
- 読込時はファイルサイズとJSONスキーマを検証し、未知の`schemaVersion`を黙って取り込まない。未知taskIdや不正値を修復して元の意味を変えない。
- インポートを既存データへ**自動上書きしない**。重複`eventId`をどう扱うか（新IDで複製／ユーザーに差分を確認／拒否）は別の正式決定。
- 一括データ削除や既存データの置換は本人の意図を明確に確認し、処理失敗で既存イベントを消さない。
- ファイルの中身を外部送信しない。ローカルに個人情報が記入されている可能性を説明。
- 旧空き家アプリのJSONを現行のイベントとして解釈しない。

## 4. 次の確認

**A案：エクスポート＋インポート／B案：エクスポートのみ／C案：機能なし**のいずれをMVPに採用するか。形式と復元に関する厳密な仕様は採用後に段階的に具体化する。ユーザーの保存条件を勝手に変更しない。
