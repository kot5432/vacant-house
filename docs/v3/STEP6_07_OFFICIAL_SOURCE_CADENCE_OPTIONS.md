# STEP6-⑦｜公式情報更新頻度の決定ゲート（2026-11-15）

> **状態：選択肢比較／正式採用前**。技術ADR-001、物理会場なしADR-002、優先順位ADR-003、再確認ADR-004、施設データ削除ADR-005、過去日ADR-006、人数ADR-007、任意メモ上限ADR-008は採用済み。旧空き家案は対象外。実装・公開・公式原資料の最新確認はしていない。

## 1. 更新運用の共通前提（どの案でも守る）

- **初回登録時と各リリース前には原ページを確認**する方針。施設固有の条件を公的出典なしに断定しない。
- 台帳は `sourceId`・URL・対象施設・適用条件・確認日・版・レビュー状態を保持する設計。
- `needs_review/suspended/retired`になった出典に依存する確定的な施設固有説明を止め、一般案内へフォールバック。無関係のタスク・別施設まで一律停止しない。
- 公式情報の改定は本人の`completed/not_applicable`を削除せず、影響する場合だけ`needsRecheck`を付与。本人の解除はADR-004に従う。
- アプリはVite/Reactの静的配信であり、ブラウザが旧版を開いたままなら、**全利用者にリアルタイムで修正が反映される保証はない**。公開前に更新通知・画面再読込の仕組みを別途設計する。
- 確認担当とレビュー担当を分け、ソースの実ページを直接確かめる。**実際の高岡市施設利用条件は本資料ではまだ確認していない**。

## 2. 定期点検の3案

| 案 | 定期点検 | 追加の確認 | 良い点 | 注意 |
|---|---|---|---|---|
| A（推奨） | **月1回** | 初回登録・各リリース前・変更を知った時 | 小さなチームでも定期点検を忘れにくい | 出典数が増えたら負担が増える。古いタブの停止は別問題 |
| B | **3か月に1回** | 同上 | 運用負担が低い | 変化に気づくまでの期間が長くなりやすい |
| C | **各リリース前のみ** | 初回登録・変更を知った時 | 最小負担 | 長期未リリースの場合に古い公式情報が放置される懸念 |

推奨はA。ただし頻度は法的な最低義務ではなく、運営側の品質ポリシー。月1回だけでは公式情報の正確性を保証しない。誤情報を把握した場合は予定日を待たず対象の断定案内を停止する。

## 3. A案を採用した場合の具体的な運用規則（提案）

1. 月1回の点検日を決め、担当者がすべての掲載中`verified`出典の原ページ・URL・対象条件・改定情報・確認日を照合する。
2. 担当者は確認日、変更の有無、問題点、担当をGit管理の台帳に記録する。レビュー担当は変更があれば適用条件・画面表示文を二重確認する。
3. 本番リリース前は定期点検直後でも再度、変更対象を含めた出典の整合を確認する。
4. 変更や誤案内疑いを把握したら`needs_review`、必要に応じて`suspended`にし、根拠不足の断定案内を止めて修正する。月次の次回まで保留しない。
5. 更新が必要なP08等だけルール版／出典版と再確認への影響をレビュー。PRで条件一致・不一致のテストを準備する。
6. Vercel Previewで検証→本番更新。掲載日時、更新版、どの施設に影響するか記録。古いタブへの即時停止保証はないと利用者向け説明を用意する。
7. 出典が廃止されていれば`retired`へ。閲覧できない状態なら検証できるまで`verified`にしない。

## 4. 残る運用上の役割・実装前ゲート

- 点検担当と確認レビュー担当の**具体的なメンバー**はチームで決める。氏名や個人の連絡先を公開台帳へ不用意に記録しない。
- 対象ブラウザ・古いタブへの更新通知、出典をViteビルド同梱とする場合のリリース手順、公開ドメインは公開前の品質ゲート。
- `OFFICIAL_SOURCE_REGISTER.md`に既存の出典を列挙していても、最新の原ページ確認・適用先の同定を完了したと見なさない。
- コンテスト提出までの運用期間と、公開後も継続するかの責任範囲は別の意思決定。

## 5. ユーザーへの次の質問
