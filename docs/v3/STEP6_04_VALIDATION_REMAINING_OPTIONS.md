# STEP6-④｜入力検証の残件・判断ゲート（2026-11-15）

> **比較資料：未承認案を正式決定と混同しない。** 技術ADR-001、物理会場なしADR-002、優先度ADR-003、再確認ADR-004、施設固有入力削除ADR-005は採用済み。実装・試験は未実施。現行地域イベント準備支援のみ、旧空き家案は対象外。

## 1. 最初の確認：過去の開催日・月をどう扱うか

基本Q3「希望時期」は`{kind:date, value:YYYY-MM-DD}`／`{kind:month,value:YYYY-MM}`／`{kind:undecided}`。日時の形式・実在性は必ず検証し、**架空の開催期限、申請期限、日数による自動P1昇格は行わない**。

| | A案（推奨）：注意して許容 | B案：過去日を入力エラー |
|---|---|---|
| 今日以前の年月日 | 形式・実在日が正しいなら保持し、過去であると確認メッセージを出す | 入力エラーにして変更するまでU03へ進めない |
| 既存イベントの再閲覧 | 過去の希望時期でも閲覧・編集可能。期限を保証しない | 元レコードの値は既に存在するため、編集画面を開くたびにブロックするおそれ |
| 参加者の困りごと | 昨日の予定を振り返って次回の類似イベントを考える場合でも利用可能 | 今後に限った計画用途に絞れる |
| 欠点 | 単発開催の準備が「過去」に見えて違和感が出るので説明が必要 | 日付変更したくない利用者が編集不能になりやすい |

**推奨A**：入力では実在日チェックだけを必須とし、過去日・過去月は警告で保持。過去だから「申請期限を過ぎた」等と断定しない。評価の基準日はユーザーのタイムゾーンで扱う必要があるため、仕様化時には固定clock／calendarDateの入力を設ける。過去のイベントの開催完了を自動判断しない。

## 2. 人数・テキスト長の候補（後続確認）

| 項目 | 候補 | 留保 |
|---|---|---|
| 人数 | 1以上の安全整数が最低条件。上限は例えば1,000人等の製品目安にするか、超過警告のみとするか | 「小規模」の明確な人数上限を仮に技術だけで決めない |
| 施設名メモ | 100字程度の候補 | 保存単位・文字数カウント・入力途中の日本語変換を確認 |
| イベント説明 | 500字程度の候補 | 任意自由文の個人情報注意・長文の画面折返しが必要 |
| 数値と入力 | 全角数字・カンマ表記等の正規化方式 | 表示と保存を一致させる |
| 日付の上限 | 極端な遠い未来年を制限するか | 根拠がない制限は設けない |

人数上限・テキストの文字数制限は**未承認**であり、検証スキーマに確定値として組み込まない。

## 3. 公式出典の更新運用は別のゲート

[公式出典の運用計画](OFFICIAL_SOURCES_OPERATIONS_V1.md)でsourceId／適用スコープ／verified・needs_review・suspended・retired／確認日／レビューを提案。**実際の高岡市公式資料の最新内容はこの文書では未検証**。出典の台帳登録時に必ず原ページ・対象施設・確認日を記録。更新頻度と担当はチームと別途決定。

## 4. 追加判断を後回しにできる理由

過去日の扱いを先に決めると基本6問のバリデーションと既存イベント編集の一貫性を確保できる。人数上限や任意テキスト長は、自由入力が未回答でも生成できる設計のため、基本フローの構造は変えない。出典台帳の運用担当はチーム体制の確定後でもよい。
