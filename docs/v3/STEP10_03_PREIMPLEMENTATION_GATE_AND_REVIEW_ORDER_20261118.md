## 2. 技術値の設計提案：採用前のレビューで決めること
- **主催入力**：`optionalDescription`を統一キーとし、旧`eventDescription`は説明ラベルとして扱う案。ADR-018由来4フィールド`importedFrom`の厳密型の確認。
- **主催子項目**：P01〜P12各チェック項目の採用済み名称・IDを照合した版付き表。**未採用IDを今回生成しない**。
- **参加情報の証拠**：各欄は`confirmed/unknown/not_applicable`、募集受付は`confirmed_open/confirmed_closed/unknown`を提案、現在有効かは日付とレビュー状態から導出。
- **募集状態の安全な表示**：一次ページに「受付中」と記載があっても、時間経過したら再確認が必要。人間が点検できない場合は最新の募集断定を停止。
- **地域・分野タグ**：高岡市を初期中心とし、他地域は十分な活動・出典が確認できた時点で段階拡張。話題分類は最小限にして、本人の適性スコアとしない。
- **技術の境界**：参加カタログはアプリに同梱する静的情報、主催入力はIndexedDB/Dexie、バックアップJSON v1の範囲は変えない。

- 地域活動への参加が主催に必ずつながる、地域活性が既に達成された等の効果を結果として書かない。

## 6. GitHubでの完了基準
- 設計Issueの「完了」は**担当以外のレビューを記録し、未決仕様の扱いを決めた場合のみ**。文章の追加だけで閉じない。
- 実装/品質Issueの「完了」は**実行した確認の証拠**がある場合のみ。全件`not_run`では閉じない。
- MVP範囲・正式ADRと開発中の技術案の区別を維持し、旧空き家案は混ぜない。

**現段階でユーザーに追加で大きな機能選択を求める必要はない**。未了項目は順番にチームレビューし、コード実装は別途許可を得る。
