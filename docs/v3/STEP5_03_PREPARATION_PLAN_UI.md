# STEP 5-③｜U03 準備プラン詳細UI仕様 v0.1（2026-11-15）

> 対象：**初めて単発・小規模の非営利地域イベントを主催する人向け準備支援Webアプリ**。空き家物件の登録・マッチング・所有者診断・6用途診断・旧「困りごと入力→相談文コピー」案は対象外。
>
> **画面設計案・机上の期待結果**。コード、利用者テスト、性能測定は未実施。MVPの採用範囲は [STEP4-⑫](STEP4_12_MVP_REQUIREMENTS_V01.md)、画面一覧は [STEP5 v0.1](STEP5_SCREEN_DESIGN_V01.md)、ホームと基本入力は [STEP5-②](STEP5_02_HOME_SETUP_WIREFRAMES.md) を参照。P01-P12と優先度の厳密な計算契約は依然レビュー対象。UI例を根拠にルールを追加確定しない。

## 1. U03の役割と成功条件

- **中心価値**：準備の全体像と、イベント条件・本人が更新した進捗に合った優先順位を理解できる。
- **主要操作**：タスクを開く→具体的な確認事項を理解する→進捗を変更する。入力を詳しくするときはU04へ移動。
- **補助価値**：該当する高岡市の公式情報を出典と確認日付きで案内。実際の許可・予約・法的適合・安全性を判定しない。
- **成功の観察条件**：利用者が「今優先する確認」「理由」「最初の具体行動」「全体の準備項目」を説明できる。実際にそうなるかは未検証。

## 2. 情報階層：スマホ・PC共通の表示順

1. **ヘッダー**：ホームへ／「準備プラン」／保存状態（このブラウザに保存済み・保存中・失敗）。
2. **イベント概要（コンパクト）**：イベント種類、参加対象、希望時期、会場状況。U04への副操作「情報を追加・編集」。名前が無い場合は種類などを仮タイトルにする。
3. **今優先する確認事項**：代表1件の見出し、優先理由、根拠の種類、状況不明な点。代表がP1でも他のP1を隠さず、同階層に「ほかの重要な確認」一覧を置く。
4. **次にできる一歩**：上記代表タスクと対応する具体的行動、必要に応じた確認先の種類。抽象的な「調べましょう」だけで終わらせない。
5. **準備の全体像**：4領域／基本P01-P12。各行はタスク名・優先度・進捗・再確認の有無・詳細展開ボタン。完了／適用外は整理して表示するが閲覧できる。
6. **出典と確認の限界**：該当するタスク詳細内に公式情報（名称・対象・確認日・リンク）。非該当なら一般的な準備提案と明示。画面末尾にブラウザ保存の限界等の案内を置く。

**重要**：代表カードだけが画面の主役になり、全体像が隠される旧案へ戻さない。「プラン生成＝イベント開催可能」とは表示しない。

## 3. 文章ワイヤーフレーム

### モバイル（単一カラム、推奨順）
```text
[← イベント一覧]               [保存状態: このブラウザに保存済み]
準備プラン
[イベント: 体験会 / 子ども / 2027年2月 / 会場未決定] [情報を編集]

今、優先して確認したいこと
[優先度 P2] 会場の条件を整理
理由: 会場未決定のため、規模・設備の条件が他の準備にも関係します。
次にできること: 希望人数や必要設備をまとめ候補施設の条件を確認。
[ほかの重要な確認を表示] ← 該当時・隠さず件数と見出しを示す

準備の全体像（4領域）
 企画・開催条件
  [P01 企画内容を整理 / P3 / 未着手       ▾]
  [P02 参加対象・人数 / P2 / 未着手       ▾]
  [P03 開催時期・費用 / P2 / 未着手       ▾]
 運営体制・安全
  [P04 役割分担 ...]
  [P05 安全・見守り ...]
  [P06 当日の進行 ...]
 会場・設備・手続き
  [P07 会場選定 ...]
  [P08 施設条件 ...]
  [P09 設備 ...]
 募集・開催前
  [P10 募集・告知 ...]
  [P11 参加方法 ...]
  [P12 開催前最終確認 ...]
[完了・適用外の項目を見る（該当時）]
[ブラウザ保存の注意と公式情報の限界]
```

### PC（推奨）
- 本文最大幅を設け、最上部にイベント概要と保存状態。
- 優先理由と次の行動は同じカードまたは連続した近接領域。横2列に離して置かない。
- 4領域はまとまりごとの縦一覧。横2列配置は優先情報を見落とさないことを比較後に採否。
- スマホで横スクロール、カード内の極小文字を発生させない。

## 4. タスク一覧の表示契約

各タスク行の最低情報：
- 安定ID（内部は `P01`〜`P12`; UIでは必要に応じ小さく）、タイトル。
- 優先区分 `P1` / `P2` / `P3`（「今優先」「次に確認」「後で確認」等の言葉も付与）。
- 進捗 `not_started` / `in_progress` / `completed` / `not_applicable` の日本語ラベル。
- `needsRecheck` は**別の表示**。「完了＋再確認が必要」が成立する。
- 展開ボタン。クリック行全体を操作可能とする場合も、進捗コントロールとイベントが競合しないこと。

### 並べ方（画面表示案）
- 全体像は**4領域の順序を固定**し、その中では優先度→安定ID順。ただし全体ランキングを探すためには最上部の優先領域を使う。
- P1が複数なら代表1件＋ほかのP1の見出し／件数を同じ優先領域に明示。折りたたみのみで存在を隠さない。
- P1がない場合はP2、P2もなければP3から代表を選ぶ。順位の算出自体はSTEP4の契約を参照。
- **適用外**（条件による非該当）と**対象外**（利用者の判断）は異なる。条件による非該当は順位計算から除外して、一覧から確認可能にする。
- 進捗率を `4/12完了` 等で表示するのは、分母・再確認・適用外の正式定義まで保留。MVP初期UI案は「完了 n件／再確認 n件」などの個別件数も定義後に採用する。

## 5. 展開されたタスク詳細

表示するもの：
1. タスク名、今の優先度・優先する理由（「あなたの入力」「一般的な準備提案」「公式情報」を区別）。
2. 今できる具体行動（実施する相手・確認事項。未確認事項を推測で埋めない）。
3. 任意のチェック項目：施設利用可否、申込方法など。ただし**チェック項目を全てチェックしても親タスクを自動完了させない**。
4. 前提条件や待機理由。準備できる部分は確認可能とし、タスク全体を強制ロックしない。
5. 該当するときだけ公式根拠カード：対象施設カテゴリ、出典名／URL、確認日、対象範囲、最新条件は管理者に確認する旨。
6. 進捗変更コントロール：ラベル付き4状態の選択。重要確認を対象外にする場合は理由確認を提示し、違法/安全の確定判断をしない。
7. `needsRecheck` がある場合は理由と「再確認を終えた」操作。完了履歴がある場合も現在の条件で確認済みと偽らない。

### 状態変更後のフィードバック
- 表示中の進捗を即時更新してもよいが、**永続保存に成功したと表示するのは保存成功後のみ**。
- 完了→未着手に戻すと再び未完了に出す。ほかのイベントには影響しない。
- 条件変更後は、根拠が消えた施設固有注意を表示に残さない。
- イベント条件が変わるとタスクの適用対象と優先度を再計算するが、過去の完了履歴を黙って破棄しない。

## 6. 代表事項と「すべて完了」の例外

| 状況 | U03の表示 |
| --- | --- |
| 未解決P1が1件 | その項目を代表として見せる |
| 未解決P1が複数 | 代表1件＋残りのP1すべての見出しを見せる |
| P1なし、P2あり | P2を代表として表示する |
| 完了のみ（再確認なし） | 「現在表示されている準備項目は完了扱いです」。イベント開催の許可・安全を保証しない |
| 完了＋要再確認あり | 「以前は完了しましたが、条件変更により再確認が必要です」として未解決に戻して案内 |
| 利用者が重要確認を対象外と指定 | 対象外の理由・注意を表示し、必要な確認まで完了と扱わない |
| 公式根拠が非該当／登録なし | 一般的な確認提案と表示。「公式条件」と誤称しない |
| 保存失敗 | 失敗の説明、再試行、未保存状態を表示。保存済みと誤表示しない |
| 復元・データ移行エラー | 破損した内容を自動初期化せず、別の画面で安全な復旧導線へ |

## 7. 保存と操作の設計

- 保存状態はヘッダーと操作直後のフィードバックなど見つけやすい位置。表示語は「変更あり／保存中／このブラウザに保存済み／保存できませんでした」。
- 読み込み済みイベントの進捗変更はイベントIDごとに保存。競合するタブがある場合、revision照合で無条件の上書きを止める。
- 保存失敗でも画面上の未保存データをできるだけ保持する。別ページ遷移前に失敗を説明し、「再試行」「この画面に戻る」等を選べるようにする。
- データがブラウザ削除・端末交換で失われる可能性を明示。サーバー保存・アカウント・エクスポート/インポート・印刷PDFは初期MVP外。
- 保存成功後でも、ブラウザの将来の削除や端末故障からの復元保証ではない。

## 8. UI文言のルール

良い例：
- 「会場が未決定なので、利用条件を先に確認すると次の準備が進めやすくなります」
- 「この施設カテゴリに該当する公式案内です。個別の利用可否は施設へ確認してください」
- 「参加対象がまだ決まっていないため、見守りが必要か確認してください」
- 「このブラウザに保存しました」

避ける例：
- 「あなたの準備は危険です」「この会場は必ず使えます」「申請期限はあと7日」（根拠なし）
- 「未回答なので準備していません」「未成年が参加するので主催者も未成年です」
- 「クラウドにバックアップしました」（サーバー保存なし）
- 「タスクは全て完了、開催して問題ありません」

## 9. レスポンシブ／アクセシビリティ

- 320px幅でも左右スクロールを生まない。タスク見出しの折り返し・長い施設名・URLに対応。
- 文字200%でも見出し・ボタン・状態の重なりがない。
- タスク展開はボタンとして操作でき、`aria-expanded`、対象領域、明確なフォーカス順を持つ（実装時に確定）。
- 進捗変更、保存失敗、再確認、優先度は色だけで判定させず、文字と適切な通知を用いる。
- 出典リンクは意味の分かる名称にし、移動先が外部であることを伝える。
- 追加の操作後、画面上部へ勝手にジャンプせず、可能な限り作業位置・展開状態を維持する。

## 12. 再確認解除の正式採用（2026-11-15）

[ADR-004](ADR_004_EXPLICIT_RECHECK_CLEAR.md)により、`needsRecheck=true`は利用者がタスク詳細で**「再確認を終えた」**を明示操作し、IndexedDB保存に成功したときだけ解除する。以前の進捗を自動変更しない。単なるタスク展開、子チェック操作、編集画面から戻るだけでは解除しない。保存失敗・競合時は解除済みと誤表示しない。詳細UIは[STEP6-①](STEP6_01_PROGRESS_RECHECK_SPEC.md)。対象外確認ダイアログの細部は未承認。

## 13. 公式情報の点検期限切れ時の画面（ADR-010正式採用）

高岡市の対象施設であっても、月次点検期限を過ぎた公式出典の確認・必要なレビューが完了していない場合、**施設固有の断定文を見せず**、次のように一般確認へ切り替える。「この施設の利用条件は現在再確認中です。最新情報は施設管理者の公式案内でご確認ください。」確認先リンク自体が無効／危険な場合はリンクを出さない。P01〜P12の一般的な準備プランは維持する。

UIでは`出典の再確認中`とタスクの`再確認が必要`を**別の見出し・表示**にし、本人の完了や対象外ステータスを変更しない。期限内かどうかの判定は表示時に出典メタデータと評価日を照合する方式を技術レビューで検討し、静的配信の古いタブに即時の停止ができると宣言しない。月内点検日の算定と更新通知は未承認。決定正本：[ADR-010](ADR_010_STALE_SOURCE_FAIL_CLOSED.md)。

## 14. 月末の公式情報点検期限を越えた場合（ADR-011）

U03の施設固有の案内は、**JST各月末日までの点検・レビュー**を前提にする。未完了のまま翌月1日00:00 JSTになれば、その施設の具体的な利用条件の断定文を出さず、「この施設の利用条件は現在再確認中です。最新情報は施設管理者の公式案内でご確認ください」と表示。リンク自体の有効性・安全性に疑義がある場合はリンクを無条件に提示しない。**一般的なP01〜P12のタスクと本人の完了状態は維持**。対象施設が変わったらその出典の説明を流用しない。日時は端末の地域設定ではなく公式出典管理のJST基準として扱う。ただし古いタブ・端末時計ずれで即時停止を保証できないという注意を公開前に検証する。[ADR-011](ADR_011_MONTH_END_SOURCE_REVIEW_DEADLINE.md)。
