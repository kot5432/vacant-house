# STEP7-⑪｜JSONバックアップの技術・安全境界レビュー

作成：2026-11-15。**仕様草案・実装前**。MVPにローカルJSONエクスポート＋インポートを含める判断は[ADR-015](ADR_015_JSON_BACKUP_EXPORT_IMPORT.md)で正式採用。ID衝突時の具体的な挙動は[STEP7-⑩](STEP7_10_BACKUP_IMPORT_CONFLICT_OPTIONS.md)でユーザー承認待ち。旧空き家関連のスキーマ・データは一切引き継がない。

## データと互換性（案）
- JSONの最上位識別子`formatId`には地域イベント準備支援専用の値を採用し、未知値・旧プロダクトの識別子を拒否。
- `exportSchemaVersion`はバックアップ形式、`eventSchemaVersion`はイベント保存形式。`rulesVersion`、`catalogVersion`、`buildId`は別の版であり、**同一視しない**。
- イベントの基本6問・条件付き入力・本人進捗・再確認理由・任意メモをバックアップ可能な値として保持する。共通タスクカタログ、施設固有の公式文面、導出優先度は出力しない。
- 古い既知版の取込みは**型と意味が変わらないことを確認した対応版のみ**許可する。未知の版は拒否。想定外のフィールドを勝手に削除して成功扱いしない。
- ファイル内のイベントID一意性、重複taskId、無効日付・人数・長文・enum、`needsRecheck`と理由コードの整合性を解析段階でチェック。
- ファイルが極端に大きい場合のメモリ負荷・JSONパース停止・ブラウザクラッシュ対策として**サイズ／件数／フィールド長の技術上限**を設計する。数値は実測前・未決。
- 復元成功は**永続化したイベントの確認後だけ**表示し、ファイル選択やプレビュー完了を復元完了と混同しない。
- 原則としてバックアップに「作成元のビルドが以前にverifiedと判断した出典状態」は含めない。復元先の現在同梱カタログとJST期限で再評価。

## 書き出しフローの失敗境界
1. U03の保存処理とU04ドラフトを区別し、永続化済みデータだけを読取トランザクションでスナップショット化。
2. ファイル生成時、件数と内容の整合性を検証。ファイルへの書き込み・ダウンロード起動はブラウザ依存。
3. 「書き出し用ファイルを作成しました」と「端末へ確実に保存・保持されました」を区別する。
4. スマホとPCのファイル選択／保存UIは主要ブラウザで実機試験が必要。

## インポートとデータ保護
1. ユーザーがファイルを選ぶ→サイズを検証→内容をメモリで解析→formatId/版・必須入力/進捗を確認→重複と衝突をプレビュー。
2. **ユーザーの明示操作までDBを一切変更しない**。
3. コミット前には最新DBとファイルの対象IDを再評価。衝突方針に従い操作対象のIDを確定する。旧タブで一度削除したイベントを暗黙復活させない。
4. **一括復元を全件成功／全件失敗のトランザクションで扱うことを第一候補**とし、途中で容量不足や競合が起きた場合に部分保存を成功と偽らない。最終の原子性仕様は衝突方針とともに確認する。
5. 同一バックアップの繰返しインポートは同一IDで検知できるが、複製案採用後はIDが変化するため、内容重複やファイル識別の追加の警告が必要。
6. バックアップには個人名等を自由記述に記録した可能性がある。**アプリが外部サービスへ送信しない**ことと、ファイルの紛失・共有には注意が必要なことをU01で説明。
7. 復元後のU03で、以前の完了・対象外と再確認状態を保持する一方、新しいルールや出典の影響がある場合は適用条件・再確認理由を再評価。古いファイルを「現在の行政上の確認完了」の保証としない。

## セキュリティ・品質検証（実行前）
| ID | 入力・状況 | 期待 |
|---|---|---|
| SAFE-01 | HTMLやスクリプト文字列がメモに含まれる | 表示はテキスト、実行しない |
| SAFE-02 | 異常なネスト・巨大ファイル | 解析の制限とエラーでDB無変更 |
| SAFE-03 | 古い既知のexportSchemaVersion | 対応可能な版だけ無損失移行 |
| SAFE-04 | 未知の版と未知のプロダクトID | 取込み拒否 |
| SAFE-05 | U04編集中に別タブで復元 | revisionを再照合し旧ドラフトで上書きさせない |
| SAFE-06 | 保存容量不足 | 全件成功と誤表示しない |
| SAFE-07 | 既存イベントとバックアップに同じeventId | 事前プレビューと承認済みの衝突解決 |
| SAFE-08 | 現行タスクP01〜P12以外の状態 | 黙って削除・変換しない |
| SAFE-09 | モバイルのファイルアクセス拒否・キャンセル | 旧DB維持、エラー説明 |
| SAFE-10 | 旧空き家時代のJSON | 現行イベントとして復元しない |

**次に利用者が選ぶべき論点**：重複`eventId`の解消方法（STEP7-⑩）。それ以外の安全要件は、既存の保存保護原則からの設計提案として具体化した。コードやファイル形式の実装は行っていない。
## ADR-016採用による更新（2026-11-15）

**既存DBとのeventId衝突は別IDで複製追加するA案を正式採用**。ファイル内で同じeventIdが複数ある場合はインポート全体を拒否。本人のプレビュー確認後に**全件成功／全件失敗のDexie一括トランザクション**として追加し、既存イベントへ書込みを行わない。プレビュー後の別タブ変更により衝突分類・コピー件数が変わるときは中断・再プレビュー・再承認。複製の進捗・needsRecheckは本人の元記録を維持するが、公式出典と優先順位は復元先ビルドで再評価。コピーのeventIdとrevisionは独立、初期revisionの厳密な値・タイムスタンプ・繰返しインポート時の警告水準は別途レビュー。[ADR-016](ADR_016_IMPORT_COLLISION_AS_COPY.md)。
