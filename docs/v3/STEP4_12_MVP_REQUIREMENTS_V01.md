# STEP 4-⑫｜MVP保存範囲と要件定義 v0.1（2026-11-14）

> **現行製品のみ：** 初めて単発・小規模の非営利地域イベントを主催する個人・小規模チーム向け準備支援Webアプリ。富山県、高岡市の確認済み公式情報を初期対象とする。空き家所有者診断・物件マッチング・営利開業支援は対象外。リポジトリ名 `vacant-house` は旧名称であり現行スコープを示さない。
>
> 本書は要件定義の**初版（v0.1）**。開発、実行テスト、利用者検証は未実施。確定したMVP方針と、実装前に要検証の詳細設計を区別する。

## 1. 決定事項と旧決定の更新

- **STEP3基本入力：** 基本6問→暫定プラン→任意の詳細化。採用済み入力選択肢は [STEP3](STEP3_MVP_BOUNDARY.md) を参照。
- **STEP4-⑥：** プラン生成後にタスク進捗を更新、優先度を再計算するB案。
- **STEP4-⑨：** ログイン不要・ブラウザ内保存・同一ブラウザで後日再開するB案を採用。
- **STEP4-⑫：** 以前の推奨案を採用し、**複数イベントの保存・一覧・選択・個別削除をMVPに含める**。最初は「新規作成」を主導線にする。アプリ独自の固定件数上限なし（ブラウザ容量制限は存在）。
- **持ち帰りの扱いを改訂：** ブラウザ内に保存して後日開くことをMVPでの持ち帰り手段とする。印刷/PDF、ファイルエクスポート/インポートは初期MVP外、将来候補。ブラウザ内保存はバックアップではないと明示する。
- **対象外：** アカウント、サーバー保存、端末間同期、共同編集、参加者個人情報の登録、実際の予約・申請、空き家関連機能。
- **旧STEP3-①との差分：** 旧記述の「継続的な進捗管理なし」は、後続のSTEP4-⑥・⑨・⑫によって**現行MVPでは更新された**。ただし初回の「短い入力からプランを得る」体験は維持する。古い説明を現行仕様として採用しない。

## 2. 画面の責務（方向性として採用、細かいUIはSTEP5で決定）

| 画面 | 役割 | 備考 |
| --- | --- | --- |
| Home | 新規イベント・保存済みイベント一覧・再開・個別削除 | 初めての利用では新規作成を優先 |
| Event Setup | 基本6問を入力して暫定プランを生成 | 必要な条件付き質問のみ追加 |
| Preparation Plan | 優先事項、理由、次の一歩、4領域P01-P12、進捗編集、タスク詳細 | 全体像を隠さない |
| Event Edit | 任意詳細化とイベント情報の編集、再計算 | 進捗の自動初期化はしない |

タスク詳細はPreparation Plan内で展開する案を優先。独立画面化・保存位置・エラー表示の詳細はSTEP5で比較・確定する。

## 3. 機能要件（採用範囲）

| ID | MVP要件 |
| --- | --- |
| FR-01 | 基本6問を入力・編集できる |
| FR-02 | 条件付き入力と任意の詳細情報を入力できる |
| FR-03 | 条件に応じた準備プランを決定的なルールで生成できる |
| FR-04 | 4領域・基本P01-P12の準備全体像、優先順位、未確認事項を表示できる |
| FR-05 | 優先する理由、実行可能な次の行動、該当時の出典付き公式情報を表示できる |
| FR-06 | タスクの進捗4状態と再確認フラグを区別できる |
| FR-07 | 入力／進捗の変更後、関連項目と優先順位を再計算できる |
| FR-08 | イベント入力・進捗・再確認の状態をブラウザ内に自動保存できる |
| FR-09 | 同一ブラウザで複数の保存済みイベントを再開できる |
| FR-10 | イベント一覧で新規作成・選択・個別削除ができる |
| FR-11 | 保存中・保存成功・保存失敗を区別し、失敗時にデータが保存済みだと誤表示しない |
| FR-12 | 破損／未対応スキーマ／移行失敗／複数タブ競合で黙って上書きしない |
| FR-13 | ブラウザ保存の限界、出典の適用範囲、予約・許可・安全性を保証しないことを説明する |

初期MVP外：PDF/印刷、JSONなどのファイル出力と復元、アカウント、クラウド、共同編集、参加者管理。

## 4. データの責務と基本条件

- イベント入力、共通タスク定義、イベント別進捗、生成結果を分離。生成結果は原則再計算する。
- `eventId` を安定IDとして複数イベントを隔離する。タスクは `P01`〜`P12` の安定ID。
- 未回答／利用者が明示した未定／タスク未着手／対象外を別の値として扱う。
- `schemaVersion` と `rulesVersion` を分離し、古い形式の移行で利用者の入力・進捗を保持する。
- 保存の成功が確認される前に「保存済み」としない。ブラウザ保存のデータ消失リスクを明示する。
- 削除は対象イベントIDに限定し、他イベントや共通の定義を消さない。失敗時に成功表示しない。
- 複数タブの競合検出・更新番号による排他、移行時の失敗復旧方法は実装技術決定後に詳細化する。
- 参加者氏名・住所・連絡先、GPS、アカウントは収集しない。施設名メモ・自由記述にも個人情報を入れない案内を付ける。

## 5. 非機能要件（要測定・要検証）

- NFR-01：通常条件でプラン再計算1秒以内を初期目標とする。測定環境は未確定。
- NFR-02：自動保存の成功・失敗・競合を明確に表示する。
- NFR-03：保存・移行・削除の整合性を守り、失敗時に元のデータを勝手に破棄しない。
- NFR-04：キーボードで主要操作可能、文字拡大・状態の文字表示、スマホ・PCに対応。
- NFR-05：タスクルール・データ保存・UIの責務分離と回帰テストを可能にする。
- NFR-06：公式情報の対象・出典・確認日を追跡。期限や可否を推測で生成しない。
- NFR-07：対応ブラウザ・版・端末を技術選定で決め、再開・削除・容量制限を試験する。

## 6. 受け入れテスト（将来の実行条件）

| ID | 入力・操作 | 期待結果 |
| --- | --- | --- |
| AT-01 | 基本6問を回答 | 暫定プランと理由を表示する |
| AT-02 | 同条件・同進捗・同ルール版で再計算 | 同一の結果 |
| AT-03 | 未回答／未定／未着手を混在させる | 別々の意味で表示し誤推定しない |
| AT-04 | 2件目を新規作成し進捗を変更 | 1件目には影響しない |
| AT-05 | 進捗を完了に変更 | 未完了一覧から外れ残りを再評価 |
| AT-06 | 完了後に会場を変更 | 関連タスクに再確認、履歴は保持 |
| AT-07 | 保存後にリロード・後日再開 | 入力・進捗が復元される |
| AT-08 | イベントAだけ削除 | Bは維持され、Aだけ消える |
| AT-09 | 保存失敗を起こす | 「保存済み」と誤表示しない |
| AT-10 | 破損・未対応スキーマ・移行失敗 | 自動初期化や無言の上書きをしない |
| AT-11 | 同じイベントを複数タブで編集 | 古い版が無条件に上書きしない |
| AT-12 | 対象外の施設カテゴリ／開催地域を選択 | 他施設固有の注意を表示しない |

**テストは未実行**。この表は実装後の合格条件。

## 7. 要件定義を完了するまでの残件

1. P01〜P12の表示条件・優先度・依存関係・チェック項目を単一の判定契約へ統合する。14日前ルールは設計仮説であり、行政締切と混同しない。
2. STEP5：画面遷移、保存状態、空状態、再確認、失敗時のUI、キーボード導線。
3. 入力データの厳密な型／バリデーションと、作成中データをいつ保存するか。
4. 保存技術（IndexedDB等）、移行、複数タブ排他、データの復元不能時の導線。
5. 公式情報の更新責任・確認日の管理と、古い情報の非表示ルール。
6. 対応ブラウザ／端末、性能測定条件、バックアップ機能を将来入れる判断基準。
7. 技術選定書→データ・アーキテクチャ・テスト・開発運用設計書。
