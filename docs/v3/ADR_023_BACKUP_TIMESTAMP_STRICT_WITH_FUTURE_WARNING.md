# ADR-023｜JSON復元時の不正な元保存日時は拒否・有効な未来日時は警告付きで許可（A案正式採用）

決定日：2026-11-15。ユーザーが[STEP7-⑲](STEP7_19_IMPORTED_TIMESTAMP_VALIDATION_OPTIONS.md)の**A案**を明示採用。**現行の地域イベント準備支援Webアプリのみ**対象。旧空き家所有者・物件・マッチングのデータを取り込まない。**設計書のみ更新、実装・実行テスト・デプロイなし。**

## 1. 正式決定

1. バックアップの元イベント保存メタデータ`createdAt`・`updatedAt`の**日時文字列が不正、存在しない暦日、比較可能な時刻を特定できない、または`updatedAt < createdAt`であればファイル全体のインポートを拒否**する。正常なイベントだけを選んで部分復元しない。
2. 日時が形式・暦・順序の検証を通り、**復元時の基準時刻より未来である場合は警告と本人の明示確認を経て復元候補にできる**。端末時計のずれの可能性は伝えるが、自動補正・日時書換えは行わない。
3. 正しいタイムゾーン付きISO 8601の時刻を比較し、**表記オフセットが異なっても同一の瞬間なら等しい**。オフセット・タイムゾーンがなく一意の時点を特定できない文字列は未対応形式として扱い、既知旧形式の明示移行手順が検証済みの場合だけ別ルートを許す。夏時間や存在しないローカル日時を推測しない。
4. `exportedAt`など**バックアップ自体の必須日時メタデータが不正なら拒否**する。有効な未来`exportedAt`についても元イベント日時とは区別した警告対象とする設計。実際のファイルが未来に作られたと断定しない。
5. 元の日時は[ADR-018](ADR_018_RESTORED_EVENT_REVISION_AND_PROVENANCE.md)どおり`importedFrom.originalCreatedAt`・`originalUpdatedAt`に**同じ瞬間を保持**。新規復元レコードは`revision=1`、`createdAt=updatedAt=importedAt`（今回の復元確定時刻）。**既存レコードの日時・revision・進捗は変更しない**。
6. **イベント開催予定日Q3の過去・未来は本決定の対象外**。[ADR-006](ADR_006_ALLOW_PAST_SCHEDULE.md)の有効な過去日／月を警告付きで保存可能とする仕様は維持する。
7. 警告付き復元であっても[ADR-022](ADR_022_BACKUP_KNOWN_VERSION_COMPATIBILITY.md)の既知対応スキーマ検証、[ADR-019](ADR_019_JSON_BACKUP_LIMIT_2MIB_100_EVENTS.md)の2 MiB・100件、[ADR-016](ADR_016_IMPORT_COLLISION_AS_COPY.md)の既存ID衝突時別コピーと**全件成功／全件失敗**を免除しない。

## 2. インポート時の検証順序

```text
ファイル選択
→ 実バイト長<=2,097,152確認
→ 現行製品formatId、exportSchemaVersion、eventSchemaVersion確認
→ 既知旧版の場合は厳密検証→安全な移行→現行形式で再検証
→ 必須日時・暦・タイムゾーン・前後関係・入力/進捗/ID一意性の全件検証
→ イベント件数<=100確認
→ 現在の復元基準時刻との比較
   ├─ 不正/矛盾 → 全件拒否（DB無変更）
   ├─ 有効な未来日時 → 対象件数とイベントを注意表示
   └─ その他 → 通常の復元プレビュー
→ 元データ・追加件数・別コピー件数・未来警告の確認
→ 本人が明示確定
→ コミット直前のスキーマ/ID衝突/警告条件を再確認
→ Dexieの全件原子的追加。成功した場合だけ「復元完了」
```

**注意**：現在時刻には端末時計のずれがあり得る。「未来」判定を絶対的な公的事実・データ破損の根拠にはしない。プレビュー中の経過時間やタブ復帰で警告対象が変わったら、確定前に再評価する。どの時計APIと日時ライブラリを採用するかは実装前技術検討。

## 3. U01エラー／注意表示

- 日時不正：「バックアップに正しく読み取れない保存日時があります。データを変更せず復元を中止しました。元のファイルは保管してください。」
- 作成更新順序矛盾：「保存日時の順序に矛盾があります。内容を自動修正しないため、このファイルは復元できません。」
- 有効な未来日時：「バックアップ内の保存日時が、この端末の現在日時より未来になっているイベントが**X件**あります。端末時計やファイル内容をご確認ください。**元の日時を変更せず**復元しますか？」
- バックアップ自体の未来`exportedAt`：「ファイルに記録された書き出し日時が、現在より未来です。端末時計とファイル内容をご確認ください。」
- 警告でキャンセル／閉じた場合：既存DB無変更。形式エラー・未来警告・既存ID衝突は**別の理由**として提示し、色だけに依存しない。
- 未来日時の明示確認は、単なるファイル選択や一般復元プレビューの表示だけでは満たされない。確認した対象・件数を保存直前に検証する。

## 4. 受入テスト（期待値設計のみ／実行なし）

| TIME-A07 | 有効な未来`exportedAt` | 別途警告し、本人が内容を確認 |

## 5. 決定と未決の境界

**正式採用**：不正暦日・構文・必須の保存日時前後矛盾はファイル全体の取込み拒否。正当な未来の日時は警告と本人の明示確認により復元可能。元日時の黙った補正・欠損は不可。

**技術残件**：厳密な時刻フォーマットの正規表現・日時API、端末時計の異常検知・時計差による未来警告の更新タイミング、JSONの初期版番号と旧形式の実際の移行試験、巨大Unicode書記素の技術上限。

**次の利用者判断**：[STEP7-⑳ 書記素制限とは別の入力サイズ安全上限](STEP7_20_TEXT_BYTE_SAFETY_LIMIT_OPTIONS.md)を比較する。
