# ADR-005｜条件外になった施設固有入力の確定時削除（B案正式採用）

決定日：2026-11-15。**ユーザーが明示採用済み。設計のみ／コード・試験・Vercel公開なし。** 現行の単発・小規模の地域イベント主催者向け準備支援Webアプリの仕様。旧空き家・所有者・物件・マッチングのデータは対象外。

## 1. 決定

**U04で基本6問・施設条件を編集している間は保存済みイベントに一切触れない。** 「変更を反映する」で入力検証・該当性評価・旧施設固有入力のクリア・進捗の再確認・revision照合を行い、**同一のIndexedDB readwriteトランザクションが成功した場合のみ確定**する。キャンセル／バリデーション失敗／保存失敗／他タブ競合時は保存済みの旧入力を変更しない。成功後に元の施設を再度選んでも以前の値を自動復活しない。

## 2. 施設固有データの取り扱いマトリクス

以下は「現在の入力条件で該当しない施設固有の回答」のクリア範囲を明確にするための**実装用設計**。項目名は[データ設計](DATA_DESIGN_V1.md)に合わせる。

| 最新の確定予定条件 | venueCategory | facilityUsersAge | venueNameMemo |
|---|---|---|---|
| 地域が高岡市ではない | `unanswered`に正規化 | `unanswered` | **その施設を指すメモなら削除**。現行の施設名メモは施設固有欄なのでMVPでは空欄へ |
| venueStatus=undecided 又は no_physical_venue | `unanswered` | `unanswered` | 空欄へ |
| 地域=高岡市、venueStatus=candidate/confirmed、venueCategory=other 又は undecided/unanswered | `other`等の本人選択を保持 | **センター利用者構成は`unanswered`** | 現在の候補施設名のメモなら保持。**旧センター名と新しい候補名を区別する入力更新は本人が行う** |
| 地域=高岡市、会場候補又は決定、venueCategory=takaoka_community_center（本人明示） | 保持 | 本人の回答または未回答を保持 | 本人が現在の候補として入力したメモを保持 |

**実装上の注意**：施設名メモが「何という施設のメモか」を持たない現行スキーマでは、同じ`region=takaoka`＋`venueStatus=candidate`のまま候補施設AからBへ変更したかを自動検出できない。**ユーザーが同じ欄を書き換えた場合のみ新しい内容として保存**し、Aの名前からBの名前を勝手に推測しない。この限界と、「候補施設が変わった場合は施設名も更新してください」というUI説明を実装前に設ける。必要なら別の識別子を次版で追加する。これは既存の6問を増やす決定ではない。

## 3. 3つの値を別に扱う

1. **入力**：`venueCategory`や`facilityUsersAge`等の該当しない旧値はクリア。
2. **進捗**：`progressByTask[P07/P08/P09].status`、`checkedItemIds`、他タスクの進捗は黙って消さない。条件変更で以前の完了・本人対象外判断が失効するとき`needsRecheck=true`を設定。
3. **生成結果**：該当条件が外れた高岡市施設固有の出典・判定・子チェック項目は**現在のプランから除外**。P07〜P09の親タスクはADR-002に従い一般確認が残る場合がある。

子項目の適用外表示と、保存済みの`checkedItemIds`が残ることは矛盾しない。再び適用されてもチェック済み＝現在条件での確認済みと自動みなさず、必要な再確認を表示する。

## 4. 保存フロー

```text
U04ドラフト変更
  → 基本6問・任意回答を検証
  → 現在条件から施設項目の有効範囲を判定
  → 不適用の施設入力をドラフト上でクリア（確定版はまだ無変更）
  → 旧入力との差分と再確認理由コードを算出
  → eventIdが存在しrevisionが一致することをDexieトランザクションで検証
  → input + progressByTask + rulesVersion + revisionを一括保存
  → 成功ならU03へ。失敗ならU04ドラフトと保存済み旧版を別に保持
```

「確定したらクリア」はボタン押下を意味せず、**DBコミット成功**を意味する。競合時に最新版へ古いドラフトを自動マージ／上書きしない。

## 5. 公式根拠・安全性の境界

`region=takaoka`だけで地域交流センターの条件を適用しない。`venueCategory`を本人が明示選択し、該当する施設条件・出典の対象が一致した場合のみ表示。施設名メモから施設カテゴリを推測しない。許可取得・安全性・法令適合をアプリで保証しない。

## 6. 検証観点（未実行）

- CLEAR-01：高岡市センター→他地域→反映成功：3施設固有値クリア。旧P08完了履歴保持、必要なら要再確認。
- CLEAR-02：上記をU04でキャンセル：旧イベントの施設入力、revision、進捗は完全維持。
- CLEAR-03：上記の保存失敗：旧イベントを維持しドラフトを再試行。
- CLEAR-04：revision競合：古い情報を上書きせず、削除済みID復活もない。
- CLEAR-05：会場候補→物理会場なし：施設固有値クリア、P07〜P09親は一般確認として残す。
- CLEAR-06：同じイベントでセンター→otherカテゴリ：facilityUsersAgeをクリア。現在の施設のメモは本人の入力として維持できる。
- CLEAR-07：再び高岡市センターを選択：以前の施設固有値を自動復元しない。本人に再入力してもらう。
- CLEAR-08：他のイベントB：入力・progress・revisionに一切影響しない。
- CLEAR-09：施設固有子チェックだけ非該当：親P08は勝手に完了・手動対象外にならない。
- CLEAR-10：未知schema/破損レコード：旧内容を黙ってクリアせず読み込みを中断。

## 7. 決定範囲

**確定**：非該当となった施設固有データはU04の確定保存成功時のみ削除。元の施設へ戻しても復活しない。他のイベントとタスク進捗は維持。現行ルールへ古い施設根拠を適用しない。

**次の未決**：年月日が過去の場合の入力許容、参加人数の上限、施設名メモ・イベント説明の文字数上限、公式出典の期限切れ運用細則。細かな確認文言と施設候補変更の識別方法も別途設計レビュー対象。
