# ADR-016｜復元時の既存eventId衝突は別IDで複製追加（A案正式採用）

決定日：2026-11-15。**ユーザーがA案を明示採用**。本決定の対象は現行の「初めて単発・小規模の地域イベントを主催する人の準備支援」Webアプリのみ。旧空き家・所有者・物件・マッチングデータは取り込まない。**設計のみ。アプリ実装・ブラウザ試験・公開は未実施。**

関連：[ADR-015](ADR_015_JSON_BACKUP_EXPORT_IMPORT.md)、[保存データ設計](DATA_DESIGN_V1.md)、[STEP7-⑩比較](STEP7_10_BACKUP_IMPORT_CONFLICT_OPTIONS.md)。

## 1. 正式な利用者向け動作

- インポートJSON内のeventIdが**既存IndexedDBのeventIdと衝突**した場合、**バックアップ側を一意な新eventIdの別イベントとして追加**する。既存イベントの本文・進捗・revision・日付は変更しない。
- 衝突なしのイベントはバックアップ内のeventIdを**可能な範囲で維持**して追加する。確定保存前の再照合で新規衝突した場合、古いプレビューのまま処理を進めない。
- **同一ファイル内でeventIdが重複していた場合はファイル不整合としてインポート全体を拒否**する。単なる既存DBとの衝突と区別する。
- ファイル選択→全件検証→追加件数・新IDで複製される件数・既存件数をプレビュー→**本人の明示確定**→原子的保存成功後にのみ「復元しました」と表示。
- 同じファイルを再インポートすると、衝突イベントは新たなコピーになり得る。**追加の重複が発生することを本人へ明記**し、本人の明示操作なしに繰返し作成しない。内容一致の自動判定・自動スキップの可否は別途決定する。
- **一括復元は全件成功または全件失敗**とする。容量不足・schemaVersion不一致・別タブ変更・途中でのエラーは、既存イベントの更新・削除や復元対象の部分追加を行わない。ファイルの「書き出し」成功とインポート後のIndexedDBコミット成功を混同しない。

## 2. ID・revision・日時・進捗の保存仕様

| フィールド | 衝突なしの取込み | 衝突あり：別コピー |
|---|---|---|
| eventId | 入力ファイルのIDを保持 | コミット時の現DBと照合し**新しい一意ID**を発行 |
| revision | 復元先の新しいレコードとして初期revision（推奨 **1**） | **初期revision（推奨1）**。バックアップ元のrevisionを現在DBの同一eventIdの履歴と扱わない |
| input | 検証済みの入力を保持 | 同じ入力を複製 |
| progressByTask | 本人のタスク状態と再確認を保持 | **同じ進捗・再確認理由を保持**。既存イベントの進捗と混ぜない |
| createdAt / updatedAt | バックアップの元日時はファイル情報として維持するか要設計 | 新イベントの作成日時は復元時の時刻を使う案。元日時の保持方式は要詳細化 |
| rulesVersion・出典版 | 復元先の現行ルール・出典で再評価 | 同左。過去の行政条件を復元して「許可済み」と扱わない |

**一意ID生成は推測可能な連番や元IDの単純な接尾辞ではなく、十分な衝突耐性を持つID生成器を検討**する。ID生成API・revision初期値・元日時メタデータの厳密なスキーマは技術設計細則で凍結し、未承認値を既決と偽らない。

複製イベントは**元イベントと別のeventId**なので、その後の編集・進捗・削除・再確認は独立する。複製であることは復元結果とU01一覧で利用者に分かるようにする（ラベル文案はUI設計で調整）。

## 3. 復元の原子的コミット契約

1. ファイルをメモリ上でサイズ・formatId・版・全イベントの入力と進捗・ID一意性まで検証。**DBへまだ一切書かない**。
2. 読み取り専用のプレビューで、衝突なし件数、別コピー作成件数、ファイル内重複の有無、既存DBを維持する旨を表示する。異常があるなら復元へ進ませない。
3. 本人の確定後、**同一Dexie readwriteトランザクション内で**最新のイベントID集合・保存対象の競合・データ版を再チェックし、新IDの衝突を再確認して一括で新規追加する。
4. プレビュー後に別タブが新しいイベントを作ったなど、**件数や処理分類が変わる衝突**が判明したらトランザクションを中断し、プレビューを更新して**本人の再承認**を求める。保存途中で勝手に別コピー数を変えない。
5. 全イベントの新規追加と更新成功が確認された場合のみ復元成功。失敗時はトランザクションをロールバックし、既存の保存済みイベント・別タブで更新されたイベント・本人のU04ドラフトを変更しない。
6. 並行した別タブ更新は`revision`やDBの現在状態と照合する。**削除されたイベントを復元処理の副作用として黙って復活させない**。ただし、本人がバックアップに含むイベントを「新規として復元する」と明示確定する操作は、削除済みIDを以前の同一レコードとして復活させる処理と区別する。

※ ブラウザのIndexedDBでの厳密な競合防止・DexieトランザクションAPIの選定は**実装前の技術レビューと実機試験の対象**。保存成功前の画面だけで保証したとは扱わない。

## 4. U01のUI・エラー

- プレビュー例：「ファイル内：3件／新しく追加：3件（うち既存IDと重複するため別コピー：1件）／既存イベント：4件（変更なし）」。
- 補足：「別コピーとして復元するイベントは、もとのイベントとは別に編集・削除できます。もう一度同じバックアップを読み込むと、コピーが増える場合があります。」
- ボタンは「3件を復元」等。ファイルの選択だけで保存は開始しない。
- プレビュー後にDBが変更された場合は「保存内容がほかのタブで変更されました。復元内容を再確認してください」とし、更新後のプレビューから再承認。
- エラー・キャンセル・容量不足・非対応版の場合は**元データに副作用を出さない**。UIが「3件復元済み」と誤認させない。

## 6. 未決事項

**正式採用済み**：衝突時に別IDでコピー追加、既存イベント保護、インポート内ID重複の拒否、本人確認、全件成功か全件失敗、プレビューから変更された衝突の再承認。

**次の確認候補**：同一バックアップを繰り返し取り込む際の重複警告／追加制限をどの程度設けるか。これは本ADRのコピー追加ルールを変更しない。その他、revision初期値・日時の保持法・ファイルサイズ／件数上限・インポート対応旧版の技術条件は実装前レビュー対象。

## 後続決定（ADR-017：同じJSONの再取込み）

同一バックアップを繰り返し選択した場合でも**ハッシュ履歴による自動ブロックはせず**、毎回、追加件数・別コピー件数・コピー増加の可能性を表示し、**本人の明示確定でのみ追加**するA案を正式採用。別IDコピー・既存データ不変・原子的な保存・衝突分類変更時の再承認という本ADR-016の決定は変更しない。正本：[ADR-017](ADR_017_REPEAT_IMPORT_WITH_CONFIRMATION.md)。
