## 1. A〜Eの責務
| 所有者 | 作業のIssue単位（着手時に実際のIssue番号を割り当てる） | 受入確認 |
|---|---|---|
| A | D00入口、D01公開一覧/絞込、D02詳細・公式URL/unknown・次の一歩 | 0件、受付終了、未確認、一次出典URL、主催草稿に転記しない |
| B | U02入力とバリデーション、P01〜12判定関数、U03読み取りカード | P05/P08、限定P2、同順位ID順、必須6問と任意回答 |

| D | EventRecord保存型、Dexie CAS、U01一覧・削除、JSON選択書出・プレビュー・原子的取込 | 100件/2MiB、未知版、重複キー、繰返し取込、DB不変 |
| E | 一次資料の個別審査、別人確認の調整、受入ケース記録、需要/競合比較・説明動画の検証 | 証拠URL・確認日時・レビュー者記録、未実施を未実施と表記 |

## 2. PRへ進める順序
1. Dが共通型＋Repositoryインターフェースの技術契約PR、B/Cがレビュー。
2. E/Aが参加カタログ形式＋一次情報採用条件をレビュー。実データ未採用なら空カタログのまま開発できる設計。
3. 4人が独立した小さいブランチで画面を開発。B/CのU03共通ファイルは事前に編集範囲を分ける。
4. B/C/D間で保存・編集・競合を結合。A/EでD02の出典・unknown判定を結合。
5. 全員が実画面を確認、Eが受入の証拠を集める（**将来の予定**）。
6. コンテスト動画・AIコーディング説明は実際の動作ができてから作成。

## 3. Issueの完了条件
- 実装IssueのDoneは「実PRがマージされ、本人が差分・受入基準を確認し、レビュアーが検証結果を確認」した時だけ。
- 設計IssueのDoneは文書の追加だけではなく、未決仕様が採用/棄却され別人が確認した時。例外は理由をIssueに記録。
- PRテンプレートのチェックは実行証拠のあるものだけ記入。AI生成コードを読まないで承認しない。
- データ破壊、審査なしの募集断定、P05/P08ルールの変更、子チェック再導入、秘密情報流出があればマージを止める。

## 4. 未完の正式ゲート
- 実名とGitHub IDでA〜Eを割り当てる。
- 重複キー検知・機械可読Schema/fixtureを実装・評価し、保存の別人レビューを取る。
- 地域掲載の責任者・訂正窓口と個別活動の審査を確定する。
- 需要・独自性を検証して結果と限界を説明する。
- ユーザーの明示したコード実装・テスト・公開の範囲の許可を得る。
