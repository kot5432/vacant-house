**4人全員がAIコーディングを使ってよい**。各領域は単独開発者を孤立させるための区分ではなく、変更責任・競合防止・レビュー先の仮割当である。全員が画面・判定・保存を理解できるよう短い説明会とPR交代レビューを行う。**同じ人が自分のPRを最終承認しない**。

## 2. AIコーディング共通作業契約（各Issue/PRに貼るテンプレート）

### Issue（人間が確認する指示）
- **目的**：どのユーザー行動・画面・タスクを実現するか（要件ID、U01〜04/P01〜12）
- **前提**：適用するADR番号・正本リンクとversion
- **変更許可範囲**：ディレクトリ／ファイル、変更してはいけない入力・進捗・出典・JSON版
- **受入条件**：入力例／期待表示／異常系／保存失敗時の処理
- **テスト予定**：単体、保存統合、E2E、アクセシビリティ（実行許可後のみ）
- **AI利用の記録**：ツール名、生成した内容、担当者が修正した部分、レビューで確認した点
- **前提の不明点**：AIが勝手に仕様を補わずIssueへ返す

### AIへ毎回守らせる制約
1. 現行`docs/v3`の最新ADRを優先する。旧空き家案・古いv1/v2・旧STEPの「未採用」説明を混入しない。
2. **仕様変更と実装提案を分離**。既決の6問・P01〜12・P1/P2/P3・保存/復元規約をAI判断で変えない。
3. AIの「テスト済み」「公式確認済み」という文章は証拠にしない。人間が実出力・ツール結果・原ページと照合する。
4. 公式資料をAIの要約だけから法的義務・施設使用可否として断定しない。出典のURLと対象範囲、最終確認日、第二レビューを要求する。
5. GitHub上のPR単位は小さくする。ドキュメント変更、型、ルール、保存、UI、公式出典を別責務に分ける。
6. 実装後のテスト出力、実際の端末・ブラウザ、合否・再現条件をPRへ添付。CIが緑でも人間レビューを省略しない。
7. APIキー、個人情報、実在の参加者名をAI入力へ不用意に渡さず、架空のイベントデータを優先する。

## 4. 変更・レビュー・公開ゲート

- **チームルールとして推奨**：feature branch→小さなPR→実装者以外のレビュー→必要なテスト結果確認→merge。初回から大規模な自動生成PRを一括取り込まない。
- AI生成率を目標にせず、**人間が機能・根拠・テスト結果を説明できる**ことを品質条件とする。
- 本番に影響するVercel接続/環境変数/公開は公開責任者とユーザーの明示許可が出てから。Vercelプレビューすら今回は作らない。
- `main`の保護、2人レビューが必要な公式出典、schema変更時の固定入力ケースの改訂を着手前にGitHub設定へ落とし込む（現在は設定していない）。
- 月次公式情報更新担当と別レビュー担当は、個人割当後に決定する（ADR-009〜011）。**2026-11-30 JSTが11月分の確認期限**。
- リリース・提出前に、最新版の募集要項・紹介動画の形式/尺・独自性・AI利用の記載を確認する。
