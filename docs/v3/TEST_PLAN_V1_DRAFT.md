## 2. 判定エンジンのテスト入力

- **固定時計**を注入し日時の揺れをなくす。現在日付に依存するルールは入力時刻を引数に持たせる。仮の「開催14日前」閾値は正式採用まで未確定。
- 同じ入力＋同じ進捗＋同じルール版＋同じ評価時刻で出力が完全一致すること。
- 基本6問の各選択肢と条件付き施設分類を組み合わせ、本人の未定、未回答、値ありを別々に扱うこと。
- 高岡市＋会場候補/決定＋本人によるセンター選択以外では、センター固有の説明を返さない。
- 子ども向け／両方ならP05を確認候補として残す。大人のみなら子ども固有の事項を省略。
- 物理会場なしの場合はP07/P08の物理施設関連タスクを該当外にし、オンライン支援の未対応を明示する。
- 完了済みP08の会場変更では履歴を保持し要再確認とする一方、無関係なタスクにはフラグを付けない。
- P1複数時も代表以外の重要事項を出力に含める。対象外（本人判断）と非該当（判定）を混同しない。

## 3. 保存・整合性のテスト

| ID | 条件 | 期待結果 |
|---|---|---|
| DB-01 | イベントA・Bを保存しAを変更 | Bの値・revisionは変わらない |
| DB-02 | 進捗変更→ページ再読込 | 完了／再確認／任意チェックが復元される |
| DB-03 | 同じeventIdで別タブから異なるrevisionを保存 | 古いrevisionによる上書きは拒否 |
| DB-04 | イベント削除→古いタブから編集保存 | 削除済み同IDが再生成されない |
| DB-05 | 削除時に例外を発生させる | 削除成功と表示せず対象イベントが残る |
| DB-06 | トランザクション途中の例外 | 中途半端なデータにならず元データを保つ |
| DB-07 | 保存容量制限で保存失敗 | 保存成功を表示せず未保存差分を維持 |
| DB-08 | 古いschemaを移行 | 入力・進捗・eventIdが保たれ、版が更新される |
| DB-09 | 移行中の意図的な失敗 | ロールバックし、旧データを勝手に削除しない |
| DB-10 | より新しい未対応schema | 開けない旨を表示し、古い形式で上書きしない |
| DB-11 | 破損したレコード | 自動初期化せず安全な復旧案内 |
| DB-12 | ブラウザデータをユーザーが削除 | 過去データの復元を保証しない説明に整合 |

## 4. UI/E2Eテスト

| ID | 操作 | 期待結果 |
|---|---|---|
| UI-01 | 何も保存していないHomeを開く | 新規イベント作成CTAが分かる |
| UI-02 | 基本6問を回答し生成 | 優先理由→次の行動→4領域P01-P12の順で表示 |
| UI-03 | 「未定」を選択して次へ | 未回答と混同してエラーを出さない |

| UI-05 | 詳細チェックをすべて完了 | 親タスクを勝手に完了しない |
| UI-06 | U03進捗変更・保存 | 保存成功後だけ「このブラウザに保存済み」 |
| UI-07 | U04で編集してキャンセル | 保存済み元データを変更しない |
| UI-08 | U04で編集・保存失敗 | 反映済みと表示せず再試行可能 |
| UI-09 | 施設カテゴリを変更 | 非該当となった施設固有案内を消す |
| UI-10 | 2件作成し一方を削除 | 削除した1件だけが消える |
| UI-11 | 320px／200%文字／キーボード | 主要操作・進捗・削除確認まで利用可能 |
| UI-12 | 再読込/直接URLでイベント再開 | 正しいeventIdのプランを表示 |

## 5. CIでの実施ゲート（今後）

- Pull RequestでLint/Typecheck/Unitテスト/Buildを必須候補とする。
- E2Eは少なくともプラン生成→進捗更新→再読込→削除を実施する。ブラウザDBのテストはクリーンプロファイルと移行済みプロファイルを区別。
- 公式資料リンクと対象範囲の点検はビルドの実行テストと異なるため、点検記録を別管理。
- 公開前にブラウザ容量不足・別タブ・破損データ・更新時の再確認を手動・自動双方で試験。
- 性能1秒以内目標はデバイス・イベント件数・ブラウザ・固定日時のベンチマーク条件を確定してから測定。
