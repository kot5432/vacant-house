# ADR-004｜再確認の明示的な解除（A案正式採用・2026-11-15）

**状態：利用者がA案を明示採用済み。** 本書の決定は現行の「初めて単発・小規模の非営利地域イベントを主催する人向け準備支援Webアプリ」にのみ適用。旧空き家物件・所有者診断・マッチング・旧相談文コピー案は対象外。**設計のみで、実装・実行テスト・Vercel公開は未実施。**

## 1. 正式決定

- **再確認は、利用者がタスク詳細で「再確認を終えた」を明示操作した場合だけ解除する。**
- 解除は進捗を「完了」「対象外」に選び直す操作とは独立。単に詳細を開く、子チェックを選ぶ、U04で情報を変更するだけでは解除しない。
- 操作後、保存された`progress.status`（以前の完了・本人対象外等）を**自動変更しない**。
- **成功時のみ** `needsRecheck=false`, `recheckReasonCodes=[]` とし、eventIdとrevisionを照合してDexie/IndexedDBに原子的に保存。失敗／競合時は永続値を解除済みと扱わない。
- 「再確認を終えた」は**本人が現在の条件を確認したという自己申告**であり、施設利用許可・安全性・法律への適合・確認事項の客観的な完了を保証しない。

## 2. 操作契約

| 事前状態 | 利用者操作 | 保存成功後 | 優先候補 |
|---|---|---|---|
| `completed + needsRecheck=true` | 「再確認を終えた」 | `completed + false`（本人の完了申告を保持） | 通常の未解決候補から除外 |
| `not_applicable + needsRecheck=true` | 「再確認を終えた」 | `not_applicable + false`（本人の対象外判断を保持） | 通常の未解決候補から除外。ただし根拠に基づく注意は表示可能 |
| `in_progress + needsRecheck=true` | 「再確認を終えた」 | `in_progress + false` | 進行中なので未解決候補のまま |
| `not_started + needsRecheck=true` | 「再確認を終えた」 | `not_started + false` | 未着手なので未解決候補のまま |
| `needsRecheck=false` | ボタンを表示しない／無効化 | 変更なし | 既存の進捗規則に従う |
| 任意状態 | 保存失敗・revision不一致 | **旧レコードを変更しない** | 未保存状態を通知、再試行または最新版の再読込 |
| 旧タブから削除済みeventId操作 | 更新要求 | 保存拒否 | イベントを復活させない |

## 3. 手動「対象外」と条件上の「非該当」の区別

- `applicability=no` はルールの判定結果。建物の予約チェックが対象外になる等、**ユーザーの進捗を変更しない**。
- `progress.status=not_applicable` は本人の選択であってアプリによる施設許可や手続き不要判定ではない。選択前の短い確認表示を**推奨するUI細則**として扱う（確認ダイアログの最終文言・形式は未承認）。
- 施設公式の重要注意、条件不足、一般的な注意は本人の対象外選択だけでは消さない。ただし現在の入力から施設適用外になった根拠は表示しない。
- 後日、確認前提が変われば`status`を保持したまま`needsRecheck=true`となる。解除は再度本人の明示操作を要する。

## 4. データ整合性

- 単一イベントの`progressByTask[taskId]`に`status, checkedItemIds, needsRecheck, recheckReasonCodes, updatedAt`を保持。
- 解除時の更新は`eventId, taskId, expectedRevision`を用い、レコードとタスクIDの存在・最新revision・現在`needsRecheck=true`を確認してから一体保存。現在Falseなら重複解除要求として扱い、勝手にrevisionを増やすかは実装契約で決める。
- 保存成功後の表示は「このブラウザに保存しました」。保存前は「変更あり／保存中／保存失敗／他のタブで変更された」を使う。
- 解除と同時に最新条件からまた新たな再確認が必要になった場合、**古いフラグを消しただけで新しい理由を隠さない**。保存時のrevision照合と現在の条件検証で不一致なら競合とする。
- `recheckReasonCodes`を解除時に空にするのは**現在の未解決理由**の意味。履歴全体を保存・閲覧する機能はMVP範囲外であり、以前の`status`を維持することと、全回の監査履歴保持を混同しない。

## 5. 受付条件（全て未実行）

- RC-01: `completed+true`で解除→保存成功後に`completed+false`、代表優先候補から除外。
- RC-02: `not_applicable+true`で解除→本人の対象外判断を保持しつつ注意を残す。
- RC-03: `in_progress+true`で解除→再確認は解決、ただし未解決の進捗として残る。
- RC-04: `not_started+true`で解除→再確認は解決、未着手なので未解決に残る。
- RC-05: ボタン操作前・タスク詳細を開いただけ→`needsRecheck`は変わらない。
- RC-06: 保存失敗→永続レコードはtrueのまま、画面で再試行可能。
- RC-07: 別タブrevision競合→古いタブから解除しない。ユーザーが最新版を読み直せる。
- RC-08: 別タブ削除→旧イベントを再生成しない。
- RC-09: P05/P08が同優先で再確認対象→ADR-003のP01〜P12 ID順を維持。
- RC-10: 施設カテゴリが変わり以前の高岡市施設根拠が対象外→現在の誤った施設注意を表示しない。
- RC-11: 必要な公式情報が未確認→「確認済み」と表現しない。
- RC-12: スマホ320px、文字200%、キーボードで操作可能。

## 6. 決定済み／未決の境界

**採用済み**：再確認の明示解除、進捗と解除を別操作、進捗保持、保存成功後のみ解除確定、旧イベント復活防止。

**UIの推奨（未承認）**：「対象外」選択時の確認ダイアログ、解除ボタン後の二重確認ダイアログ、再確認理由の長文表示、recheck原因の完全監査履歴の保存。
