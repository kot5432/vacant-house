# STEP7-⑥｜旧版タブ・IndexedDBスキーマ移行の安全契約（実装前レビュー）

作成日：2026-11-15。**提案・未承認の技術詳細**。ADR-001のDexie/IndexedDB、ADR-004の明示的再確認解除、ADR-005の施設値クリア、ADR-012の公式出典同梱、ADR-013の新版検知／手動リロードは正式採用済み。現行地域イベント主催者支援のみ。旧空き家モデルなし。実装・テストは未実施。

## 1. 不変条件
- 新版で`schemaVersion`が増えた場合、旧タブが古い形の`EventRecord`で**上書き・upsert・削除済みイベントの復活**をしない。
- `schemaVersion`はIndexedDB保存形式、`rulesVersion`はタスクの判定、`catalogVersion/sourceRevision`は公式出典内容、`buildId`は配布物の識別。**それぞれ別軸**。
- IndexedDB読込失敗・未知version・破損は**「イベント0件」扱いにしない**。削除・初期化を自動実行せず、データが残り得ることと復旧手順を説明。
- U02の初回未保存入力は永続下書きにしない。U04の編集ドラフトは元レコードと別。U03保存失敗を保存済みと表示しない。
- 公式出典カタログの新版だけで本人`completed/not_applicable`を自動解除・初期化しない。

## 2. 読込と更新の状態表（提案）

| ケース | 検出 | 処理 |
|---|---|---|
| DBが現在対応schema | ランタイム検証成功 | 同じeventIdとrevisionを基に閲覧・更新可 |
| DBが古い既知schema | 移行できる版と判別 | **完全なバックアップ不能を明示**した上で、検証済みの一方向移行をトランザクションで行う。元値の自動欠損は禁止 |
| DBが新しい未知schema | 旧タブからアクセス | 読込・更新を拒否、最新版への更新案内。旧タブで上書きしない |
| DBの一部が不正 | 型・整合検証失敗 | 当該イベントの誤上書きを防止。別イベントまでゼロ件にしない |
| 別タブが先に変更 | revision不一致 | 更新拒否。U04ドラフトやU03未保存状態を説明し、勝手にマージしない |
| 別タブが削除 | eventId不在 | 自動createせず、削除済みとして案内 |
| 新版があるが編集途中 | buildId不一致 | 新版通知のみ、本人が入力を保存／破棄するまで自動リロードしない |
| 出典カタログの版のみ更新 | catalogVersion差 | 本人の進捗DBマイグレーションと混同せず、影響タスクだけ再確認検討 |

## 3. 初回のデータスキーマを固定するまでの確認項目

- 型の定義：`eventId`が一意、`revision`が単調増加、`schemaVersion`とEventInputの必須列挙の形式、`progressByTask`の12タスク構造をランタイム検証。
- U03自動保存とU04明示保存は**同じイベントのrevision整合性**を共有。CAS（読み取ったrevisionと現在のrevisionが一致するか）を同一トランザクション内で判定。
- IndexedDBのDB自体のバージョンとアプリ`schemaVersion`は厳密には別概念。Dexie upgradeとイベントJSON検証を混同しない。
- 複数タブが別コード版で動いているときの`blocked/versionchange`対処をE2Eで計測。
- schema変更を必要とする機能は旧版との両立性を検討し、旧版が新データを壊す可能性が残る場合は書込を止める。ブラウザの完全な競合防止はテスト・技術レビューを要する。
- データの外部バックアップ／同期は現行MVPで未採用。IndexedDBの容量超過・サイトデータ削除などで復元できない可能性を明示。
- 旧空き家案のDBは移行対象にならない（リポジトリ名が同じでもデータ互換性を作らない）。

## 5. 残る採否と次の設計優先度

- **現段階で新たに正式採用しない**：マイグレーション時のバックアップ方針、エラーからの復元UI、別タブ停止の実装技術。
- 次にユーザー判断が必要な論点は、**対応するブラウザの範囲**。Intl.Segmenter、IndexedDB、手動リロードの案内を一貫して検証できる範囲を決めることが重要。
- それまでP01〜P12の細かな判定理由、データモデル、UI文言を確認可能な草案として整理していく。
