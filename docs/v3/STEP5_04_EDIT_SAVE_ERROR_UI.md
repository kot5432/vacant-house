## 1. 画面の責務と方針

- U04は保存済みイベントの基本6問と任意詳細（人数、責任者決定状況、設備・備品、任意説明、条件に該当する施設カテゴリ・任意施設名メモ）を編集する。
- **既存の確定データと編集中のドラフトは別オブジェクト**。U04では編集途中の値を確定イベントへ自動保存しない。主操作「変更を反映する」で検証→影響分析→保存→U03へ。
- U03の**進捗変更は自動保存**。2種類の操作の保存タイミングの違いを混ぜない。
- **初回U02の未完成下書きはA案で永続保存しない（正式採用）**。画面内の入力値は保持し、初回DB保存成功後のみU03へ。U04編集ドラフトの非永続化とは別の操作。
- 保存失敗／競合は本人の意図なしに既存データを上書きしない。ブラウザ内保存はバックアップではない。
- 4領域P01〜P12の判定ルールを利用する。タスク定義の厳密な版・依存関係・再確認条件はSTEP4の単一契約化まで設計案扱い。

## 2. U04画面レイアウト

```text
[← 準備プランへ]                  [イベント情報の編集]
[対象イベントの仮タイトルと、最後の保存時刻]

基本情報
 [イベント種類]       （既存4分類）
 [参加対象]           （子ども／大人／両方／未定）
 [開催時期]           （日付／月／未定）
 [会場の状況]         （未定／候補あり／場所確定／物理会場なし）
 [開催地域]           （高岡市／県内その他／県外／未定）
 [主催者形態]         （一人／複数人／未定）
 [条件に該当する施設カテゴリ／施設利用者の年齢構成]

さらに詳しくする（任意）
 [参加人数（正の整数／未定／未回答）]
 [運営責任者が決まっているか]
 [設備の必要性→該当する場合のみ設備カテゴリ]
 [イベント内容の任意説明]
 [施設名の任意メモ（該当時）]

[キャンセル]           [変更を反映する]
```

- 基本6問はU02と選択肢・バリデーションを共有し、画面ごとに相違を作らない。
- 条件付き質問：高岡市＋会場候補または確定＋「高岡市地域交流センター」を本人が明示した場合のみ施設利用者の年齢構成を質問。参加対象が未成年でも利用者が未成年のみとは推定しない。
- 条件変更により非該当となった施設値は**判定に使わない**。既存データとして残すかクリアするかは、データ保持・プライバシー・再編集UXを見て後で確定する。非該当の施設公式情報はU03から消す。
- 変更の反映で関係のない進捗をリセットしない。タスクチェック項目の履歴も勝手に消さない。

## 3. 更新処理の状態遷移

| 段階 | 状態 | UI表示と遷移 |
| --- | --- | --- |
| E0 | 元のイベントを読込 | サーバーではなくブラウザ保存の現在版／revisionを記録 |
| E1 | 編集中（差分なし） | 保存済みの元データと同じ。反映ボタンは無効でもよい |
| E2 | 編集中（差分あり） | 「変更があります」。キャンセルはE0へ戻す |
| E3 | 入力エラー | 該当項目にエラー、修正できる状態を維持。永続保存しない |
| E4 | 検証・再計算・保存中 | 重複送信を抑止。保存結果が出るまで「保存済み」としない |
| E5 | 成功 | 新版を保存後、U03に戻り変更後プランを表示 |
| E6 | 保存失敗 | 元の保存済みデータは維持、編集差分を画面に保持、再試行可能 |
| E7 | revision競合 | 「別のタブで変更された」と表示、無条件上書き禁止 |
| E8 | 読み込み失敗・未対応版 | 編集できたふりをせず、安全な再試行・戻る導線 |

**推奨する保存の処理境界**：基準revisionの照合とイベント本体・進捗の関連更新を、選定するブラウザDBで一体のトランザクションとして扱う。再確認の理由を含む現在の計算結果を確定した入力に整合させる。保存失敗で元データを破壊しない。技術選定後に実装方式と実際の整合性を試験する。

## 4. 保存失敗・画面移動

- U04で差分があるまま「キャンセル」または戻るときは、**「変更を破棄して戻る」**を明示し、保存済みのイベントに影響しない。差分がない場合は確認不要。
- 反映中は多重実行を防ぐ。保存が成功した場合だけU03へ進む。
- 保存に失敗した場合は「今回の変更はまだ保存されていません」と説明。**再試行**と**編集を続ける**を提示。画面を閉じたときの一時入力の保持は保証しない。
- 外部のブラウザタブを閉じる・リロードの全状況を確実にブロックできるとは保証しない。ブラウザの通常の離脱警告だけに依存せず、画面内で未保存状態を表示する。
- 保存成功は「このブラウザに保存しました」。クラウド同期・バックアップと誤認させない。

## 5. 条件変更と再確認の処理

入力差分と、どのタスクの確認前提が変わったかを分けて処理する。

| 変更 | 影響の例 | 保持する情報 |
| --- | --- | --- |
| 参加対象：成人→子ども／両方 | P05安全・見守りの詳細と優先候補を再計算 | その他タスクの完了履歴 |
| 会場：候補→別の会場候補 | P07／P08／P09の確認前提を再評価。完了済みで依存が変わった項目に再確認 | 以前の完了履歴 |
| 地域：高岡→その他 | 高岡市固有の案内・適用条件を現在の表示から除外 | 別の条件に依存しない進捗 |
| 施設カテゴリ：地域交流センター→その他 | センター固有のP08案内を削除 | 施設以外の進捗 |
| 日付を変更 | P03・P12等、日時に依存する説明・優先候補を再計算 | 無関係なタスク |
| 必要設備を変更 | P09の詳細確認を更新 | 別カテゴリの進捗 |

- 「タスク完了」はイベント条件が決まったこととは異なる。
- `completed + needsRecheck` は許容し、未解決の確認事項としてU03に戻す。**完了履歴を暗黙に未着手へ書き換えない**。
- 新条件でタスクが非該当になった場合、現在の優先候補から除外。過去の進捗履歴の表示や保持は別途データ契約を確定する。
- 変更の影響を受けるタスクの厳密なリストは、P01〜P12の依存定義を単一契約へ整理して最終確定する。表は代表例であり全組合せを保証しない。

## 6. 別タブとの競合

想定：Aタブがrevision 10を読み込む→Bタブがrevision 11を保存→Aタブから編集内容を反映。

- Aタブは無条件にrevision 11を上書きしない。
- 画面に「別のタブでこのイベントが変更されました」と明示する。
- 可能なら本人が現在の差分を確認できるようにする。「新しい保存内容を読み込む」は**現在の未保存差分を失う可能性**を告知してから実行。
- 競合解消のための自動マージや端末間同期はMVPでは行わない。最新版を読み直して編集し直す方式を第一候補にする。
- イベントIDとrevisionの比較を保存トランザクションで保証できる方式を選定する。

## 7. イベント削除：U01から

```text
[イベントカード] [その他の操作 → 削除]
       ↓
「このイベントを削除しますか？」
（識別できるイベント名・開催時期）
「このブラウザ内の入力と進捗を削除します。元に戻せません。」
[キャンセル] [削除する]
       ↓
削除中 → 成功なら一覧から除去・失敗ならカードを残して説明
```

- 個別削除は**必ず対象イベントIDを特定**する。ほかのイベントは保持する。
- 削除中に他タブが同イベントを変更したら競合を検出し、何を削除するか再確認する方針（実装方式は技術選定後）。
- 削除後に別の古いタブから同IDが「復活」しないよう、存在・revisionを検証して保存を拒否する。
- 誤削除の自動復元はしない。ファイル書出し・クラウドバックアップはMVP外。
- アプリ側共通のP01〜P12定義や公式資料は、個別イベント削除で消さない。

## 8. 共通保存・障害状態

| 状態 | 表示例 | 禁止する動作 |
| --- | --- | --- |
| 保存済み | このブラウザに保存しました | クラウド保存済みと誤称 |
| 未保存差分 | 変更があります | 保存済みと誤表示 |
| 保存中 | 保存中… | 二重保存でデータ競合 |
| 保存失敗 | 保存できませんでした。変更はこの画面に残っています | 成功画面への無条件遷移 |
| 複数タブ競合 | 別のタブで変更されました | 自動上書き |
| 破損／未対応版 | 保存データを開けません。再試行・確認案内 | 自動初期化 |
| 容量不足・保存利用不可 | このブラウザに保存できません | 長期保存を保証 |
| 公式情報なし | 該当する公式案内は未登録です | 架空の条件を追加 |

## 9. 画面品質・アクセシビリティ

- 未保存離脱／変更破棄ダイアログはボタンの意味を明確化し、危険な操作が初期フォーカスや既定操作で実行されないようにする。
- 320px幅・文字200%でも、項目・説明・エラー・操作が見えること。
- 項目ラベル、入力値、エラーを近接させる。キーボードのみで反映／キャンセル／競合確認／削除確認まで操作できる。
- 保存状態を色だけで伝えず、過剰な読み上げを避ける適切な通知にする。
- 保存が失敗していても、すでに保存済みの版と未保存編集内容を同一視しない。

## 12. 要件定義・技術選定までの残件

1. **U02初回下書きは非永続化A案で採用済み**。再確認解除・本人対象外の操作詳細は[STEP6-①](STEP6_01_PROGRESS_RECHECK_SPEC.md)で提案。

3. タスク展開の複数同時表示・進捗分母・任意イベント名称のUIの要否。

## 13. 施設固有入力のクリア（ADR-005正式採用）

地域・会場状態の変更で以前の施設カテゴリ／施設利用者構成／施設名メモが非該当となった場合、**U04の「変更を反映する」に伴うIndexedDB保存成功後のみクリアが確定**。保存失敗・キャンセル・revision競合時、保存済み版は変更しない。保存成功したとき旧値は自動復元しない。P07〜P09の進捗とチェックの過去状態は消さず、必要な再確認理由を付与。現在の施設に該当しない出典・施設条件をU03に出さない。詳細なフィールド別マトリクスは[ADR-005](ADR_005_CLEAR_INAPPLICABLE_FACILITY_INPUT.md)。同じQ4状態のままで候補施設が変わったことは自動検出できないため、施設メモを本人に更新してもらう導線が必要（別途レビュー）。

## 14. 過去の開催日・月（ADR-006正式採用）

希望開催日が過去の実在日、または希望開催月が過去月である場合も、U04では注意文を表示したうえで変更・保存できる。当日・当月は過去扱いしない。月を1日に補完しない。過去であることだけを理由に法的な期限超過や開催済みと断定しない。存在しない日付は従来どおり入力エラー。[ADR-006](ADR_006_ALLOW_PAST_SCHEDULE.md)。

## 15. 参加人数1000超の扱い（ADR-007正式採用）

U04の任意人数は1以上の安全整数を受け付ける。**1001人以上でも入力・保存が可能**で、「小規模向けの案内には限界がある」旨の注意をフィールド付近に表示し、`変更を反映する`操作を阻止しない。0、負数、小数等は入力エラー。保存が失敗してもドラフト値を保持。数値の大きさで許可取得・安全性・定員を判定しない。[ADR-007](ADR_007_ATTENDEE_COUNT_WARNING.md)。
