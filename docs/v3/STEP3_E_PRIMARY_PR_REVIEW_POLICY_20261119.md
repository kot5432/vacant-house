## 2. チームが行うPRの手順
1. Issueの対応範囲を確認し、担当の個人ブランチで変更、PRを作成。
2. PR本文に変更点、影響するADR・画面・データ、AI使用、実際に実行したテスト（未実施なら`not_run`）を記載。
3. **A〜DのPRはGitHubのReviewersに`kot5432`を指定**。必要な専門担当にも追加依頼（ただしEの最終主レビューを省略しない）。
4. **E作成PRではEをレビュアーに指定せず、A〜Dから1人以上を指定**。
5. E（E作成PRなら指定されたA〜D）が差分と受入条件を確認し、問題があればRequest changesまたはコメント。
6. PR作者が修正し、必要な確認結果を記録。**コメントの解決なし・レビュー未了ならmainへマージしない**。
7. 承認と必要な実行検証がそろったらmainへマージ。誰がいつ承認したか履歴を残す。

## 3. GitHub設定と未完の技術強制
- README/CONTRIBUTING/PRテンプレートの**運用文書への反映は完了**。
- mainへの直接push禁止、PRでのレビュー必須、最新push後の承認失効（可能な場合）などの**branch protection / rulesetは管理者による実設定・画面確認が別途必要**。今回の文書PRだけで設定済みとは主張しない。
- GitHubの「最低1人の承認」は一般に**『必ずEが承認』まで自動で保証しない**。チーム規約として、A〜DのPRはEのレビューを必須にする。
- Eが管理者でも、自分作成のPRを自分の承認だけでマージしない。管理者によるレビュー規則の例外操作は通常禁止。
- 緊急例外が必要な場合は、Issueに理由・影響・代替レビュー担当を記録し、**Eを含めたチーム合意を先に得る**。
