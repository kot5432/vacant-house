# 開発・運用計画 v1（2026-11-15）

> **設計だけ。実装・依存導入・公開・実測・利用者テストは未実施。** 現行の単発・小規模の非営利地域イベント開催準備支援Webアプリ専用。旧空き家所有者診断・物件登録・マッチング等の資産は混ぜない。
>
> 技術選定： [ADR-001](ADR_001_TECH_STACK_ADOPTED.md) ／機能： [要件定義v1草案](REQUIREMENTS_V1_DRAFT.md) ／ルール： [RULE_ENGINE_CONTRACT_V1.md](RULE_ENGINE_CONTRACT_V1.md) ／データ：[DATA_DESIGN_V1.md](DATA_DESIGN_V1.md) ／構成：[ARCHITECTURE_V1.md](ARCHITECTURE_V1.md)。

## 1. ゴールと出荷判断

- 利用者が基本6問から準備の全体像と現在の優先事項、その理由・次の一歩を理解できる。
- 同じブラウザで複数イベントを作り、進捗を更新・保存・再開・個別削除できる。
- 高岡市の施設固有情報は**本人選択＋対象条件一致＋確認済み公式出典**でのみ表示する。
- 未回答／未定／進捗未着手／対象外を混同せず、進捗完了をイベントの許可・安全の保証としない。
- **現状は設計のみ**で実装着手には別途判断が必要。コンテスト応募規定・日程も提出前に再確認する。

## 2. 開発体制（3人以上の少人数チーム想定）

| 役割 | 内容 | AIコーディングとの分担 |
|---|---|---|
| 機能実装担当（ローテーション可） | 小さいPR単位でReact画面、ルール、Repository等を実装 | AI生成コードをそのまま取り込まず、入出力・型・依存を確認 |
| レビュー担当（実装者以外） | 仕様との照合、セキュリティ、テスト、UIアクセシビリティを確認 | AI提案の欠陥も人間が判定 |
| 検証・公開担当 | テストケース、公式情報出典台帳、Vercelプレビューと本番公開を管理 | 試験結果や公式判断はAIの推測を根拠にしない |

役割は人に固定する必要はないが、**PR作成者と承認者を分ける**。GitHub権限と公開担当者はメンバー確定後に決定。

## 3. 実装の順序（時間を固定しない開発フェーズ）

| フェーズ | 開発範囲 | 成果物・完了条件 |
|---|---|---|
| G0 仕様の最終承認 | 基本入力・判定契約・初回下書き・オンライン範囲・公式出典の有効性 | 不明点一覧を残さず、実装仕様版に固定 |
| G1 環境・基盤 | React+TS+Vite、Dexie、ルーティング、テスト、Lint・Typecheck、PR運用、Vercelプレビュー | ローカル/プレビューで空画面起動、CIが動く。旧コード混入なし |
| G2 ルールエンジン | P01〜P12の適用、優先、理由、再確認、固定日時、テーブルテスト | 期待ケースと境界の単体テスト合格 |
| G3 保存Repository | Dexie schema、複数イベント、revision、保存・復元・削除、migration・異常系 | 競合/削除後復活防止/破損/容量不足のテスト合格 |
| G4 画面U01/U02 | 新規イベント・保存済み一覧・基本6問・条件付き施設質問 | 基本フローとバリデーションのE2E合格 |
| G5 画面U03/U04 | 優先→次の行動→全体像、進捗、編集ドラフト・キャンセル | 進捗自動保存とU04確定保存を区別し、再確認・競合・失敗のE2E合格 |
| G6 品質と公開 | モバイル・キーボード・文字拡大、公式出典更新、導線・説明、Vercel本番チェック | 受入テスト通過・表示文言・データ保持の制限を説明・公開判断 |

開発は並行してもよいが**後続画面のPRが前提となるdomain/repository契約を無断変更しない**。変更時はレビューで仕様も更新する。固定の日数や担当者名は、チーム実績と応募日程を確認してから計画する。

## 4. ブランチ・PR運用

1. `main`を設計資料とレビュー済み成果物の基点とする案。公開接続時には本番への自動配信を無意識に有効にしない。
2. 1PRにつき1つの責務（例：基本6問のバリデーション、P05の判定、Dexie CRUD、U03の進捗表示）。
3. PR本文に「対応要件ID」「変更した判定・保存契約」「対象テスト」「スクリーンショット／動作説明」「AI利用範囲」「残るリスク」を記載。
4. レビュー担当はコード差分だけでなく、**自動テストに存在しない条件**を指摘。公式施設の許可判断をAIに任せない。
5. CI候補：依存インストール→Lint→Typecheck→Vitest→Build→Playwright重要導線。正式なCI/テストツールは実装前に確定。
6. VercelプレビューはPR確認用。PreviewとProductionのIndexedDBはオリジンが違い、テストデータの共有はしない。

## 5. 公式情報の更新と表示責任

- 出典台帳に`sourceId, タイトル, URL, 対象施設, 対象条件, 確認日, 公開／改定日が確認できればその日付, 最終レビュー者`を保存。
- ルールが特定施設に該当するかは本人の**明示選択**が必要。自由メモの文字列から自動判定しない。
- **公開直前**に対象施設の公式情報を再確認して根拠リンクを点検。根拠が未確認／改定されている場合は施設固有の断定案内を停止し、一般的な「管理者へ確認」に置き換える。
- 公開後は少なくとも**各リリース前**に関連出典を点検。月次などの固定頻度は運用担当者・資料の変動頻度を見て決める。
- エラー報告や仕様疑義はIssueに記録し、重要な誤案内が疑われる場合は該当する出典文言を停止してから修正する。

## 6. セキュリティ・プライバシー・利用規約の確認

- 氏名／住所／連絡先／GPS／参加者名簿は機能に含めない。任意説明欄は個人情報を入力しないよう案内。
- 外部分析SDK・第三者スクリプト・外部フォント・外部URLを監査し、入力情報が不要に送信されないか確認。
- Cookie・ログ・Vercel側アクセス情報等、**利用者DBに保存しないこととホスティング側の標準ログの存在は別問題**。公開前にプライバシー表記とサービス仕様を確認する。
- CSP等のヘッダー、依存脆弱性更新、アクセス権限、公開ブランチ保護、秘密情報の保管を確認。
- VercelのHobby/Pro料金と個人・非商用利用条件、チームの作業方法を公開前に確認する。

## 7. コンテスト向け確認

- 架空の例を用いた説明は明示する。実装済み／利用者検証済み／行政が認めたと誤解させない。
- **中心デモ**：基本6問→優先理由＋全体像→進捗更新→条件変更による再確認→同一ブラウザ再開。
- 比較対象の汎用ToDo・会場検索・行政情報と本製品の違いは「状況別の準備全体像＋優先順位」。独自性・需要は利用者評価で検証予定。
- 動作デモや成果発表前にブラウザ・オリジン・保存データを固定して再現性を確認する。

## 8. 完了ゲートと未決事項

- **仕様ゲート**：P01-P12依存・同順位・施設固有情報の適用・物理会場なしの支援範囲を最終確定。**U02下書き非保存はA案で決定済み**。
- **技術ゲート**：正式採用したReact/TS/Vite + IndexedDB/Dexie + Vercelで、周辺のrouter・validation・test・styleを選定。対応ブラウザ・Vercelプラン・公開管理者を決める。
- **品質ゲート**：保存失敗/競合/移行/削除、320px/200%文字/キーボード、公式情報の誤適用がないことを試験。
- **利用者ゲート**：初めてのイベント主催者へ「全体像・優先の理由・次の行動」が分かるかを検証（**現状未実施**）。
- **公開ゲート**：プライバシー・免責表記、公式出典、依存更新・脆弱性、コンテスト規定、Vercel条件の確認。

本計画は**設計段階の計画書**であり、スケジュールや完了見込みの保証ではない。

## 9. 公式出典の管理工程（v0.1提案）

[公式出典台帳・改定時の運用設計](OFFICIAL_SOURCES_OPERATIONS_V1.md)を参照。実際に使用する高岡市の公式資料について、担当者が原ページ・対象施設・確認日・利用者への表示文言を検証し、別のメンバーがPRレビュー。取得不能や改定疑いは施設固有の断定表示を停止し、一般的な確認案内へ。リリース前の点検は必須候補とするが、月次等の頻度・運用担当者・長期間更新されない配信物への対応は別途決定。**現時点で公式サイトの最新内容を実地確認したわけではない**。

## 10. 公式情報の版・停止・再開と人数B案

[出典状態遷移の詳細案](OFFICIAL_SOURCES_STATUS_TRANSITIONS_V1.md)では未確認時に施設固有断定を止め、再確認と別メンバーのレビュー後に掲載再開する手順を提案。月1回＋各リリース前の点検頻度は**未決**。人数は[ADR-007](ADR_007_ATTENDEE_COUNT_WARNING.md)で**1以上の安全整数、1000超は警告のみ・保存可**を採用済み。大人数の入力だけで管理者の申請・安全判断を自動判定しない。
