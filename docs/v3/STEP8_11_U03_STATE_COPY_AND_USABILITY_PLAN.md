# STEP8-⑪｜U03の優先理由・進捗・出典の状態別表示と利用者検証シナリオ（推奨設計）

作成：2026-11-16。**現行アプリの既決MVP内での画面詳細案**。[ADR-003](ADR_003_PRIORITY_RULES_ADOPTED.md)、[ADR-027](ADR_027_P08_P2_NO_FACILITY_AUTO_ESCALATION.md)、[ADR-028](ADR_028_LIMITED_P2_PRIORITY_BY_EXISTING_INPUTS.md)の正式優先順位を変更しない。旧空き家案の資産・機能なし。**画面実装／利用者テスト／法令・公式原出典の再確認は未実施**。

## 1. U03の上から下への情報順（新画面なし）

1. イベントの入力要約：「体験会」「参加対象：未定」「開催時期：11月ごろ」等、本人が入力した事実だけを表示。任意欄が空なら勝手に値を補完しない。
2. **次に確認するとよいこと**：未解決の最上位タスク名、優先度ラベル（P1/P2/P3）、理由（最大の目安1〜2文）、具体的な次の一歩（1文）を同じカードに表示。「絶対に必要な手続き」「危険」という誤解を生むラベルを避ける。
3. **ほかの優先事項**：代表以外の未解決P1があれば視認可能に表示。P2/P3も一覧から到達可能にする。
4. **準備の全体像**：4領域・P01〜P12、本人進捗（未着手／進行中／完了／対象外）、アプリの「優先度」、条件変化による「要再確認」を別の視覚要素とテキストで表示。
5. **根拠と確認先**：本人入力に基づく提案と、対象が適合し有効な公式ページを分ける。施設固有の有効性が失われたときはその断定を止め一般の確認先に戻す。
6. **保存の状態**：進捗保存中／成功／失敗・競合を明示。失敗状態を色だけで示さず、保存完了前の画面離脱に注意を示す。

## 2. 代表カードの文言例（設計用ダミー入力）

| 入力の例 | 代表タスク候補（本人進捗が全未着手の場合） | 理由表示の案 | 次の一歩 |
|---|---|---|---|
| `audience=both`, `venueStatus=undecided` | **P05・P1** | 「子どもも参加するため、見守りや当日の連絡方法を先に確認しましょう」 | 「当日の連絡・見守りについて関係者と確認する」 |
| `eventType=other`, `audience=undecided` | **P01・P2**（他のP1がない場合） | 「どんな活動か整理すると、次に必要な準備を選びやすくなります」 | 「実施したい体験を一文でまとめる」 |
| `venueStatus=undecided`, `audience=adults`, 他のP2が未解決 | **P05・P2の可能性がある**。P07=P2だがIDが後 | 「安全面と連絡方法を確認しましょう」 | 「緊急時の連絡方法を考える」 |
| `venueStatus=no_physical_venue`, `audience=adults` | **P05・P2**。P08もP2 | 「開催方法に合わせた安全面の確認から始めましょう」 | 「参加者への連絡方法を考える」 |
| 高岡市の対象施設に一致・出典有効 | 代表は**他の未解決P1/P2も含めた全タスク順位**で選ぶ | P08はP2を維持し、該当公式ページと対象範囲を別表示 | 「該当施設の公式ページ／窓口で確認する」 |

※「代表」は**他の全タスクの入力・本人進捗を評価した結果**で決まる。例の一部条件だけから代表を必ず確定すると誤認させない。P05・P08の行政義務や施設利用可否を断言しない。

## 3. 状態別表示

| 状態 | 提示 | 禁止する誤解 |
|---|---|---|
| 本人未着手 | 「未着手」＋先に確認する理由 | P3＝不要、P1＝法的必須 |
| 本人進行中 | 「進行中」＋次の具体行動 | アプリが作業を完了した |
| 本人完了 | 「完了（本人が設定）」 | 主催資格・安全・許可の認定 |
| 本人対象外 | 「対象外（本人が判断）」 | ルール上`applicable=no`と同じ |
| `needsRecheck=true` | 「以前の判断を保存したまま、再確認が必要」＋理由 | 完了履歴の抹消、開くだけで自動解除 |
| `applicable=needs_information` | 「確認に必要な情報が足りません」＋確認行動 | 未入力＝不要 |
| `applicable=no` | 「今回の条件では非該当」 | 本人が手動で対象外を選んだ |
| 施設出典期限切れ | 「施設の最新条件を公式窓口で確認してください」 | 旧情報を今も有効と断言 |
| 保存中 | 「変更を保存しています」 | 保存完了と誤表示 |
| 保存失敗・CAS競合 | 「保存できませんでした。最新の内容を確認してください」 | 変更がサーバーに送信済み、上書き済み |

## 4. キーボード・スクリーンリーダー・小画面

- 代表カードのタスク名を見出し、理由と次の一歩をその直後の文章とし、**視覚順と読み上げ順を一致**させる。
- 展開できるP01〜P12には「詳細を開く／閉じる」を明確に示し、キーボードでも操作できる。複数展開の候補は既存[STEP5-⑤](STEP5_05_UI_DECISIONS.md)に従う。
- P1/P2/P3は色だけで伝えない。「先に確認」「後で確認」などの短い説明を併記。未着手・要再確認も色だけの区別にしない。
- 非同期の保存成功・失敗は適切なステータスメッセージを利用し、**連続入力で読み上げが過剰にならない**頻度を実機で検証する（現時点の具体aria属性は技術案）。
- 320px幅・文字拡大200%で、優先理由と次の一歩が分断・横スクロール・省略されないことを受入条件とする。

## 5. 利用者検証の進め方（企画・未実施）

対象は**実際に小規模な地域イベントを企画したい人または初主催者**。実施人数・合格閾値を未検証のまま確定した数値として扱わない。

1. 架空の体験会を6問で設定してもらう。説明なしに「次に確認すること」を見つけられるか観察する。
2. 「なぜそのタスクが上に出たと思いますか？」と尋ね、実際の回答条件と結び付いた説明か確かめる。答えを誘導しない。
3. P05とP08の違いを確認し、P1/P2を行政義務・安全保証と誤解していないか聞く。
4. 既存進捗を完了にし、会場条件変更による再確認の意味を本人の言葉で説明してもらう。
5. U01で一部のイベントだけJSONに書き出し、何件含まれなかったか理解しているか確かめる。

記録対象：タスクを見つけられたか、理由の理解、迷い・誤操作の箇所、本人が言語化した改善案、所要時間（参考）。**達成率や需要があることを検証前に断定しない**。
