## 作業の重複回避
- U03：Bはカード読取表示、Cは進捗操作、Dは保存の責務を保持。
- Cは直接Dexie/JSON Schemaを改変せず、DへAPI要望をIssue化。
- Aは個別活動の公表状況を勝手に「掲載可能」と判断せず、Eが記録しA/Bが別人審査。
- 画面横断共通UIや画面遷移ルーターはA/Bで事前合意し、同一ファイルの競合を避ける。

## PRテンプレートに加える確認
- 関連Issue、変更した画面、保存/型へ影響した箇所、既決ADRへの整合、実行した確認だけを記載。
- 受入ケースID、未実行は`not_run`、AI生成コードの読み合わせ、スクリーンショットは実物/モックを区別。
- Eが原則レビュー、C↔Dなど高リスク領域は相互レビュー。E自身のPRはA/Bに承認依頼。
- `main`保護を作業効率のために常時無効化しない。

## Issueの作成時点
仕様と人の担当を確定させてから「実装Issue」を発行し、担当者を設定。現在は設計Issueに留める。実際の作業量・期日はチームの日程を確かめてから決める。
