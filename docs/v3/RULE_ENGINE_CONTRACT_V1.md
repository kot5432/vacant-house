# STEP4｜判定エンジン実装契約 v1 草案（2026-11-15）

> **状態：実装のための統一案。P01〜P12の最終条件・同順位・期限閾値は承認前。** 計算ルールを検証できる形で定義したものであり、実装や安全・法令認定ではない。
> 対象は単発・小規模の地域イベント準備支援。**空き家物件・所有者診断・マッチング・旧困りごと質問は使用禁止。**
> 既存の [STEP4判定案](STEP4_INPUT_OUTPUT_EVIDENCE.md) と2026-11-14以降の進捗・保存の後続決定を統合する。矛盾したときは正式採用済みの入力方式・保存方式を優先する。

## 1. 入出力契約

**入力**：正規化済みの `EventInput`、イベント別 `TaskProgress`、固定された `EvaluationDate`、版付き `TaskCatalog`、確認済み `OfficialSourceRegistry`。日時・地域・施設の条件を勝手に補完しない。

**出力**：P01〜P12について以下を返す。

| フィールド | 意味 |
|---|---|
| taskId / area | 安定ID・4領域 |
| applicable | `yes / no / needs_information`。本人の手動「対象外」と独立 |
| priority | P1 / P2 / P3、非該当の場合null |
| reasonCodes | 版管理された理由IDの配列 |
| reasonText / nextAction | 確認可能な入力に根差した説明・次の行動 |
| progress | 未着手／進行中／完了／対象外（本人の操作） |
| needsRecheck / recheckReasonCodes | 変更前の確認前提が失効したか |
| effectiveOpen | 優先候補の未解決項目か |
| sources | 適用確認された公式情報のID／出典／確認日 |
| checkItems | 具体的な確認項目、チェック済みでも親タスクは自動完了しない |

同じ入力・同じルール版・同じ出典台帳・同じ評価日時は同じ出力にする。`Date.now()`やDB読み込みを純関数内で直接呼ばない。

## 3. ルールの順序（正式な計算順として提案）

1. **入力検証・正規化**：基本6問の有効値を検証。選択肢「未定」は有効、未回答は別。人数は整数1以上、上限の設定は未決。
2. **施設の適用条件を確認**：高岡市＋会場が候補/確定＋本人選択で地域交流センター＋必要な利用者構成・出典範囲が合致した時だけ公式注意を付与。自由記述の施設名からカテゴリを推測しない。
3. **タスク該当性の判定**：非該当/情報不足を別表現。情報不足を自動で「不要」にしない。
4. **優先候補の生成**：各P01〜P12についてP1/P2/P3を評価。P1=重要な確認の提案、P2=他準備の前提になる確認、P3=後で行う一般準備。危険度・法令評価ではない。
5. **依存と理由を組み立てる**：必要な入力・未確認事項を説明。「会場確定」と「許可取得済み」を混同しない。推測の申込期限を作らない。
6. **保存済みの進捗と再確認を合成**：タスク該当性と進捗を別フィールドで保持。
7. **effectiveOpenを導出**：`applicable=no`は候補外。本人の`completed`または`not_applicable`かつ`needsRecheck=false`は通常未解決候補から外す。ただし、本人が安全・公式条件の確認を対象外にした場合も、その条件の**情報としての注意**を消さない。完了＋再確認は**未解決に含める**。
8. **代表タスクを選ぶ**：未解決のP1→P2→P3。全てのP1は優先領域に表示し、1件代表でもほかを隠さない。最後の同順位並べ替えは固定安定ID。ただし明示的な公式期限に基づく並びの採用は別途決める。
9. **画面用に出力**：代表理由と次の行動、4領域の全体像、該当公式情報／確認日を分離。古い施設条件は再計算で除去。

## 4. 再確認の状態遷移

- `progress.status` は本人が選んだ4値で、アプリは原則勝手に書き換えない。
- `needsRecheck` と `recheckReasonCodes` は独立。条件変更によって**以前の完了・対象外判断の前提が変化した場合**に付与を検討する。
- 対象外の理由が失効しない場合は他のタスクの進捗を保持。条件変更のたびに全タスクを初期化しない。
- `completed + needsRecheck` は過去に完了した履歴と、現在の未解決の確認が共存する状態。
- 再確認の解除は「新条件で確認し終えた」ことを本人が明示した場合。単なる画面を開く／詳細項目の閲覧では解除しない。
- **要検討**：`not_applicable`（本人）を本人の確認なしに未着手へ変えることは禁止。ただし施設・参加対象の変化により手動対象外の理由が無効になれば、再確認を表示する。
- 公式情報に変更があった場合、影響するタスクが完了であっても再確認候補。対象施設が異なれば非該当。

## 5. 固定の優先順と期限

- `P1 > P2 > P3`。同一優先区分内で必要な期限が公式根拠付きで分かる場合に並べる案があるが、**締切の読み込みや差分計算は現MVPでは未実装**。
- 過去の会話にあった**「開催14日前」**は行政期限でも法定要件でもない**未採用の設計仮説**。現行実装契約へ固定の閾値として入れない。
- 代表選択の仮の並べ方：P08（該当重要確認）→P05→P07→P04→P03→P09→他ID。ただし利用者の順位最終承認前はテスト期待値を「P1は全て残る」「同条件で決定的」にとどめる。

## 7. 出典と責任範囲

- 出典台帳で`sourceId, url, title, checkedAt, applicableArea, facilityCategory, edition`を管理。
- 規則の適用は本人が施設カテゴリを明示した場合のみ。公式リンクは情報提供であり「許可済み」「利用禁止を最終決定」という法律判断ではない。
- 出典の版・確認日が古くなった場合の再確認・表示停止条件は運用計画で定義する。
- 開催費用、施設の空き状況、申込締切、必要スタッフ人数、保険適格性などは基本6問から機械的に確定しない。
