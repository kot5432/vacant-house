# STEP7-④｜出典期限切れと更新反映の実装前選択肢

作成日：2026-11-15。**比較・未承認**。[ADR-009](ADR_009_OFFICIAL_SOURCE_MONTHLY_RELEASE_REVIEWS.md)月次とリリース前の確認、[ADR-010](ADR_010_STALE_SOURCE_FAIL_CLOSED.md)期限超過時停止、[ADR-011](ADR_011_MONTH_END_SOURCE_REVIEW_DEADLINE.md)日本時間の月末締切は正式採用済み。現行地域イベント準備支援Webアプリのみ対象。実装・動作試験・デプロイはしていない。

## 1. 未解決の実装境界

アプリはReact + Viteの静的フロントエンドであり、利用者データはIndexedDBにある。公式出典の`reviewedMonth`等をアプリ同梱の読み取り専用データで扱う場合、**ブラウザを開いたまま日本時間の月末を越えること、端末時計のずれ、次月の出典がレビュー済みでも古いビルドのままであること**に注意が必要。

[ADR-011](ADR_011_MONTH_END_SOURCE_REVIEW_DEADLINE.md)は期限超過時の**停止**を確定しているが、再確認完了した最新出典を**どの仕組みで受け取って再掲載するか**はまだ決まっていない。

## 2. 設計の3案

| 案 | 出典の最新状態の取り扱い | 良い点 | 注意 |
|---|---|---|---|
| **A（MVP推奨）** | **出典データをViteの静的ビルドに同梱**。表示時・タブ復帰時にJST月次期限を評価し、期限超過は一般案内へ。新しい`verified`出典の復帰はアプリの新しいビルドを読み込んだときのみ | サーバー・リアルタイム配信なしで実装しやすく、レビューされたセットのみ公開しやすい | 更新版を開かなければ、既に再確認した出典の再掲載が遅れる。古いタブで即時の更新は保証できない |
| B | 静的な`sources.json`を別URLとして配信し、起動時・タブ復帰時に最新版を取得して`catalogVersion`と照合 | コードの再ビルドなしで出典だけ更新しやすい | キャッシュ、取得失敗、バージョン不整合、外部通信、エラー時の検証が増える。信頼できる配信元やCSPの設計が必要 |
| C | 専用APIで出典の有効状態を問い合わせ、更新通知も設ける | 比較的速い更新反映の仕組みを作れる | サーバーと運用負担が大きく、採用済みのサーバーDB・認証なしMVPから逸脱しやすい |

**推奨A**：出典状態が不明・期限切れ・破損なら施設固有断定を出さない、という既決の安全側の挙動を最小構成で守りやすい。**時計の異常による判定漏れや、アプリが更新されない場合の表示についての保証はない**ため、公開時には制限を明記する。

## 3. A案の動作提案（正式承認前）

- アプリ起動時とU03画面を開いたときに、`effectiveStatus`を現在の公式出典カタログの`reviewedMonth`とJST基準日から算定。
- タブが隠れていた後で再表示された場合も再評価し、期限超過なら施設固有の断定を取り除く。
- 月末の境界を**アプリを開いたまま**越えた場合の再評価には、表示中のときの定期再評価／日付境界の更新の仕組みが必要。ただしsetInterval等の実装方式は技術比較後。
- 最新の出典レビュー完了による`verified`復帰は**最新版の静的ビルドを読み込み、現在の適用条件に一致したときのみ**。古いレビュー記録を自動的に当月の確認完了へ変換しない。
- 取得していない新しい出典を、現在のビルド内で`verified`として創作しない。
- 出典情報更新を検知したときは「最新情報を反映するため再読み込みが必要です」と案内し、ユーザー入力のU04未保存ドラフトを突然破棄しない。新しい静的ビルドの検知方法は未決。
- ブラウザのローカル時計が不正確だと分かった場合に`verified`を保証しない。どの水準の不正確さを検知するかは未決。
- 利用者イベント内容・タスク進捗は外部へ送信しない。

## 4. 受け入れテスト（期待のみ・未実行）

| ID | 条件 | A案なら期待 |
|---|---|---|
| UPD-01 | 月末前、確認済み・対象一致の出典 | 出典を表示 |
| UPD-02 | 月末を表示中に越え、前月レビュー未完了 | 出典の断定が画面から消える |
| UPD-03 | 非表示タブで月を越えた後に戻る | 復帰時に期限を再評価して断定停止 |
| UPD-04 | ブラウザの旧ビルドから新レビュー月に切替 | 古いビルドが勝手に新月のverifiedとなることはない |
| UPD-05 | 新しいビルドの出典がverified、本人条件一致 | 新しい確認日と版で再掲載可能 |
| UPD-06 | U04で未保存編集あり、更新を検知 | 破棄せず再読み込み前に注意を表示 |
| UPD-07 | 時計のずれ／出典カタログ破損 | 期限内を無条件に保証せず一般案内へ |
| UPD-08 | リリースがない長期間 | 月末ごとに現行の古い出典が順次失効。本人の準備タスクは維持 |

## 5. ユーザーへの次の意思決定

**公式出典の配信・最新化はA案（静的ビルド同梱・次版読込で復帰）／B案（静的JSONを別配信・画面で最新版確認）／C案（専用API）**のいずれを採用するか。MVPの設計・運用負担からA案を推奨。採用後、アーキテクチャ・出典データ・U03更新表示・テストを詳細化する。

**この選択が決まるまで更新方式を正式確定せず、アプリ実装を始めない**。
