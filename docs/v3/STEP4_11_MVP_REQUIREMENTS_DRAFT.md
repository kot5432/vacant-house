# STEP 4-⑪ MVP範囲・保存範囲・利用フローと要件定義（2026-11-14）

> **現行プロダクトのみ**：富山県内（公式情報は高岡市から）の、初めて単発・小規模の非営利地域イベントを主催する個人・小規模チーム向け「準備全体像・優先順位」支援Webアプリ。
> **本書は要件定義の草案**。実装・動作テスト・利用者検証は未実施。旧空き家活用・所有者診断・物件マッチング・営利開業支援の仕様やデータモデルは引き継がない。
> 関連：[現行入口](README.md)、[STEP3採用事項](STEP3_MVP_BOUNDARY.md)、[STEP4判定案](STEP4_INPUT_OUTPUT_EVIDENCE.md)、[設計資料ロードマップ](DESIGN_DELIVERABLES_ROADMAP.md)。

## 1. 採用確定した前提

- STEP1：初めて単発・小規模の非営利イベント／体験会を主催する個人・小規模チームが主対象。
- STEP2：準備全体像と本人の状況に合った優先順位・理由が中心価値。確認済み公式情報と次の一歩は補助。
- STEP3：**基本6問 → 暫定プラン → 任意詳細化 → 持ち帰り**。既存の入力選択肢を維持。
- STEP4-⑥：プラン生成後、完了済みを含め進捗を更新して再評価するB案。
- STEP4-⑨：**ログイン不要、ブラウザ内にイベント条件と進捗を保存し、同じブラウザで後日再開するB案**をユーザーが採用。サーバー同期／アカウントはMVP外。
- 4領域P01〜P12を基礎に、タスク内に詳細確認項目を表示する提案。判定契約と各タスク粒度は最終承認・検証前。
- 保存先の具体的なブラウザAPI（IndexedDB等）、利用ライブラリ、フレームワーク、ホスティングは**技術未決定**。

## 2. STEP4-⑪の推奨案（まだ利用者の最終採用前）

| 論点 | 推奨案 | 判断状況 |
| --- | --- | --- |
| イベント数 | 複数イベント保存。初回は一覧管理を意識させない | 提案 |
| 保存件数上限 | アプリ固有の件数上限は設けない。ブラウザ容量による制限は明示 | 提案 |
| 持ち帰り | ブラウザ保存・後日再開がMVP必須。印刷/PDF、ファイルエクスポート/インポートは後続候補 | 提案 |
| 主要画面 | Home／基本入力／準備プラン／タスク詳細・編集（独立画面か展開か未決） | 提案 |
| アカウント・共同編集・複数端末同期 | MVP対象外 | 保存方式の採用に整合 |
| タスクの進捗 | 未着手・進行中・完了・対象外。再確認は別フラグ | 詳細仕様の提案 |

**注意**：ブラウザ内保存はバックアップではない。プライベートモード・サイトデータ削除・端末変更などで失われる可能性がある。保存失敗を成功と表示しない。

## 4. 非機能要件（初期目標、測定前）

- NFR-01：タスク再計算は通常条件で1秒以内を目標。測定端末・条件未確定。
- NFR-02：保存成功・保存中・保存失敗を区別して表示。
- NFR-03：破損データ、移行失敗、複数タブ編集競合で黙って上書き・初期化しない。
- NFR-04：参加者の氏名・住所・連絡先やGPSは収集しない。任意メモには個人情報を入力しない案内をする。
- NFR-05：キーボード操作・文字拡大・状態の文字表示を想定。
- NFR-06：スマホ・PCで主要操作を実施可能とする。
- NFR-07：入力・判定ルール・進捗保存・UIを責務分離する。
- NFR-08：対応ブラウザとバージョンを技術選定・テスト計画で指定。

## 5. 受け入れ条件（実装後に検証。現状は未実施）

1. 基本6問で準備プランを生成できる。
2. 同条件・同進捗・同ルール版なら同じタスクと優先順位を生成する。
3. 未回答・本人が未定とした回答・作業の未着手を混同しない。
4. P01〜P12の適用条件に従い関連する準備を表示する。
5. 優先理由と次の具体的な行動を説明できる。
6. 進捗の変更後に残りの準備を再評価する。
7. 会場等の変更時に関連する完了済みタスクへ再確認を付け、履歴を残す。
8. 保存処理が成功した後だけ保存済み表示になる。
9. 再読み込み・後日の起動で保存済み情報を復元できる。
10. イベントを削除でき、削除に失敗した場合は成功表示をしない。
11. 対象外の施設固有情報を表示しない。架空の予約期限・法的判断を生成しない。
12. 保存容量、破損、スキーマ移行、複数タブ競合で不正な上書きを防ぎ、失敗を説明できる。
