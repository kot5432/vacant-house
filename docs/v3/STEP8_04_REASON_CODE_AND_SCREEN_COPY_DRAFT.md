# STEP8-④｜P01〜P12の理由コード・次の一歩・否定例（推奨設計、実装前）

作成：2026-11-16。ユーザーの「細かな設計は推奨で進めてよい」という委任に基づき作成。**文言・理由コードの名称は採用済みの中心価値に沿う推奨設計**であり、未決のP01〜P12の新しいP2/P1昇格条件を正式採用したものではない。重要な[ADR-027](ADR_027_P08_P2_NO_FACILITY_AUTO_ESCALATION.md)（P08施設固有条件では自動P1昇格なし）は正式採用済み。現行地域イベント準備支援Webアプリのみ。旧空き家関連の機能・資料は対象外。**実装・判定実行・実機試験なし。**

## 1. 表示理由の設計規則

- `reasonCodes`は**判断に使った入力とルール版**から導く安定ID、`reasonText`は利用者向けの説明、`nextAction`は本人が始められる確認行動。「P1だから危険」「P2だから義務」と表示しない。
- 情報不足時は「必要なことを確認しましょう」とし、未入力から法的・会場条件を決めつけない。
- 同じ入力・同じ評価日時・同じルール版・同じ出典版に対して同じ理由コードを返す。表示の文言が変わっても保存済みprogress/status/needsRecheckを勝手に変更しない。
- 施設固有出典は**公式情報の実際の対象範囲・有効状態を満たす場合だけ**出し、期限切れ・カテゴリ未選択では一般的確認へ戻す。
- P08は**P2基本、公式条件だけでP1自動昇格なし**。P05は未成年／両方=P1、成人／未定=P2。ほかの昇格候補は下記の「候補」であり新ADRではない。
- P01〜P12の「次の一歩」は**イベント開催を主催者本人が判断するための提案**であり、申請完了・法令適合・安全確保の認定ではない。

## 2. タスクごとの候補コードと説明

| ID | 推奨reasonCodeの例 | 説明（候補） | 本人が始める次の一歩 | 禁止する推測 |
|---|---|---|---|---|
| P01 | `CONTENT_NEEDS_CLARITY` / `CONTENT_GENERAL` | 目的・内容を整理します | 来場者に何を体験してもらうか一文にする | 説明欄が空＝企画失敗 |
| P02 | `AUDIENCE_UNDECIDED` / `AUDIENCE_GENERAL` | 参加対象と人数を考えます | 誰に来てほしいか、人数の目安を考える | 空欄人数＝0人・定員 |
| P03 | `SCHEDULE_UNDECIDED` / `SCHEDULE_MONTH_ONLY` / `SCHEDULE_GENERAL` | 時期と費用を整理します | 日付か月の目安、準備費用の項目を書き出す | 申請締切が開催14日前 |
| P04 | `RESPONSIBLE_UNDECIDED` / `ROLES_GENERAL` | 当日の運営体制を考えます | 責任者・緊急連絡の役割を確認する | 個人主催＝担当決定 |
| P05 | **`AUDIENCE_INCLUDES_MINORS` / `AUDIENCE_ADULT_OR_UNDECIDED`** | 参加対象に応じて安全・見守りを確認します | 安全上気になる点、当日の連絡方法を確認する | 必要なスタッフ人数・義務を算出 |
| P06 | `RUN_OF_SHOW_GENERAL` | 当日の進行と連絡を整理します | 受付から終了までの大まかな流れを作る | 日付だけでP1へ昇格 |
| P07 | `VENUE_UNDECIDED` / `VENUE_CANDIDATE` / `VENUE_CONFIRMED` / `VENUE_NONPHYSICAL` | 開催方法・会場の状況を整理します | 会場候補、利用できる場所・方法を確認する | 会場確定＝予約完了 |
| P08 | **`FACILITY_CONDITIONS_CHECK` / `FACILITY_SOURCE_MATCHED` / `FACILITY_SOURCE_STALE` / `VENUE_NONPHYSICAL_CONFIRM`** | **場所の利用条件を公式情報で確かめます** | 本人の対象となる施設・場所の公式ページ・窓口で確認する | **公式出典だけでP1自動昇格**、許可済み・申請必須と断定 |
| P09 | `EQUIPMENT_SPECIFIED` / `EQUIPMENT_UNDECIDED` | 備品・必要環境を確認します | 会場で使える設備と必要なものを照合する | 未回答＝備品不要 |
| P10 | `ANNOUNCEMENT_GENERAL` | 募集・告知の方法を考えます | 告知先、伝える内容を簡単に整理する | SNSを必須化、架空の募集締切 |
| P11 | `CONTACT_WITH_MINORS` / `CONTACT_GENERAL` | 参加方法と連絡方法を考えます | 参加希望者への案内と必要な連絡を整理する | 個人情報収集機能を勝手に追加 |
| P12 | `FINAL_REVIEW_GENERAL` | 開催前の確認を整理します | 当日の担当・持ち物・連絡方法を見直す | 開催日だけで完了扱い・14日前昇格 |

**`reasonCode`の英語識別子は設計用の名前候補**。保存する本人の進捗statusとは別。コード命名は将来の実装レビューで統一できる。文言には地域や日付の確定していない情報を含めない。

## 3. 優先度と該当性を混同しない例

| 条件 | 該当性・優先度（確定分） | 理由・画面文言 |
|---|---|---|
| `audience=minors` / `both` | P05 P1 | 「子どもが参加するため、見守り・安全の確認を優先しましょう」。実人数は推測しない |
| `audience=adults` / `undecided` | P05 P2 | 一般の安全確認。対象未定なら「確認」と示す |
| `venueStatus=no_physical_venue` | P08親`needs_information`・P2 | 「場所や開催方法に応じた利用条件を確認」。建物専用子項目のみ非該当 |
| 高岡市＋本人選択施設カテゴリ＋有効公式出典 | **P08 P2** | 対象となる公式リンク・確認日。P1にしない |
| 出典期限切れ／対象条件不一致 | **P08 P2基本** | 施設固有条件は表示せず、一般的な確認先 |
| P05・P08ともP2 | 同優先度はtaskId昇順 | P01〜P04など他の未解決項目も候補に含めたうえで代表を決める |
| P08本人`completed`かつ`needsRecheck=true` | 履歴は完了のまま未解決候補に残る | 「以前完了しましたが、条件変更のため再確認が必要です」 |

## 4. U03画面上の情報順（推奨・既存UIの範囲）

1. 「今回のイベント」：入力の要約と上限違反の注意があれば表示。
2. 「次に確認したいこと」：未解決の代表タスク**1件**、理由1文、本人ができる行動1文。
3. 「ほかの優先事項」：代表外のP1を省略しない。P1以外の未解決項目へも移動可能。
4. 「準備の全体像」：4領域・P01〜P12の状況。本人statusとアプリの優先順位、公式出典の有効性を独立表示。
5. 「確認先」：P08など関係するタスクに公式リンク・確認日・対象範囲。期限切れのときは一般的案内。
6. 「進捗保存状態」：変更処理の保存中／保存済み／失敗、別タブ競合を知らせる。自動の完了認定なし。

新画面や基本6問を追加しない。P1の順位と表示が変わる大きな変更は、利用者へ確認する。

## 5. 手動テスト用の追加ケース（設計のみ）

| ID | 入力と状態 | 期待される理由・否定例 |
|---|---|---|
| RC-01 | `audience=both` | P05 P1、子どもを含む理由、人数の断定なし |
| RC-02 | `audience=undecided` | P05 P2、確認が必要、子ども参加と断定しない |
| RC-03 | `no_physical_venue` | P08親P2、一般確認。オンライン専用規則は出さない |
| RC-04 | `venueStatus=confirmed` + facility source matched | P08 P2、公式リンク、許可済みとは言わない |
| RC-05 | source stale | P08 P2、施設固有断定しない |
| RC-06 | `schedule=month` | 開催日の正確な日付・申込期限を補完しない |
| RC-07 | optional attendance count absent | 0人とみなさず、人数目安の検討案内 |
| RC-08 | `eventDescription`が空 | 活動内容をAIで推測しない |
| RC-09 | `progress=completed` + `needsRecheck=true` | 完了履歴を残して再確認表示 |
| RC-10 | イベントのinputが上限超過でU03更新 | 元入力不変でprogressだけCAS保存、U04は修正が必要 |

**未解決の改善課題**：任意人数・設備・運営責任者の入力有無とP01〜P12の昇格候補に基づくスコアが利用者に納得されるかは需要・ユーザビリティ検証が必要。理由がない優先度を無理に作らない。公式高岡市等の原ページ実確認は未実施。
