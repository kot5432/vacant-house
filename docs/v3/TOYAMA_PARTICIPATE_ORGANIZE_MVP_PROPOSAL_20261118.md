# 富山特化「参加する・企画する」MVP設計 v0.1｜2026-11-18

> **状態：MVP採用に向けた提案／ユーザー承認前。実装・テスト・CI・デプロイなし。** ユーザーは「富山の地域活動を始めるハードルを下げる」方向を選択し、**主催支援＋参加側の独自性**を具体化するよう依頼した。既存U01〜U04、基本6問、P01〜12、正式ADR-001〜029は**現時点で変更しない**。本書は新機能設計案であり、正式採用ADRや実装開始許可ではない。

## 1. 取り組む課題と中心価値

**課題仮説**：富山で地域活動に関わりたい人の中には、参加先の情報を見つけても自分が参加できるか・どこから申し込むか分からず、主催したい人の中には、準備と地域の問い合わせ先を整理できず、最初の一歩で止まる人がいる。

**中心価値**：『富山で地域活動への最初の一歩が分かる』。参加側では初参加の判断材料・確認すべき情報・公式導線、主催側では条件に応じた準備順位・理由・高岡市などの確認先。参加者が必ず主催へ進むことをゴールにしない。

需要の証拠と未検証を区別：富山には実在の活動と支援制度、参加検索サービスがある（地域活動の存在の証拠）。**本サービスへの利用意向・初参加不安の内訳・主催希望者の行動変化は未測定**。

### 競合に勝てるとまだ言わない
- 「とやまちむすび」は地図・短時間の活動・ブックマーク・口コミ・フォロー/メッセージ・AI提案を提供。検索やAIマッチング自体は差別化にならない。https://apps.apple.com/jp/app/id6816786868
- 「サポナビたかおか」は市民活動ポータルとイベントカレンダーを提供。地域活動一覧を再制作するだけでは価値が薄い。https://saponavitakaoka.jp/ ／ https://saponavitakaoka.jp/calendar/
- 富山県「みんなのまちづくりカレッジ」は活動を始める個人を支援。https://www.pref.toyama.jp/140401/r8_machizukuricollege.html

## 2. 提案するMVPの境界（主催中心、参加小さめ）

| 機能 | MVP判定 | 完成に必要な条件 |
|---|---|---|
| 参加・企画の2入口 | 提案採用 | 自由に選べる。主催を強制しない |
| 参加：活動一覧 | 提案採用 | **高岡市中心の公開情報5〜10件程度を手動確認して初期登録できた場合**（数は開発・調査上の目安、利用実績ではない） |
| 参加：2つの絞り込み | 提案採用 | 開催地域と活動分野。参加条件で誤って除外しない。日付絞込はデータがそろえば追加 |
| 参加：初参加の判断カード | **参加の主役** | 参加資格/費用/日時場所/申込方法/初参加歓迎/単独参加可/所要時間/持ち物を、**確認済み・未確認・対象外**で区別。掲載元が未確認の値を生成しない |
| 参加：次の一歩 | **参加の主役** | 「公式募集ページで参加条件を確認」「主催者に問い合わせる」等、根拠ある公式リンクと未確認事項を提示。**参加可能保証・申込完了保証ではない** |
| 参加：公式ページへ遷移 | 提案採用 | 運営主体が確認できたURLのみ。アプリ内申込/チャットなし |
| 参加→企画への任意入口 | 提案採用 | 「自分でも企画したい」リンクのみ。参加履歴、個人プロフィール不要 |
| 主催：既存U01〜U04 | **維持** | 基本6問、P01〜12の順位/理由、進捗・CAS・JSON、既決ADRを改変しない |
| 主催：高岡市の公式情報 | **既存方針を重点強化** | 地域・施設カテゴリ・出典確認日・対象条件に合う場合のみ掲載。P08を施設理由でP1にしない |
| イベント投稿/共有、参加申込、ログイン、支払、DM、AI推薦、位置情報、口コミ、参加履歴、SNS | **MVP対象外** | 競合重複/運用・セキュリティ負担。ユーザーが後日新たに採用しない限り含めない |

**重要な縮小ルール**：開始前に確認済みの掲載イベントが少なければ「活動を発見する入口と公式ソースの案内」のみに縮小する。架空イベントや過去募集を現在募集中と偽って5〜10件に水増ししない。

## 3. 画面とユーザーフロー：既存U01〜04をリネームしない

```text
D00 入口（参加してみたい / 自分で企画してみたい）
  ├→ D01 活動を探す（地域＋分野で絞込、確認済みのみ）
  │      → D02 活動詳細（参加前の判断カードと根拠・更新状態）
  │           ├→ 運営元の公式案内へ（アプリ外）
  │           └→ 自分でも企画してみる → U02
  └→ U01 既存イベント一覧（主催支援の既存Home）
             ├→ U02 既存基本6問 → 保存成功 → U03準備プラン
             └→ U03保存イベント → U04編集
```

- `D00/D01/D02`は今回だけの**仮画面ID**。現在のU01/U02/U03/U04の意味・既存ADRを変えない。
- U01から参加側へ戻れる全体ナビを追加する想定だが、具体のUI配置、文字サイズ、ボタン色等は実装段階の比較に委ねる。
- **D02→U02**は通常の新規作成を開く。参加活動の情報で初回6問を**自動入力しない**。活動分野と主催イベント種別を推測結合しない。
- 参加側はログイン不要・参加事実の記録不要・申込情報は収集しない。

## 4. 参加データの設計（主催EventRecordと絶対に混ぜない）

```text
ParticipationListing (静的公開データ、案)
  listingId: 内部の固定文字列（実際の施設名・URLで自動生成しない）
  title: 公開情報にある正式の活動名
  organizerName: 運営元の公開名
  area: 市町村・地区の確認済み値（不明なら非表示/不明）
  categories: [] / 定義した活動分野タグ
  scheduleLabel: 開催日時または「定期/随時」、出典が正確なら記載
  participationFields: {
    eligibility, fee, duration, soloWelcome, firstTimerWelcome,
    registrationMethod, belongings, locationDetails
  }
  sourceUrl: 公式の具体的な活動/募集ページURL
  sourceOwner: 出典運営者・団体
  lastVerifiedAt: 実際に元ページを人が確認した日
  recruitmentState: open | closed | unknown（公表/確認できないならunknown）
  recordStatus: verified | needs_review | archived
```

**各フィールド**は`{state:"confirmed", value, sourceUrl, verifiedAt}`または`{state:"unknown"}`または`{state:"not_applicable"}`とする**技術案**。absence/unknownを「参加できる」「歓迎」「無料」に変換しない。`soloWelcome/firstTimerWelcome`は**未記載ならunknown**、推定して「ひとりOK」と出さない。

**運用境界**：参加データは`src/domain/participationCatalog/`等のビルド同梱の公開カタログという設計案。利用者自身の企画・進捗は既存Dexie/IndexedDB。参加カタログを本人のJSONバックアップに混ぜない。新API/スクレイピング/第三者への投稿機能は導入しない。公式情報をコピーする場合は必要最小限にして、長い原文・写真は転載しない。

**更新と期限（採用前の方針案）**：
1. 掲載候補は運営元の一次ソース（団体/自治体の告知）を確認して登録。転載サイトだけでは断定しない。
2. 確認日と出典URLを内部記録し、参加詳細でも出典と「情報は変わる可能性」を示す。
3. 定期イベントと単発イベントを区別。過去日が確定している単発は**現在募集中として表示しない**。更新確認ができない募集は「募集状況未確認」にし、要確認の案内のみ。
4. 主催側の静的公式出典のJST月末レビュー（ADR-011/012）を**参加募集の自動期限/法的有効性と同一視しない**。参加データは独立した公開カタログ版と確認日で運用する。
5. 掲載元サイトがアクセスできなくなったら確認済みの現在募集として表示しない。元イベントの参加資格を勝手に修正しない。
6. 公開前に掲載先の権利条件、URL、安全な外部遷移、掲載訂正窓口を検討。個人の非公開連絡先や非公開住所を保存しない。

## 5. 参加側の「最初の一歩」導出（独自性候補）

表示は参加資格の適合スコアや本人向けの「参加可能」認定ではなく、**確認できたことと、確認すべきことを区別する整理**。

優先順位（案・非自動申込）：
1. 募集終了が確実なら「募集終了」と表示し、申込導線を積極提示しない。再募集があるとは推定しない。
2. 開催が過去または確認日が古く状況不明なら「最新の開催・募集状況を公式情報で確認する」。
3. 応募条件・対象年齢・費用が不明なら「参加条件/費用を公式情報で確かめる」。年齢に関する安全な条件を推測しない。
4. 参加申込方法が公開済みなら「公式ページで申込方法を確認する」。ページが単なる説明なら「主催元に開催/参加方法を問い合わせる」等の実在根拠ある案内に限定。
5. 情報がそろい応募受付中と一次ソースで確認できても**参加可能・空席あり・登録完了を断定しない**。

**次の一歩は1つ示すが、確認事項と公式リンクを同時表示**。利用者をログイン/個人情報入力に誘導しない。外部サイトに移動した後の申込は各運営元の責任範囲。

## 6. 参加から主催への接続（価値仮説・採用前）

D02または参加側トップに**任意**の「自分でも小さく企画したい」入口を設ける。U02の基本6問へ。誰かが参加したかどうかは判定しないし要求しない。参加活動のタイトル/対象者を本人のイベント計画へ無断コピーしない。

**差別化候補**：
- 参加：推薦・地図ではなく**初参加の判断材料の不足と確認行動を透明に表示**。
- 主催：一般タスク生成ではなく**P01〜P12状況別の優先度/理由 + 高岡市の有効な一次情報への確認導線**。
- 両者：富山で地域活動へ関わる行動を**「次の一歩」**に統一。ただしこれが実際に便利かは利用者による競合比較が必要。

## 8. コンテスト用の説明と実証設計

**課題説明**：富山には活動の場と行政・団体の公開情報はある。しかし初めて参加・主催する人が、必要な情報を自分の状況で読み解き、次の行動を決めるには負担があるという仮説。

**技術の見せ方**：1) 参加カタログの出典・鮮度・未確認項目を分けた決定的な次の一歩の提示、2) 主催6問→P01〜P12優先順位＋地域ソースの条件照合、3) 状況変更後の再確認と安全な保存。AI推薦やSNS機能の量で勝負しない。

**需要検証**（未実施、対象2群を分ける）：
- 初参加希望者：実在の活動案内と従来ポータル vs D01/D02設計案で、参加条件・最初の行動を説明できるか。
- 初主催希望者：行政ページ＋通常チェックリスト vs U02/U03設計案で、最初の準備・確認先を説明できるか。
- 比較では出典情報・制限時間を統一し、誘導質問「便利ですよね？」を避ける。例：成功定義「本人が次の一歩を自分の言葉で説明できる」、所要時間、誤解件数、主観評価。
- 参加→主催への移行は**仮説**。実際に主催者へ転換した実績を測定なしに主張しない。

## 9. 採用前の判断・開発負担とリスク

### MVP追加を認めるためのゲート
- 高岡市付近で**一次ソース・更新日が確認できる実際の地域活動が数件確保可能**か（募集中を断言するにはその日の確認が必要）。
- 高岡市以外の富山県内をどう扱うか（本MVPは「まず高岡市中心」、他市を完全対応したと宣言しない）。
- 参加詳細に掲載できる情報が不足した場合でも、公式リンクと確認事項だけで利用価値があるか。
- 4人初心者の開発負担を考慮し、既存U01〜U04品質を落とさないか。
- 元資料の権利・公開可否・過去イベント表示の保護・外部リンク表示。
- 本人の入力・参加希望条件を新たにサーバーへ送らないこと。

### 不採用候補
イベント投稿、主催者プロフィール/DM、会員登録、参加申込/決済、AI推薦、ランキング、GPS、口コミ、参加履歴・実績、SNS、ポイント、複数自治体一括スクレイピング。初回MVPの「主催準備の説明可能な判定」という核を壊さない。

### 既存設計への影響
- **現時点で既存ADR/Issue #1〜13の採用値は変更しない**。新規`D00〜D02`は設計案。
- 一覧の公開カタログは主催者の個人EventRecordと別、既存JSON形式に追加しない。
- 本MVPの追加決定後、別途正式ADR・新Issueを作成し、主催側と参加側の依存境界だけを修正する。
- 本資料はアプリの動作、実証、出典掲載承諾、施設の予約可否、参加受付可否を保証しない。
