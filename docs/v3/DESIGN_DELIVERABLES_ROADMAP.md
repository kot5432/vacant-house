## 2. 確定事項・提案・未決事項の区別

### 利用者が採用した方針
1. STEP1：初回の単発・小規模非営利イベント主催者を対象とする。
2. STEP2：準備全体像と状況別の優先順位を中心価値とする。
3. STEP3：基本6問→暫定プラン→任意の詳細化→持ち帰り。入力項目の選択方式は [STEP3_MVP_BOUNDARY.md](STEP3_MVP_BOUNDARY.md) が正本。本人が今困っていることは追加質問しない。
4. STEP4-⑥（2026-11-14）：**B案「準備プラン生成後に、利用者が完了済みの作業や進捗を確認・更新し、未完了タスクと優先順位を再計算」**を採用。初期入力に進捗質問を増やさない。

### STEP4-⑥の詳細設計（会話で提示した仕様案。実装・テスト未実施）
- ルールベースで、共通／条件付き／確認タスクを抽出。安全・開催可否、確認済み期限、依存関係、着手しやすさにより3段階で優先付け。
- 進捗候補は未着手／進行中／完了／対象外。入力変更時は適用条件と優先度を再評価し、完了履歴は勝手に削除しない。会場変更などのときには「再確認が必要」を別フラグで表す。
- 初回生成時に「入力した条件が確定している」と「準備作業が完了した」を混同しない。申請期限・施設利用可否・安全性を推測で断定しない。
- 8件の架空テストケースについて期待結果を文章で検討したが、**動作テストではない**。
- **旧STEP4との整合要確認**：既存 [STEP4_INPUT_OUTPUT_EVIDENCE.md](STEP4_INPUT_OUTPUT_EVIDENCE.md) は「4領域12項目（P01-P12）」の最終承認前の案。一方、新たな会話では「6カテゴリ／T01-T12」の整理例を提示している。**両方を確定仕様と扱わない。**次の詳細設計で分類・ID・重複・優先ルールを一本化するまで、既存P01-P12の置き換えや削除を行わない。

### 重要な未決事項（混同禁止）
- **進捗更新の範囲**：STEP4-⑥ B案は「生成後の状態変更」を確定したもの。以前のSTEP3-①「一回の利用で作成・持ち帰り／継続管理なし」を自動で撤回するものではない。**同じ利用中だけ更新するか、端末保存して後日再開を可能にするか、サーバー同期するかは未決**。後日管理やアカウント機能を勝手にMVPへ追加しない。
- 4領域12項目か6カテゴリ12タスクかの最終タスク体系、UI詳細、期限情報の扱い、持ち帰り形式。
- フロントエンド、言語、状態管理、DB・保存先、認証の要否、デプロイ方式、Cloudflareなどの具体サービス、テスト基盤、ライブラリ。**過去に候補として挙がったホスティングも採用済みと断定しない**。
- チームの役割、実装日程、地域情報の更新責任、需要の実証、受入試験。

## 3. 作成する設計成果物（9点＋共通台帳）

| 成果物 | 最低限含む内容 | 作成するタイミング |
| --- | --- | --- |
| 01 プロダクト定義書 | 対象者・課題・価値・対象外・MVP・需要仮説 | タスク体系を確定する前後でv1 |
| 02 要件定義書 | 機能／非機能要件、ユースケース、受入条件 | タスク体系・利用範囲を確定後 |
| 03 機能詳細設計書 | 入力、条件分岐、タスク、優先度、進捗、例外 | 次のSTEP4-⑦以降で段階的に |
| 04 画面設計書 | 画面一覧、状態、画面遷移、UI、アクセシビリティ | 機能の入出力契約が固まった後 |
| 05 技術選定書 | 候補比較、採否理由、コスト、開発体制との適合 | 非機能要件・保存範囲を確定後 |
| 06 アーキテクチャ設計書 | 構成図、責務、データフロー、境界、セキュリティ | 技術選定とデータ保存方式決定後 |
| 07 データ設計書 | エンティティ、状態遷移、タスクID、スキーマ、保持方針 | 進捗・保存範囲確定後 |
| 08 テスト設計書 | 単体・結合・画面・異常系・境界値・回帰と期待結果 | 機能仕様確定時から追記 |
| 09 開発・運用計画書 | AIコーディングと人のレビュー分担、段階、公開、根拠更新 | 開発着手の判断前に完成 |

共通台帳として **決定ログ、未決事項、変更履歴、用語集、参照する正本の一覧** を維持する。設計途中の資料には「確定／提案／未検証／廃止」を付ける。資料を完成済みと偽らず、決まった部分から順次作成する。
