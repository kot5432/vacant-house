# STEP7-⑫｜同じJSONバックアップを繰り返し取り込む際の扱い（選択肢・未決）

作成：2026-11-15。**利用者確認待ち**。既存eventId衝突時はバックアップ側を別の一意IDでコピー追加するA案を[ADR-016](ADR_016_IMPORT_COLLISION_AS_COPY.md)で正式採用済み。本書は「同じバックアップを繰り返し取り込んだときの追加コピー」に関するUI／技術判断であり、既決の別ID複製を否定しない。現行地域イベント準備支援Webアプリ専用。旧空き家データは対象外。実装・試験・デプロイなし。

## 1. 問題設定

例えば、保存済みイベント2件をバックアップし、一度インポートした後に同じファイルを再びインポートすると、元のeventIdがDB内に存在するため、ADR-016のルールどおり**さらに別コピーが増える**。利用者が意図せず繰り返した場合はU01のイベント一覧が見分けにくくなる。

同じイベント名・内容でも別のイベントである可能性がある。**タイトルや本文が一致しただけで「同じファイル」「復元済み」と断定しない**。内容が同一でも本人の進捗が異なる場合がある。

## 2. 3つの案

| 案 | 同じバックアップの再取込み | 長所 | 短所 |
|---|---|---|---|
| **A（推奨）** | **毎回プレビューに新規追加件数・別IDコピー件数と重複の可能性を警告し、本人が明示確定すれば追加**。特定ファイルの既取込み履歴はMVPでは追跡しない | 既決のコピー追加と矛盾せず、軽量で単純。本人が必要なら何度でも復元可能 | 「以前読み込んだ同じファイル」との厳密判定はできない |
| B | **インポート済みファイルのハッシュをローカルで保持**。同一内容を再選択した場合は強めの警告・追加確認の後で複製を許可 | 意図しない再取り込みに気づきやすい | ローカル取込履歴、ハッシュの互換性、データ消去・別端末での判定、履歴削除の設計が増える |
| C | **同一ファイルだと判断できる場合は二度目の取込みを拒否** | 重複増加を防ぎやすい | 意図して再復元したい場合も拒否。ハッシュ・履歴管理が必要 |

**推奨A**：初期MVPでは「何件が新規追加され、何件がコピーになるか」を必ず伝え、追加の本人確認を確実にする。ファイルを2回読み込んだという厳密な記録を持たなくても、既存データを壊さない安全契約は成立する。

## 3. 全案共通の既決仕様

- ファイル内部の同じeventIdは**入力エラーとして全件取込み拒否**。同じeventIdを持つ既存DBとの衝突とは別。
- **別IDコピーと既存イベント不変**、プレビュー後の衝突分類変更で再承認、保存失敗は全件ロールバックを維持。
- 同じ名前・説明を持つイベントは区別がつかないため、コピー後の表示に「復元したコピー」等の情報を付ける方法は今後UIで具体化する。
- 読込件数、コピー追加件数、現在の既存イベント件数を本人が確認できるようにし、アップロード／ファイル選択だけで保存しない。
- コピー元のJSONの`rulesVersion`や古い出典の`verified`状態を公式な確認済みと扱わない。

## 4. A案採用時の受入期待（未実行）

| ID | 操作 | 期待 |
|---|---|---|
| REPEAT-01 | 1回目の復元 | 件数プレビュー→本人確定→全件追加 |
| REPEAT-02 | 同じファイルをもう一度選択 | 追加・コピーになる件数を再表示し、本人が確定するまではDB不変 |
| REPEAT-03 | 本人が2回目の確定を選ぶ | 既存イベント不変、コピーが独立IDで増える |
| REPEAT-04 | 2回目のプレビューでキャンセル | DB無変更 |
| REPEAT-05 | 同じタイトルで進捗の異なるイベント | 題名一致だけを理由に誤検知・取り込み拒否しない |
| REPEAT-06 | 既存タブがプレビュー後にデータ追加 | 衝突分類差分があれば再プレビュー・本人再確認 |

## 5. 確認事項

**繰返し取込みはA案（毎回件数と重複可能性を明示して本人承認）／B案（ファイルハッシュ履歴で強い警告）／C案（同一ファイル再取込み禁止）**から選ぶ。推奨A。ユーザーが選ぶまでローカル取込履歴や自動スキップをMVPに正式追加しない。
