# STEP10-⑨｜ADR-031親タスクのみ採用後の保存・JSON・U03差分設計

日付：2026-11-18。**設計のみ。実装・テスト実行・デプロイなし。** 正本は[ADR-031](ADR_031_PARENT_TASK_PROGRESS_ONLY_NO_CHILD_CHECKS_ADOPTED.md)。旧資料の子チェック案は今回採用されない。

## 1. データ差分

| 対象 | 以前の草案 | 今回の初期MVP |
|---|---|---|
| 親進捗 | P01〜P12 status | **維持** |
| 子進捗 | `checkedItemIds:string[]` | **初回v1から除外**。空配列としても残さない |
| 本人の状態 | `not_started/in_progress/completed/not_applicable` | 維持 |
| 再確認 | `needsRecheck: boolean`と`recheckReasonCodes` | 維持。理由コードの厳密enumは別レビュー |
| 優先度 | P1/P2/P3、該当性、理由 | **入力・公式出典から導出し保存しない** |
| 設備入力 | `equipmentNeed` と任意`equipmentCategories` | 子チェックではないため別途継続。category enumは未決 |
| 公式出典 | 本人保存から独立した静的カタログ | 維持 |
| 参加活動 | 静的読み取り専用カタログ | 主催JSONへ入れない |

**最小の親進捗イメージ（説明用・厳密JSON Schemaではない）**：

```json
{
  "progressByTask": {
    "P05": {
      "taskId": "P05",
      "status": "completed",
      "needsRecheck": true,
      "recheckReasonCodes": ["<reviewed-code-pending>"],
      "updatedAt": "2026-11-18T20:00:00+09:00"
    }
  }
}
```

`<reviewed-code-pending>`は**有効な保存値ではないプレースホルダー**。実際のデータとして利用しない。完全なrequired/optional仕様と再確認コードの固定が済むまでJSONサンプルを合格用のfixtureと呼ばない。

## 2. 画面ごとの仕様差分
- **U01**：従来の一覧・再開・削除・JSONバックアップUIは維持。「24子項目の達成率」「子チェック済み件数」を表示しない。12親タスクの完了状況を出すなら完了/対象外の区別と分母規則を別途明示。
- **U02**：基本6問・条件付き任意入力・初回下書きの扱いは従来通り。子チェック入力を追加しない。
- **U03**：P01〜12の4領域・代表タスク・理由・次の一歩・公式出典・保存状態を維持。各親タスクに本人が選べる進捗状態（未着手/進行中/完了/本人対象外）と要再確認を示す。詳細は**説明/確認先のみ**でチェック操作なし。P05がP1なら他のP2より優先。P08はP2。再確認の明示解除は親単位。
- **U04**：主催条件の明示編集・キャンセル・CASを維持。変更前後の条件が本人の過去の確認に影響する親のみ要再確認。子チェックの保持/切捨てや表示移行は発生しない。
- **D00〜02**：参加側UIは影響なし。D02の参加条件表示にチェック操作を足さない。

## 3. バックアップ仕様
- `BackupEnvelope.formatId="toyama-community-event-prep-backup"`、`exportSchemaVersion=1`、イベント`schemaVersion=1`はADR-029どおり。**まだ実装・公開された子チェックありのv1は存在しない**という現時点の前提で、初回公開前に正規schemaを揃える。
- 新規保存・JSON出力では`checkedItemIds`を書かない。インポートでは現在の正規schemaに含まれない`checkedItemIds`を無視して「成功」としない。対応旧形式なし、実データが見つかった場合は移行を別途判断。
- JSON完全体は原子検証・プレビュー→承認→原子的追加。件数とByte上限・重複eventId・未知schema・元日時検証は一切変更しない。
- `recheckReasonCodes`は残すため、**永続コードの有効値の凍結が必要**。優先度表示用の`reasonCode`とは別である。
- `progressByTask`未登録タスクはUI上「未着手」として扱う既存設計を維持し、未操作タスクを自動で一括書き込まない。
- 12タスクがすべて完了したからといって許可済み/安全確保済みと表示しない。

## 5. 実装責務への影響
- A（型・判定）は`checkedItemIds`の登録/検証と24子IDを**生成しない**。親進捗と再確認コードは設計維持。
- B（画面）は子チェック用UI/件数表示/子項目の展開操作を作らない。タスク詳細の理由・次の一歩は維持。
- C（保存・JSON）は子チェックを保存せず、`schemaVersion=1`の仕様を統一。旧データが存在した場合は無断削除ではなく未対応として停止。
- D（出典・品質）は子チェック用受入ケースを削除し、12親の期待ケース・未確認の扱いに置換。
