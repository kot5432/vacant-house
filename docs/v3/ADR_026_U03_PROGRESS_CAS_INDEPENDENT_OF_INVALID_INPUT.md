# ADR-026｜U03進捗更新は旧入力を保持して独立CAS保存（A案正式採用）

決定日：2026-11-15。利用者が[STEP8-①](STEP8_01_CORE_VALUE_RULES_AND_LEGACY_PROGRESS_REVIEW.md)の**A案**を明示採用。また「原則は推奨案を継続、中心価値・大きな変更のみ都度確認」の設計委任を受領した。対象は現行の単発・小規模地域イベント準備支援Webアプリ専用。旧空き家・物件・所有者・マッチング仕様は一切対象外。**設計のみ。実装・試験実行・デプロイなし。**

## 1. 正式な決定

- 既存EventRecordの入力が現在のUnicode書記素／UTF-8バイト数の上限を超えていても、**U03の本人のタスク進捗（P01〜P12）と明示的な再確認解除を、入力のU04全体保存とは別のコマンドで保存できる設計**とする。
- **イベントの入力文字列・施設メモ・説明、入力schema、createdAt、由来情報は進捗更新によって無断で変更しない**。古い入力の上限違反を理由に進捗・再確認を自動初期化しない。
- **既存イベントの存在確認＋該当イベントの最新revisionを照合するCAS**を採用。進捗更新の成功時にrevisionを1つ進め、updatedAtは保存成功時の更新日時へ（createdAtは不変）。他タブが途中で更新していた場合、上書き・無言マージをせず競合として扱う。
- 更新するのは**対象taskIdの進捗フィールドおよび本人の明示操作で変化する再確認フィールド**。既存の他タスクの進捗、needsRecheck、recheckReasonCodesや元の入力は不変。対象タスクID・進捗enum・保存される構造・既存schemaの対応可否は検証する。無効な保存データを強制変換・捏造しない。
- **再確認解除**は[ADR-004](ADR_004_EXPLICIT_RECHECK_CLEAR.md)どおり「再確認を終えた」の明示操作があり、**CASトランザクションがコミット成功した後だけ**確定。画面表示や通常の進捗変更だけで勝手に解除しない。
- **U04の入力編集**は[ADR-025](ADR_025_LEGACY_OVERSIZED_RECORD_READ_ONLY_UNTIL_FIXED.md)どおり本人が不適合テキストを上限内へ修正して入力全体の保存検証を通るまで保存できない。U03が保存できることとU04が保存できることを区別する。
- **バックアップ**はADR-025どおり不適合入力があるイベントのエクスポートで全選択対象の書出しを停止し、インポートは不適合イベントが1件でも含まれるなら全件拒否する。U03進捗保存成功をもってそのイベントがバックアップ可能になったとは扱わない。
- **アプリ側で「データ保存済み」と表示するのはIndexedDB書込み成功後のみ**。端末のサイトデータ削除・ストレージ消去や端末故障に対する永久保証はしない。

## 2. 論理トランザクション（実装コードではない）

```text
U03: 本人がPxxの進捗変更 / 「再確認を終えた」を明示操作
→ イベントIDと期待revision、タスクID、変更内容を引数として保存要求
→ 同一Dexie readwriteトランザクション内で現在のEventRecordを取得
    ├─ 不在・未知schema・未知taskId・無効な進捗値 → 保存拒否
    ├─ revision不一致 → 競合を返して保存中断、DBを変更しない
    └─ revision一致 → 入力・他タスク・他メタデータを維持し
           対象progressByTask項目のみ必要な変更
           revisionを1増分、updatedAtを保存時刻に更新
→ トランザクションコミット成功後にだけU03表示を「保存済み」へ
→ 失敗・別タブ競合 → 元DB不変、未保存操作の再確認や再試行を案内
```

**実装レビュー**：更新するオブジェクトはDB上の現在値を基に扱い、古い画面のEventRecord丸ごと`put`で別タブの入力や他タスクの進捗を上書きしない。実際のIndexedDB/Dexieの原子性、同一レコードCAS、ブラウザ非同期処理は実機試験で検証する。

## 3. U03画面の振る舞い

- 「入力項目にサイズ上限を超える内容があります。内容は削除されていません。入力編集は修正が必要ですが、準備タスクの進捗は記録できます」と**状態を区別して表示**する。
- U03進捗の変更は通常の既定どおり自動保存を試みるが、保存中／保存済み／失敗を分ける。処理が失敗したら「保存できませんでした。進捗を再確認してください」を表示し、保存済みだと偽らない。
- 他タブとの競合を検知したら「別の画面でイベントが更新されました。最新の記録を確認してください」とし、既存タスクの進捗を無言で上書き・併合しない。
- `needsRecheck`の理由と本人の完了・対象外状態を同一にせず、明示の再確認解除後も本人のprogress.statusは保持。公式出典`needs_review`はさらに別の状態。

## 4. 受入テスト（設計のみ・全件未実行）

| ID | ケース | 合格条件 |
|---|---|---|
| U03-CAS01 | 施設名メモが4,097バイトの既存イベントでP01を完了 | P01のみ保存、メモと他タスク・createdAtは不変、revision+1 |
| U03-CAS02 | 入力違反のあるイベントのP02を保存 | U04での入力保存は引き続き修正前不可 |
| U03-CAS03 | P05完了済みでneedsRecheck=true、単に閲覧 | 再確認が解除されない |
| U03-CAS04 | 本人がP05「再確認を終えた」を選択し保存成功 | P05のneedsRecheckがfalse、完了履歴は保持 |
| U03-CAS05 | 明示再確認解除の保存が失敗 | 再確認済みと確定表示しない。DBのフラグはtrueのまま |
| U03-CAS06 | 別タブでU04を保存しrevisionを変更 | 古いU03操作は競合で停止し、入力を上書きしない |
| U03-CAS07 | 別タブでイベントを削除 | U03更新がイベントを再作成しない |
| U03-CAS08 | 別タブで別タスク更新 | stale revisionで上書き禁止、本人へ再確認 |
| U03-CAS09 | 1イベントに未知schema／未知taskId | 不正更新を拒否し旧DB不変 |
| U03-CAS10 | 入力上限超過のままバックアップ書出し | U03保存の成否と無関係にADR-025の書出し停止条件を維持 |
| U03-CAS11 | 進捗を押してIndexedDB保存が容量不足 | UI上「保存済み」にせず競合・失敗を区別 |
| U03-CAS12 | PC・スマホの連続タップ | 保存順・revisionの競合を正しく扱い進捗を黙って失わない |

## 5. 推奨案へ進める委任と大きな変更の境界

**ユーザー確認なしに進められるもの**：既存の基本6問・P01〜P12・U01〜U04・ADR-001〜026に沿う説明文言、無推測のルールテスト化、UIの注意表示、状態遷移の明確化、レビュー資料更新、未採用の14日前閾値の排除等。これらは既決と整合する**設計推奨**として進め、未承認の新機能・ルールを「正式決定」と偽らない。

**大きな変更として確認が必要**：対象利用者の変更、基本6問またはタスク集合の追加削除、P1/P2の広範な再優先づけ、法的手続きや安全の必須判定、本人の進捗自動初期化、データ消去・外部送信・アカウント・同期導入、MVP大幅拡大、公開・実装への着手など。

次は[STEP8-② P01〜P12の中心価値ルール監査](STEP8_02_RULES_CORE_VALUE_AUDIT.md)で現行ルールをレビュー。これ自体は新しいルールの一律正式採用ではない。
