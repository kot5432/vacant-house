## 1. 出典管理の主な役割（担当者氏名は未決）

| 役割 | 責務 | 原則 |
|---|---|---|
| 出典確認担当 | 公式原ページを直接開き、発行元・施設・改定日・適用範囲・リンクを記録 | AI生成の要約だけを根拠に`verified`にしない |
| レビュー担当 | 異なるメンバーが出典・表示文言・対象条件・コード差分を照合 | 公式情報を確認できない場合は承認しない |
| リリース担当 | Vercel Previewで確認し、本番デプロイと案内を管理 | 本番への更新権限とレビューを分離 |
| 連絡・誤案内対応担当 | 誤案内報告をGitHub Issue等へ記録して一次対応する | 個人情報を含む報告の公開に注意 |

一人が兼任する場合も、施設固有の**適用条件と出典の2人目レビュー**を推奨。初回のメンバー・権限設定は開発前に合意する。

## 2. いつ確認するか：推奨運用サイクル

| トリガー | 実施内容 | 具体的な頻度案 |
|---|---|---|
| 初回出典登録 | 原ページと対象施設条件を照合 | 掲載前必須 |
| 本番リリース前 | 全`verified`出典のURL・内容・対象条件を点検 | **毎リリース前** |
| リリースがない期間 | リンク切れ・改定有無・重大注意を確認 | **月1回**を推奨。負担次第で見直す |
| 公式情報の変更を把握 | 台帳を`needs_review`にし影響を判定 | 気づき次第 |
| 誤案内・施設側からの訂正 | 対象表示を停止し、確認担当へ回す | **対応優先**。24時間などの保証は置かない |
| 出典を再確認できない | `needs_review`／`suspended` | 再確認まで施設固有の断定文を止める |

**月1回は正式採用前の提案**。施設ごとの改定頻度、チームの稼働、出典数によって調整する。

## 4. 変更時の工程

1. 出典変化を発見→台帳ステータスを`needs_review`、明らかな誤案内は`suspended`。
2. 旧新資料の違いを比べ、適用条件・必要確認内容・表示の理由を記録。
3. 対応するPxxだけの出典・判定・再確認の必要性を検討し、対象外のタスクに広げない。
4. 2人目が確認。問題なければ`verified`へ戻す。
5. Vercel Previewで対象条件と**非対象条件**の表示テスト。対象施設以外へ文言が漏れないか試す。
6. 本番デプロイ後、掲載URLとアプリ出典版を確認。古いタブを開いたままのユーザーへ即時反映を保証しないため、版更新と再読み込み案内を検討。

## 5. 出典に問題がある場合の画面上の対応

- `verified`＆本人の条件が合致：出典名・確認日・URL・対象施設の範囲を表示。
- `needs_review`：個別の申請期限や許可条件について**断定しない**。一般的な「管理者の公式ページで確認する」案内。
- `suspended`：当該施設固有の案内を停止する。ほかの出典を自動流用しない。
- `retired`：表示対象から外す。過去の本人の進捗を消さない。
- 公式ページの閉鎖・リンク切れ：検証まで`verified`のままの案内をしない。

## 6. 版管理とブラウザ保存の難点

アプリはローカルブラウザのIndexedDBにイベントを保存する。出典の確認日や改定結果のサーバー配信による強制反映は**採用されていない**。静的アプリが古い状態で開かれている場合、更新後の公式情報がすべての利用者の画面へ即時伝わるわけではない。出典の更新に伴う再確認は、ユーザーが新しい版を読み込んだ後のルール／出典版差分から計算する想定（実装仕様と検証は今後）。

## 7. 公開・レビューの受け入れ条件（未実行）
