## STEP9｜判定・優先順位の整合検査（設計上の期待結果）

入力正本は基本6問：`eventType`、`audience`、`date`（他資料のscheduleと同一の1問）、`venueStatus`、`region`、`organizerForm`。追加の任意入力に`responsible: Known<decided|not_decided>`、`equipmentNeed: Known<yes|none_identified>`、人数等がある。未回答・未定・回答済みを区別する。自由記述を自動分類しない。

| タスク | 優先順位の確定した境界 | 禁止する推測 |
|---|---|---|
| P01 | eventType=otherのみP2、その他P3 | 自由記述からイベント種別を断定 |
| P02 | audience=undecidedのみP2、その他P3 | 人数未回答から自動昇格 |
| P03 | date=month/undecidedならP2、その他P3 | 月を月初日に補完、14日前の閾値 |
| P04 | organizerForm=undecidedまたはresponsible=answered/not_decidedならP2、その他P3 | responsible未回答を「未決定」とみなす |
| P05 | minors/both=P1、adults/undecided=P2 | 法的な危険・許認可の認定 |
| P06 | P3 | 日数や人数による自動昇格 |
| P07 | venueStatus=undecided/candidateならP2、その他P3 | confirmedを予約・許可済みと断定 |
| P08 | 原則P2。no_physical_venueでは親をneeds_informationのままP2 | 施設の公式条件一致だけでP1に昇格 |
| P09 | equipmentNeed=answered/yesのみP2、その他P3 | 未回答・none_identifiedを「必要なし」と確定 |
| P10〜P12 | P3 | 開催直前だから自動昇格 |

※ 具体的な該当性・子項目・出典条件は既存の判定契約を参照し、この一覧を唯一のルールとして実装しない。P07〜P09の「物理会場なし」は親の一般確認を残し、建物固有の子項目だけ非該当。

**順序・進捗の検査契約**：
1. `applicability`、`priority`、`userProgress`、`needsRecheck`、`sourceStatus`を別値として扱う。
2. 未解決代表候補はP1→P2→P3、同じ区分ではtaskId数値昇順。複数P1を省略しない。
3. completed/not_applicableで再確認不要なら代表候補から外す。completedでneedsRecheck=trueなら候補へ戻し、完了履歴は残す。
4. 優先度再計算は本人進捗・revision・完了日時・出典状態を書き換えない。
5. 公式出典の失効は施設固有の断定を止めるだけで、一般タスクや本人進捗を消さない。

**設計レビューの代表境界ケース**：
- minors、P05未着手：P05=P1。他のP2より先。ほかのP1はすべて表示。
- adults、P05/P08が未着手：両方P2ならP05→P08の順。ただし他に小さいIDのP2があればそれが先。
- responsible未回答・organizerFormが確定：未回答だけを理由にP04=P2としない。
- venueStatus=no_physical_venue：P08親P2/needs_information、建物固有子項目は非該当。
- equipmentNeed=answered/yes：P09=P2。none_identifiedまたはunansweredならP3。
- P05完了でneedsRecheck=true：完了履歴を保持して未解決候補へ。
- 利用者が会場を変更：影響する施設固有情報と再確認だけを既決ルールに従って更新、無断の一括進捗消去なし。

既存[STEP8-⑲](STEP8_19_ACCEPTANCE_CASES_AND_EVIDENCE_TEMPLATE.md)のRULE-F01〜F14と照合すること。これは期待値の再記述であって**試験PASSの宣言ではない**。

## STEP10｜画面と操作：引き継ぎ時の検収ポイント

| 画面 | 主目的 | 必須表示・遷移 | 失敗時 |
|---|---|---|---|
| U01 | イベント一覧・バックアップ | 複数保存済みイベント、選択式JSON書出し・取込み、削除確認、U02/U03へ | 読込不可と未保存を区別。既存データを保持 |
| U02 | 基本6問の入力 | 条件付き施設入力、回答の見直し、初回生成→保存成功後だけU03 | 下書きは同一操作中保持・永続化しない。生成失敗なら画面維持 |
| U03 | 準備全体像・理由・次の一歩・進捗 | 4領域P01〜P12、P1/P2/P3、該当性、本人進捗、再確認、公式情報の根拠を別表示 | 独立CAS失敗なら成功と表示しない。該当taskId以外を書き換えない |
| U04 | 保存済みイベント編集 | 現行値と編集ドラフトを分離。「変更を反映する」でのみ確定、キャンセルは破棄 | revision競合・検証エラーは元の保存済み入力を保持 |

**U03の情報階層（確認用）**：イベント要約 → 今まず確認すること（理由・次の行動）→ 全タスク一覧（領域別）→ 本人進捗／再確認／出典状態。単なる色やバッジだけで状態の意味を伝えない。P1は「優先して確認」であり法的義務や危険判定ではない。

**操作保護**：U02下書き、U04未保存編集、U03保存中は新バージョン検知による強制リロード禁止。320px幅・200%拡大・キーボード・読み上げ・IMEの受入基準は維持。UIの見栄えの承認ではなく、実機検証を別途要する。

## STEP11｜データ・例外・安全性の設計確認

| 対象 | 保持する不変条件 | 設計上の失敗処理 |
|---|---|---|
| 新規作成 | U02保存成功で初めてイベント成立 | IndexedDB失敗時にU03へ遷移しない |
| 進捗 | 該当taskId単位のrevision CAS | 同時編集を黙って上書きしない |
| 編集 | U04明示保存、条件外となる施設固有入力のみ整理 | キャンセル・失敗・競合で元レコード不変 |
| 削除 | 削除済みIDを古いタブから復活させない | 古いタブでは競合として案内 |
| JSON書出し | 本人選択・初期0件、100件・2MiB上限、無断分割・切詰めなし | 超過時は選択見直し。実際のファイル保存成功は保証しない |
| JSON取込み | 形式・版・日時・IDを厳密検証、プレビュー承認後原子的追加 | どれか不正なら全件拒否、元DB不変 |
| 旧入力・未知schema | 既存内容を無断変更・切詰めしない | 更新不可理由と保護的な代替行動を明示 |
| 公式情報 | 有効な地域・施設・主体・出典のみ断定表示 | JST月末失効等は固有断定停止、一般タスクと本人進捗は維持 |

**公開前に技術値の固定が必要**：バックアップの`formatId`、`exportSchemaVersion`、`eventSchemaVersion`、`EventInput.date`、旧版対応表。STEP8-⑫は候補であり正式採用済みと表現しない。2MiB=2,097,152 UTF-8バイト。

## STEP12｜テスト設計と証拠の扱い

実装後に少なくとも以下の順で確認する：
1. **判定単体**：P01〜P12全分岐、未回答/未定の差、同順位、複数P1、再確認。
2. **保存統合**：初回保存失敗、CAS競合、削除後旧タブ、条件変更時の施設入力整理。
3. **バックアップ**：0/100/101件、2MiB境界、無効Unicode/日時、未知版、ID重複、原子的失敗、重複取込み承認。
4. **公式出典**：有効/期限切れ/地域不一致/施設不一致/利用主体不一致。一般タスクは保持。
5. **画面・アクセシビリティ**：320px/200%、主要PC・スマホブラウザ、キーボード、読み上げ、IME、保存状態の誤表示防止。
6. **利用者試験**：最優先の理由と次の行動を利用者が自分の言葉で説明できるか、行政義務と誤解しないか。

記録形式は既存STEP8-⑲の`caseId / inputs / preconditions / expected / actual / result / browser / os / testedAtJST / tester / evidence / issueLink`。**全ケースnot_run。** ユーザーが実装・試験実行を指示するまではactual/testedAtJST/PASSを記入しない。
