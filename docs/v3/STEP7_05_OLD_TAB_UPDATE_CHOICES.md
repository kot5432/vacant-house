# STEP7-⑤｜古いタブの新版検知・再読み込み導線（比較・未承認）

作成：2026-11-15。**A/B/Cの設計選択肢。採用前。** [ADR-012](ADR_012_BUNDLED_OFFICIAL_SOURCE_CATALOG.md)は「公式情報をアプリの静的ビルドに同梱し、新しい版の読み込み時に再掲載する」決定。ここで比較するのは**最新版があると利用者にどう知らせるか**だけで、出典を実行時に別配信・API化する提案ではない。対象は現行の地域イベント準備支援Webアプリのみ。旧空き家案なし。実装／試験／デプロイなし。

## 1. 前提と技術上の限界

- 出典カタログはGitのレビュー・Viteビルド・Vercel本番配信と同じ版で管理。タブが古いとき、最新`catalogVersion`や`reviewedMonth`を推測で`verified`に更新しない。
- 出典が期限超過したときの**安全側の非表示**は、現在開いているビルドの同梱データとJST時刻で再評価。新版があるかどうかを確認できなくても一般案内は維持する。
- 新版の有無を確認する方式を採用する場合でも、**ユーザーのEventRecordや入力内容を外部送信しない**。最新版検知の通信と、公式出典カタログの別配信は異なる。
- ブラウザの停止／スリープ中や誤った時計、オフライン状態では、リアルタイムな失効・新版反映は保証できない。

## 2. 3案比較

| 案 | 動作 | 利点 | 留意点 |
|---|---|---|---|
| **A（推奨）** | **同じ配信元の軽量なビルド識別子だけを起動時・タブ復帰時などに確認**。現ビルドと異なる場合に「最新版があります。再読み込みしてください」と案内し、**利用者が明示的に再読み込みする**。公式出典カタログ本体は別取得しない | 新版があることを検知でき、U04ドラフト保護も設計しやすい | 検知通信・キャッシュ無効化・同一オリジン・通信不能時の扱いなど追加の試験が必要 |
| B | **最新版の有無は自動チェックせず**、利用者が任意で「更新を確認」／「再読み込み」を行う。期限切れは画面側で評価 | 最も単純で外部通信を増やさない | いつ新しい公式情報が入ったか気付きにくい |
| C | 自動的に新しいアプリ版を再読み込みする | 利用者の操作負担が少ない | U02/U04の未保存入力の喪失リスク。アプリの初回未完成入力は永続保存しない方針と相性が悪く、**非推奨** |

**A案の通信はアプリ版の識別子を照合するもの**で、公式出典JSONそのものを実行時に読み込むADR-012不採用B案ではない。

## 3. A案の実装前契約の例（確定前）

- `buildId`のみを返す同一オリジンの静的メタデータ（例：軽量なビルド識別子）。ビルド同梱の`buildId`と比較し、不一致の場合のみ新版通知。
- 検査タイミング：起動時、U03表示時、タブ再表示時。表示中の頻繁な自動ポーリングを行うかは技術負担で決める。
- 読み込み不能／タイムアウト／識別子欠落／キャッシュで旧値しか見えない場合は**新版ありと断定しない**。期限超過時の施設固有断定停止は現行の同梱値を用いて別途判断する。
- 「最新版があります。変更を保存または破棄してから再読み込みしてください」など。**U04だけでなくU02の未完成6問も初回下書き非保存A案のため、勝手に再読み込みしない**。
- 更新をユーザーが選んだ場合、未保存入力があるときは再読み込みの前に明確に確認。非同期保存中は保存完了／失敗を判別する。
- 別のオリジン（Preview、本番、開発）間でIndexedDBやタスク進捗の同期があると誤認させない。
- 更新後に新しいルール版・出典版で評価し直しても、イベントの本人`completed/not_applicable`は自動変更しない。

## 5. 残る技術残件

- ビルド識別子の場所、キャッシュヘッダー、再取得の頻度・タイムアウト。
- アプリを表示したままJST月境界を越えるときの失効再評価と、ブラウザ非表示/スリープ復帰。
- 端末時計の不整合が疑われる場合の公式出典の安全側の扱い。
- `schemaVersion`と`rulesVersion`が新旧タブ間で異なる場合の読込保護。

## 6. 次のユーザー判断

A：軽量な**版識別子だけ自動確認して、再読込は本人の操作**（推奨）／B：本人が必要時に更新確認のみ／C：自動リロード（非推奨）。決定後にアーキテクチャ・U02/U03/U04・テスト・運用設計へ反映する。
