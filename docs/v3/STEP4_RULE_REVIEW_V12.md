# STEP4 判定ルール最終レビュー用仕様 v1.2（2026-11-15）

> **目的**：正式採用済みの条件と未承認の細則を明確に切り分けて、実装前の判定契約を完成可能にする。旧空き家物件／所有者診断／マッチングは対象外。プログラムコード・試験は未実施。
> 正式採用済み：[ADR-001技術](ADR_001_TECH_STACK_ADOPTED.md)、[ADR-002物理会場なし限定B案](ADR_002_NO_PHYSICAL_VENUE_SCOPE.md)、生成後の保存B、初回下書き非保存A。基本6問とP01〜P12・4領域を維持。

## 1. 6問とタスクの入力対応

| 基本質問 | 保存値の例 | 主な影響 | 避ける推定 |
|---|---|---|---|
| Q1 イベント種類 | workshop/lecture/exchange/other | P01, P06, P09, P10 | 種類だけで実施内容・必要設備を確定しない |
| Q2 参加対象 | minors/adults/both/undecided | P02, P05, P11 | 「主催者が未成年」と推定しない |
| Q3 希望時期 | date/month/undecided | P03, P06, P10, P12 | 14日前等の架空期限を設けない |
| Q4 会場状況 | undecided/candidate/confirmed/no_physical_venue | P07, P08, P09, P11, P12 | confirmed≠許可済、no_physical≠オンライン確定 |
| Q5 開催地域 | takaoka/toyama_other/outside_toyama/undecided | P07, P08, P09 | 市町村だけで施設種別を推定しない |
| Q6 主催者形態 | solo/group/undecided | P04, P05, P06 | 一人主催≠責任者決定済 |

基本6問の数は変えない。必要に応じた施設カテゴリ・施設利用者の年齢構成だけを条件付きで補う。人数・責任者・設備の必要性・内容説明は任意で、未回答は「不要」ではない。

## 2. P07〜P09の厳密な分岐（ADR-002を反映）

| Q4 | P07親 | P08親 | P09親 | 施設専用の細目 |
|---|---|---|---|---|
| undecided | `yes`、候補場所を整理 | `needs_information`、施設条件が必要か確認 | `yes`、必要環境を整理 | 具体施設の申込条件は推定しない |
| candidate | `yes`、候補の条件を比較 | `yes`、候補施設の条件を確認 | `yes`、必要設備の確認 | 本人の明示カテゴリ＋根拠適合時だけ施設固有 |
| confirmed | `yes`、新しい場所探しは求めない | `yes`、確定していても利用条件は確認 | `yes`、設備と利用環境を確認 | 本人の明示カテゴリ＋根拠適合時だけ施設固有 |
| no_physical_venue | `needs_information`、建物の会場探しは求めず開催方法・場所を確認 | `needs_information`、建物予約は適用外、屋外等の条件の要否は未確定 | `needs_information`、館内設備は非該当、開催方法に必要な環境を一般確認 | 建物の選定／施設予約／館内備品子項目は `no`。オンライン固有・屋外固有の可否判定は提供しない |

**注意**：親の`needs_information`は「手続き必須」という判定ではなく、要否を判定するだけの入力がないこと。条件による子項目の`no`と、本人が親を手動`not_applicable`にした状態を混同しない。P07〜P09の親ラベルは基本IDを維持しつつ、`no_physical_venue`では表示の説明を切り替える。

## 3. 施設固有情報の判定境界

対象施設の重要注意を表示するには**同時に全条件を満たす**：
- Q5が高岡市
- Q4が候補あり／本人申告の決定済み
- 利用者が該当施設カテゴリ（高岡市地域交流センター）を**明示選択**
- 必要な施設利用者の年齢構成・該当条件が本人回答または適用を断定できない状態として扱われる
- 公式出典台帳の出典ID、適用対象、確認日が照合できる

条件を満たさない場合は**その施設の断定文を出さない**。利用者本人の自由記述の施設名から施設カテゴリを推定しない。個別の利用許可や安全性をアプリで判定しない。

## 4. 進捗と再確認：未解決を決める真理値表（提案）

| `applicability` | `progress.status` | `needsRecheck` | 結果 |
|---|---|---|---|
| no | 任意 | 任意 | 現行タスクは優先候補外。ただし過去履歴と再確認理由を保持 |
| yes / needs_information | not_started / in_progress | false/true | 未解決として表示 |
| yes / needs_information | completed | false | 通常の未解決から除外。「利用者が完了とした」と表示 |
| yes / needs_information | completed | true | **未解決として優先候補へ復帰**。「以前は完了・再確認が必要」 |
| yes / needs_information | not_applicable | false | 本人の対象外判断を尊重。安全/出典の一般的注意は表示から消さず、「不要の確認は本人判断」と明記 |
| yes / needs_information | not_applicable | true | 対象外判断の前提が変わったため未解決として再確認を表示 |

- `needsRecheck`は関連フィールドが更新されただけでは付けず、以前完了／対象外とされた内容の**確認前提が失効し得るときのみ**付ける。
- 結果画面で詳細を開くだけでは再確認を解除しない。本人が新しい条件を確認したことを明示する操作が必要。
- 公式情報が未確認または対象外になったら、古い公式文言を現在のプランから削除する。過去の進捗の履歴は別途保持。
- ユーザーの過去の「完了」「対象外」を勝手に未着手へ書き換えない。

## 5. 未決の優先度細則：比較して承認する項目

### 5.1 P05（一般安全・見守り）の基本優先度

- **案A（推奨）**：成人のみの場合の一般安全確認はP2。対象未定は「見守り要否の確認」P2、子ども/両方はP1。良い点：基本的な安全確認の見落としを減らす。留意：P2が多くなる可能性。
- **案B**：成人のみの一般確認はP3。対象未定はP2、子ども/両方はP1。良い点：P2を前提条件に集中。留意：安全の一般確認が埋もれる可能性。

**P1=危険認定ではなく確認の優先順**。人数・イベント内容から必要な安全要員数や医学的/法的判断は行わない。

### 5.2 同じ優先度の代表順

- **案A（推奨）**：同優先度ではタスクID昇順（P01〜P12）。シンプルで説明しやすい。ただしP08がP05より後ろに回ることがある。**すべてのP1を同じ優先欄に明示**するので残るP1は隠さない。
- **案B**：出典付き施設条件P08→未成年の安全P05→会場P07→責任者P04→時期P03→設備P09→残りID。準備に沿う可能性はあるが「施設条件を安全より先にする理由」が未検証で、状況によって不自然。
- 公式の明示期限を優先する機能は現MVPの入力とルール契約では採用しない。**「開催14日前」という閾値は未採用**。

### 5.3 P08物理会場なしの優先度

- **推奨：P2の一般確認候補**。建物予約案内は出さないが、屋外等の利用条件の要否が不明なため「確認が必要か調べる」を提示。P1の施設固有根拠には絶対昇格しない。
- 将来オンライン等の形式を追加すれば分岐を再評価する。未定が法令違反という意味ではない。

## 6. 具体的な出力文言のテンプレート例

| 条件 | 優先理由の例 | 次の行動の例 |
|---|---|---|
| Q4=undecided | 「会場の状態が未定なので、条件を整理すると他の準備も進めやすくなります」 | 「候補となる場所の必要な広さや設備を整理する」 |
| Q4=confirmed | 「会場は決まっていますが、利用条件を確認したかどうかは入力から分かりません」 | 「利用条件と必要な手続きを施設の管理者に確認する」 |
| Q4=no_physical_venue | 「建物の会場を使わないとのことですが、開催方法によって確認すべきことが変わります」 | 「開催する方法・場所と、必要な利用条件がないかを整理する」 |
| Q2=minors/both | 「子どもが参加するため、運営側の見守り体制を事前に確認することが役立ちます」 | 「見守り・連絡体制と責任者を確認する」 |
| P08=completed+recheck | 「以前は確認が完了していましたが、会場の前提が変更されています」 | 「新しい会場の条件を確認し、再確認を完了にする」 |

これらは**例文**であり、実際の行政情報や子どもの安全を保証しない。正式な固定文言はUIレビュー後に決める。

## 8. 正式な確認ゲート

判定エンジンに実装を渡すため残る重要判断：
1. P05一般安全確認のP2/P3基準。
2. 同順位時、単純な安定ID順か、P08/P05などの固定順か。
3. P08の物理会場なしの一般確認をP2に固定するか。

これ以外に、出典台帳の最新版照合、データ型・検証値の完全列挙、保存時の競合/削除のUI検証は必要。**ユーザーの明示採用なしに残る優先度細則を確定しない**。
