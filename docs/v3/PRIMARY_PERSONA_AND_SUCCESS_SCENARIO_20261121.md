# 主役のペルソナを一人に固定する（2026-11-21）

## 決定する設計上の中心人物
**佐藤 葵（架空の18歳・高岡市在住の学生）**。地域の小学生10人程度に向けた約90分の小さな勉強会を、来月、初めて開きたい。主催経験はなく、個人で構想中。会場は未定。

**本人の課題**：「やりたいことは決まっている。でも会場・運営体制・子どもの安全・告知など、準備の全体像と何を先に確認すべきかが分からない」。

**期待する成果**：自分の条件からP01〜P12の準備タスクを確認し、**今日の最初の行動を理由・出典とともに説明できる**。アプリは開催可否や施設使用・法令上の許可を保証しない。

## 一人の利用場面に沿った主要導線
1. D00で「企画する」を選ぶ（D01/D02の参加機能を経由する義務はない）。
2. U01から新規イベント作成へ進む。
3. U02で既決の基本6問と必要な補助項目を入力。勉強会・子ども対象・個人・約10人・来月・会場未定・高岡市を**テストシナリオの例**として使用する（実際の値/キーはADR-029〜032に従い、勝手に必須項目を追加しない）。
4. U03でP01〜P12の全体像と優先順位、理由、次に確認することを見る。P05等は既定の安全判定に従い、P08を施設データから自動P1昇格させない。
5. 進捗を更新し、必要ならU04で会場等を変更。要再確認と保存成否を正しく区別する。
6. 本人が次の具体的な行動を自分の言葉で説明できれば成功とみなす。

## MVPへの影響
**今回の変更は「中心ペルソナと応募説明の一本化」のみ。** 正式採用済みの[ADR-030](ADR_030_TOYAMA_PARTICIPATE_AND_ORGANIZE_MVP_SCOPE_ADOPTED.md)の「参加＋企画」二入口は維持し、AのD00/D01開発も取りやめない。参加側は補助的価値として扱い、公式掲載承認済み0件なら正直な空状態を表示する。主催側の保存形式・優先順位・親タスク・JSONバックアップ契約は変更しない。

## 実際に確かめる仮説（未検証）
- 初めて小規模イベントを企画する人は、準備の順番が分からず困る場合がある。
- 単なるチェックリストより「自分の条件に合う優先順位と理由」があると、次の行動を説明しやすい。
- 保存/再確認は中断後の再開に役立つ。

この人物は**ユーザー調査結果ではなく仮説ペルソナ**。実在の人数・需要・効果を裏付ける数字として使わない。調査計画は[STEP22](STEP22_DEMAND_DIFFERENTIATION_VALIDATION_PLAN_20261119.md)。外部ヒアリングの実施・連絡は未許可。

「地域で小さな勉強会を開きたいけれど、何から準備すればよいか分からない。そんな初めての主催者が、準備の全体像と最初に確認すべきことを理由付きで整理できるWebアプリ。」
