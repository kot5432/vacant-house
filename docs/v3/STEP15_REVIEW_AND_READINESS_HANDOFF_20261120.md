## 3. レビュアーに伝える一律の確認手順
1. 該当PRの`Files changed`で編集されたファイル名/差分/削除を確認する。**今現在のmain**と照らし、既存のSTEPが消えないかを確認。
2. **レビュー観点**：ADR-029〜032不変、現在のMVPは参加D00〜D02と企画U01〜U04、Dの先行共通環境、E主レビュー方針、11/23からローカル実装許可、CI/デプロイ未許可。
3. README・CONTRIBUTING・ACTION_CHECKLIST・WORK_PACKAGEの追加行が他PRと重なっている場合、無条件の片方採用をしない。後続PRでは先行済みmainを取り込み、各STEPのリンクと最新決定を残す。
4. 問題があれば`Request changes`やPRコメントで具体的な修正箇所を伝える。問題がないと本人が判断した場合にのみApproveする。
5. **Eが書いたPRの承認は他担当によるレビュー**であり、Issueに「レビュー完了」と書くだけではGitHub承認数に反映されない。
6. レビュー承認後に新しいコミットが追加されたら、古いApproveはGitHub側で自動失効しない（現設定では`dismiss_stale_reviews_on_push=false`）。**最新差分の再確認**を求める。
7. approvedになってもすぐ全PRをまとめてマージしない。**一件ずつmainに統合→次PRのmergeable・差分・リンク・仕様優先順位を再確認**する。安全性が不明ならマージしない。

## 4. 11/23開始時のGo/No-go（自動判定しない）
- **Start（準備作業）**：各担当の現有環境でできる設計/画面の独立作業は継続可能。本人のPCの環境が未確認でもすべての人の作業を停止させない。
- **Start（ローカル実装）**：ユーザーがSTEP6で11/23から明示許可。各自の実機環境と現行ADR契約を確認してから進める。**コード実装が済んだとは扱わない**。
- **Hold（mainへの統合）**：別人のApproved、必要な検証、未解決コメント解消、競合の解消が揃うまで統合しない。
- **Hold（外部操作）**：CI・Vercel/Cloudflareへのデプロイ・公開URL作成・外部調査配布・応募送信は明示的な別許可が必要。
