# STEP7-⑱｜JSONバックアップのバージョン互換性（未決の選択肢）

作成：2026-11-15。**利用者判断待ち**。採用済み：[ADR-015](ADR_015_JSON_BACKUP_EXPORT_IMPORT.md)（JSON入出力）、[ADR-016](ADR_016_IMPORT_COLLISION_AS_COPY.md)（衝突時別IDコピー）、[ADR-017](ADR_017_REPEAT_IMPORT_WITH_CONFIRMATION.md)（再取込注意）、[ADR-018](ADR_018_RESTORED_EVENT_REVISION_AND_PROVENANCE.md)（revision=1・日時由来）、[ADR-019](ADR_019_JSON_BACKUP_LIMIT_2MIB_100_EVENTS.md)（2 MiB／100件）、[ADR-020](ADR_020_MANUAL_EVENT_SELECTION_EXPORT.md)（選択式分割）、[ADR-021](ADR_021_EXPORT_INITIAL_NONE_SELECT_ALL_WITHIN_100.md)（初期未選択）。現行地域イベント準備支援アプリのみ対象。旧空き家アプリのJSONは復元不可。実装・実行試験なし。

## なぜ決めるか

長期間バックアップを保管すると、アプリの`schemaVersion`やJSON形式`exportSchemaVersion`が変わり得る。一方、古いJSONを無条件で受理すると本人の進捗やイベント条件を誤解釈する。**バージョンの違いを無視して読み込んだり、未知フィールドを削って成功と扱うことは不可**。

## 3案比較

| 案 | 復元を認める範囲 | 利点 | 注意 |
|---|---|---|---|
| **A（推奨）** | **現在の形式＋移行手順を検証済みの既知の旧形式**。未対応の旧版・未知将来版・別プロダクトIDは拒否 | 保存データを可能な範囲で長く利用でき、型・意味の検証で安全性を維持 | 旧版移行テストや対応版一覧が必要。どの旧版をサポートするかは実測後に確定 |
| B | **現在の同一`exportSchemaVersion`だけ**受理 | 実装とテストが単純 | アプリ更新後に古いバックアップを復元できなくなるおそれ |
| C | **未知の将来版も柔軟に読み込み**、使えるフィールドだけ採用 | 広く復元を試みられる | 不明な構造・進捗を黙って失い、保存データを誤解釈する可能性が高いため非推奨 |

**A案推奨**：直近で使われていた古いJSONを安全に取り込める余地を残す。ただし、すべての古いJSONと互換である保証はしない。未対応版は明示的に拒否し、元DBを変えない。

## A案の技術契約候補（未承認）

1. `formatId`は現行アプリのJSONバックアップ専用の固定識別子。旧空き家／他アプリのJSONは同名のフィールドがあっても拒否。
2. `exportSchemaVersion`と各イベントの`eventSchemaVersion`を**分けて比較**。`buildId`・`rulesVersion`・`catalogVersion`を同一視しない。
3. 移行を許す既知旧版ごとに**版を特定する厳密な検証→データ意味を変えない変換→最新形式で再検証**という手順を定義。移行不可のフィールドがあれば無断切捨てせず復元を拒否。
4. インポートの**2 MiB／100件制限は変換前のファイルにも適用**。変換後の表現が大型化する場合のメモリ技術上限は別途検証。
5. 進捗と本人の再確認は保持し、導出タスク・公式出典は復元先の現在版で再評価。未知の`progressByTask`や施設条件を解釈できない場合に黙って「完了」へ変更しない。
6. サポート対象となる具体的な旧`exportSchemaVersion`の番号・最大何世代までを含むかは**実際にバージョンを発行した後**に設計と試験により確定する。存在しない旧版をサポート済みと書かない。
7. 本人の承認前にDBに書込まず、衝突・繰返し・別IDコピー・原子的追加とrevision=1はADR-015〜018に従う。
