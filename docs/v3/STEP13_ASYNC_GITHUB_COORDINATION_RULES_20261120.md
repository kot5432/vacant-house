# STEP13｜GitHub非同期進捗共有・相談・ブロッカー対応ルール

決定日：2026-11-20。利用者決定：**B案＝GitHub上の非同期共有を中心にする。定例会議を必須にせず、必要時のみ短い打ち合わせ**。対象：2026年11月23日からのA〜D並行開発、E品質レビュー。

## 1. 唯一の正本と役割
- **担当Issue**は「今何を作るか・担当・期限目標・作業状況・困りごと」の正本。#34（A）/#36（B）/#38（C）/#51→#40（D）、#43（E）、#45（横断統合）。
- **PR**は「実際にどこを変更したか・確認/未確認・レビュー議論・マージ判断」の正本。IssueにPRリンクを貼る。
- **#55**は11/23開始前の各人のGit/Node/npm環境確認と作業可能時間の報告専用。進捗の定例投稿とは分ける。
- **#45**は全体依存・統合ブロッカーの一覧。担当Issueだけで解けない問題は#45にリンクを追加する。
- **E @kot5432**は週次に#45を整理し、A〜DのPRを原則主レビュー。E自身が作ったPRはA〜Dの別人レビューを受ける。Eがすべての技術判断を単独で背負うのではなく、型はD/B/C、ActivityCatalogはA/Eで相談。
- 日々の雑談・通知はチームの任意の連絡手段を使ってよいが、**仕様・優先度・担当・マージ判断の結論はGitHub Issue/PRに残す**。GitHubが唯一の最終記録。

## 2. 頻度（非同期を第一とする）
1. **各人が週1回、担当Issueに進捗をコメントする**（目安：金曜〜日曜の好きな時間。11/23〜29初週も同じ。毎日報告は求めない）。
2. 作業が進みPRを作った時や、依存・仕様の質問が発生した時は、週次投稿を待たず**対象Issue/PRにコメント**する。
3. 質問は適切な担当者へ`@mention`。ブロッカーは「何が止まったか／必要な回答／影響Issue／暫定回避」を簡潔に記す。
4. **緊急でない質問の返事の目安は48時間**。授業・試験・休日などで遅れる場合は「いつ確認できそうか」を答えるだけでよい。強制的な常時通知や夜間即応を要求しない。
5. **24時間以上作業が止まりそうな依存**は、分かった時点で担当Issueへ書き、#45にもリンク。期限近くまで抱え込まない。
6. 返信が得られない場合、Eが情報を整理して関係者へ再確認。**本人の承認を推測して仕様変更やマージを行わない**。

## 3. 各人の週次コメントの型
```text
【週次進捗｜11/23〜11/29】担当：A/B/C/D/E
対象Issue：#...
状態：未着手 / 作業中 / PR準備中 / レビュー待ち / ブロック中 / 完了
今週できたこと：（実際に終えた事実・PR URL）
次にやること：（作業を1件）
困りごと・依存：（なし / 誰のどの回答待ちか、Issueリンク）
テスト：未実施(not_run) / 実施済み（コマンドと結果はPRに記載）
目標への影響：予定どおり / 要調整（理由）
```
- 状態「完了」は**別人レビュー・必要検証・mainマージ・受入確認を経たもののみ**。PR作成だけで完了扱いにしない。
- 学校・私生活の細かな事情や個人情報を公開Issueに書く必要はない。「今週は時間が少ない」で十分。
- PR未提出ならURL欄を空欄/「なし」にする。存在しないPRや実行ログを作り出さない。

## 4. 質問・仕様変更・ブロッカーの流れ
- **自分のUI内の質問**：担当Issueにコメント → 関連担当をmention → 根拠ADRを確認 → 返答をIssueに記録。
- **B/Dの入力型・保存API、C/DのCAS、B/CのU03境界**：担当Issueと#45で相互参照。Dが共有型、Bが判定、Cが進捗操作を持ち、別担当のコードを無断で上書きしない。B/Cは共有環境が未統合ならmockと明示。
- **A/Eの地域データ**：出典未確認や別人レビュー未完なら`visible=0`のまま。質問を出しても公開承認にはならない。
- **ADRと矛盾する新要件**：実装を止め、Issueに「変更案・理由・影響範囲・代案」を記録。Eが利用者の確認を取り、正式な変更決定後にPRを更新。
- **動作不具合/セキュリティ**：公開Issueに鍵・個人情報・実データを貼らない。機密内容は安全な経路でEへ連絡し、公開Issueは抽象的な状況のみ。データ損失や安全性に関するPRはマージ前に原因を確認。

## 5. 打ち合わせを行う例外条件
通常は定例会議なし。次のいずれかで**非同期だけでは判断できない場合**に、関係者だけで15〜20分程度の短い相談を提案する（全員を必ず集めない）。
- B/C/Dの型やU03統合方針が食い違い、Issue上のやり取りでは合意できない
- 11/29の小PR目標または12/20の統合計画に大きな影響
- 安全性・保存データの破損リスク・旧仕様との衝突
- 同じ問題が複数回行き来し、対話したほうが早い

**会議の前**にIssue URLと決めたいことを共有、**会議の後**に担当者が決定/未決/次の担当をIssueに残す。会議だけで仕様変更を完了させない。

## 6. PRレビューとマージ
1. 1 Issue ≒ 1小PR。A〜Dがレビュー依頼するときはE @kot5432を指名し、必要時に技術担当を追加する。
2. E作成のPRはA〜Dから別人レビューを得る。mainの既存`protect-main` rulesetはActiveでPR＋承認1名・未解決レビューコメントの解決を求める。
3. 作業中のPRはDraftを許容。**Eが差分・ADRとテスト結果を確認してから承認**する。実行していないテストは`not_run`。
4. 新コミットによる既存承認の自動失効は現時点では無効のため、**承認後の変更差分がある場合は人が最新差分を再確認**してからマージ。
5. レビュー待ちが増えたらPRを小さくし、Eは#45でレビュー順を共有する。Dの共有環境#51が初期の最優先で、その後A〜Cの接続部分/ #40の型を調整する。
6. **CI/デプロイ・プレビュー公開・応募送信は未許可**。ローカル実装・ローカル実行テストのみSTEP6で11/23以降許可されている。

## 7. 最初の週の運用（11/23〜29）
- **初日**：#55で各自環境と参加可否を共有。Dは環境#51、Aは#34、Bは#36、Cは#38を開始できる範囲で準備。
- **作業中**：依存があれば即Issueコメントと`@mention`。待っている間は依存しない小作業を進める。
- **週後半**：11/27を小PR提出の努力目標、11/29をA〜D各1PRの初週目標とする。Eはレビュー待ち状況を#45で整理。
- **週次報告**：各人が11/27〜29の好きな時間に担当Issueへコメント。欠けている場合はEが追跡するが、完成を推測して埋めない。
- **初週Done判定**：提出状況・レビュー状況・実際に実行したローカル確認結果は別々に記録する。
