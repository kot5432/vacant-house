# 実装着手前｜4人AI開発のGitHub Issue・レビュー実行計画 v0.2

作成：2026-11-18。**設計資料のみ。GitHub Issues/Projects/ラベル/ブランチ/PRは作っていない。コード実装・試験実行・CI・デプロイはしていない。**

対象v3.1。**4人全員初心者／AIコーディング中心**。機能をGitHub Issuesの大分類、コード責務を`domain/application/infrastructure/features`で分離する。旧空き家案の機能は対象外。

参照：[機能8分類・16 Issue原案](FEATURE_MODULES_AND_GITHUB_ISSUES_PLAN.md) ／ [共有型](PREIMPLEMENTATION_SHARED_DATA_CONTRACT_REVIEW.md) ／ [サービスと画面](PREIMPLEMENTATION_UI_SERVICES_AND_ERROR_CONTRACT.md) ／ [4人開発計画](PREDEV_FOUR_PERSON_AI_DEVELOPMENT_PLAN_20261117.md)。

## 1. 管理する単位

- **Epic相当**：F0共通 / F1入力編集 / F2判定 / F3進捗 / F4保存・一覧 / F5バックアップ / F6出典・更新 / F7 UI・品質。GitHubではProjectのAreaフィールド／ラベルでグループ化。
- **Issue**：1つの見える成果、1人の主担当、別のレビュアー、依存、対象ADRと受入条件。大きすぎるものは子Issueに分割。
- **PR**：1 Issueにつき原則1 PR。変更パスと受入ケースを明記。AIにすべてのファイルを無制限に書き換えさせない。
- **Projectの状態**：Backlog→Ready→In progress→Review→Testing→Done。現時点の実装案件はBacklog、設計レビューはReady止まり。**実行テストなしでTesting/Doneへ進めない**。
- **衝突を避けるラベル**：`area:foundation/event-input/rules/plan/data/backup/sources/quality`、`type:design/feature/test/docs/bug`、`work:critical/normal/later`。`priority:P1`はアプリ内P1と誤解されるため使用しない。

## 4. すぐに起票するなら「設計」と「実装」を別Issueへ

- 設計を閉じる順：`DESIGN-01`イベント説明・importedFrom・全入力キーの凍結→`DESIGN-02`画面サービス公開型→`DESIGN-03`固定受入データ→`DESIGN-04`GitHub運用の担当者・権限→`DESIGN-05`施設出典の監査計画。
- 実装の`PLAN-01〜16`は着手許可が出るまでBacklogとし、**未作成のPRを作成済みと表現しない**。
- 最初の統合体験は`U02入力→保存成功→U03理由・一歩`。保存を飛ばした「動くデモ」を完成MVPと呼ばない。

## 5. 4人全員がAIを使うときの具体ルール

1. 開発担当はIssueの**入力・出力・触ってよいファイル・禁止する仕様変更**をAIへ渡す。ADR-001〜029の最新決定を優先。
2. AIのPR出力は**差分だけでなく境界ケースを人が読む**。生成コードの長さや速度を成功指標にしない。
3. Aは共通型/優先度のAPIを主にレビュー、Cは保存/JSONの原子性を主にレビュー。Dは公開/品質のチェック、Bは画面文言/操作のチェック。ただし**自己PRを自己承認しない**。
4. `App.tsx`, `event.ts`, `database.ts`, `package.json`など共有ファイルの変更は先に担当者間で調整。AIの自動全体リファクタリングを無断マージしない。
5. PRには**AIで生成した範囲・人が修正した点・実際のテスト実行記録・未確認事項**を記載。初回は小PRでチーム運用を練習する。
6. 当日のリリース役、月次出典レビュー役、バックアップ最終確認役は明示割当。権限・公開作業はユーザーの許可まで実行しない。
7. 公式根拠の原文確認・施設への実際の問い合わせ・個人データの扱いはAIに自己認定させない。
8. 初心者のため、**毎PRで人間が「何を変えたか」「元に戻すには」「どの確認が必要か」を短く説明できる**ことをチェックする。

## 6. Issue本文テンプレート（登録時に貼り付け）

```md
## 目的と利用者の体験
## 参照する最新ADR・現行仕様
## このIssueで変更してよいフォルダ・ファイル
## 触ってはいけない契約・他Issueの責任
## 入力と期待結果（架空データ）
## 正常系・保存失敗・競合・不正データの受入条件
## 依存Issueと先に固定する公開型
## AIへの指示／AI利用記録
## 人間のレビュー観点
## テスト証拠（未実施ならnot_run）
## 完了条件・未決事項
```

## 7. PR本文テンプレート（登録時に貼り付け）

```md
## 対応Issue／設計書・ADR
## ユーザーから見た変化
## 変更パスと依存関係
## 変更していない既決仕様
## 実際に確認したこと（コマンド/ブラウザ/入力/出力/証拠）
## 未実行・未確認
## AIツール名と作成内容、人が修正・確認した内容
## データ互換性と既存イベントの保護
## レビュー担当と統合時の注意
```

**テスト未実施の時点で「PASS」と書かない**。PR/Issue/CIやVercelをこの文書だけで自動作成しない。

## 8. 実装開始前のDoR（Definition of Ready）

- [ ] DESIGN-01の全フィールドとJSON v1の機械可読スキーマ／検証表のレビューが完了
- [ ] U01〜U04とサービスのエラー型・保存境界の統一
- [ ] 4人の仮担当A〜Dを実際の担当者に割り当て、レビューの代理を確保
- [ ] 架空の固定入力と期待結果のセットを2条件以上準備
- [ ] GitHub権限、main/PR、ブランチ方針、実装しない仕様の禁止表の共有
- [ ] 実装開始をユーザーが明示許可

**実装完了や公開には別のDone/G5/G6ゲートが必要**。アンケート・施設管理者への実連絡も別途承認・証拠が必要。
